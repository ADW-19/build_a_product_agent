# 第二章：中间件选型

## 2.2 PostgreSQL vs MySQL 8.0

### 2.2.1 结论

**选 PostgreSQL，因为 Agent 场景天然需要非结构化数据能力 + 向量扩展。**

### 2.2.2 什么是关系型数据库？（概念）

关系型数据库就是"用表格存数据"的数据库。每张表有固定的列结构（Schema），数据一行一行存，不同表之间通过"外键"关联。——这是最经典的企业数据存储方式，MySQL 和 PostgreSQL 都属于这一类。

### 2.2.3 核心对比

| 维度      | MySQL 8.0                               | PostgreSQL                                            |
| --------- | --------------------------------------- | ----------------------------------------------------- |
| JSON 查询 | ⚠️ 5.7+ 就有 `->` / `->>` 运算符；但缺 `@>` 包含运算与 JSONB 式 GIN 索引，多值索引需 8.0.17+ | ✅`->` / `->>` / `@>` 全套操作符，JSONB 直接建 GIN 索引 |
| 全文搜索  | ⚠️ InnoDB 原生 `FULLTEXT`（自然语言/布尔模式），CJK 要 ngram 解析器；无 `ts_rank` 类相关度算子、算子少 | ✅ 内置 `tsvector` + `tsquery` + GIN，相关度排序、查询词位置/权重算子丰富 |
| 向量支持  | ❌ 8.0 无（MySQL 9.x 才有 `VECTOR` 类型，Community 版仅存储，无 ANN 索引与 `VEC_DISTANCE_*`） | ✅`pgvector` 扩展，可在同一张表做混合检索           |
| 扩展能力  | 弱，插件生态有限                        | 强，`pgvector`、`pg_cron`、`postgis` 等活跃扩展 |
| 复杂查询  | ⚠️ 嵌套查询优化一般，CTE 较晚才完善   | ✅ 优化器成熟，CTE + 窗口函数 + LATERAL JOIN          |
| 并发模型  | 单进程多线程                            | 多进程，长事务更稳                                    |

### 2.2.4 三个决定性的理由

**理由一：Agent 大量存储 JSON。**

Agent 的每一步推理、工具调用结果、用户上下文都是半结构化的。比如一条对话记录：

```json
{
  "session_id": "abc123",
  "messages": [
    {"role": "user", "content": "帮我查一下订单"},
    {"role": "assistant", "tool_calls": [{"name": "search_order", "args": {"user_id": 42}}]},
    {"role": "tool", "name": "search_order", "content": "[{...}]"}
  ]
}
```

PostgreSQL 的 **JSONB**（二进制 JSON）支持在 JSON 字段上建 GIN 索引，可以直接在 WHERE 子句里查 JSON 内部字段，速度不输普通列。MySQL 8.0 也有 JSON 类型和 `->` / `->>` 运算符（5.7 起就有，`->>` 等价于 `JSON_UNQUOTE(JSON_EXTRACT(...))`），但**真正拉开差距的是索引**：PostgreSQL 的 GIN 索引可以对任意 JSON 路径建索引、支持 `@>` 包含判断；MySQL 到 8.0.17+ 才有多值索引（multi-valued index），还得先建虚拟生成列，路径和查询形态都受限。JSON 功能 MySQL 是"能用"级别，PostgreSQL 是"好用"级别。

**理由二：Agent 需要"模糊搜索 + 精确过滤"混合查询。**

例如："找出最近一周用户提到'退款'的对话，按时间倒序"——这既需要全文搜索（`tsvector` 查"退款"），又需要精确过滤（时间范围 + 用户 ID）。PostgreSQL 一条 SQL 搞定。**注意这里的差距不是"MySQL 完全没有全文检索"**：MySQL 8.0 的 InnoDB 原生支持 `FULLTEXT` 索引（自然语言模式与布尔模式），CJK 还需要手动指定 ngram 解析器。差距在能力深度——MySQL 没有 `ts_rank` 这类相关度算子、检索词位置/权重/短语算子也少得多，和 JSON 字段、向量字段的联合过滤更是缺位，实际做到"可用的中文语义检索"时通常还是得外接 Elasticsearch。PostgreSQL 的优势是 `tsvector/tsquery` + GIN 索引 + 与 JSONB / 向量**同库混合过滤**：检索、过滤、排序写进一条 SQL，不需要跨系统同步数据。

**理由三：pgvector 让向量和业务数据同库共存。**

Agent 的 RAG（检索增强生成）场景需要在同一个查询里混合向量相似度排序和业务字段过滤。PostgreSQL + `pgvector` 扩展可以做到：

```sql
SELECT content, 1 - (embedding <=> %s) AS similarity
FROM documents
WHERE user_id = $1 AND created_at > $2
ORDER BY embedding <=> %s
LIMIT 10;
```

**对 MySQL 8.0 而言，你无论如何都要额外引入一个向量数据库**——8.0 没有向量类型，也没有向量索引（MySQL 9.x 才提供 `VECTOR` 数据类型，但 Community 版只有存储、没有 ANN 索引和 `VEC_DISTANCE_*` 距离函数，向量索引能力在 HeatWave / MySQL AI 里）。

### 2.2.5 什么时候选 MySQL？

如果你的业务是**纯 OLTP，表结构固定、无 JSON 查询/全文检索/向量需求**，MySQL 仍然是成熟的选择。但对于 Agent 后端这些需求全是刚需，PostgreSQL 更合适。

## 2.3 Milvus vs Chroma vs FAISS

### 2.3.1 结论

**选 Milvus，因为它是面向生产的分布式向量数据库。Chroma 适合原型开发，FAISS 只是一个索引库。**

### 2.3.2 什么是向量检索？（概念）

LLM 不认识你的私有数据（比如你公司的产品手册、用户历史对话），但它可以先把文本"翻译"成一串数字——这叫**向量嵌入（embedding）**。两段意思相近的文本，它们的向量在数学空间里距离就近。

"帮我查一下退货政策" → `[0.12, -0.34, 0.56, ..., 0.78]`（1024 维浮点数向量）

当你提问时，系统把问题也转成向量，然后在库里找到距离最近的几条文本，塞进 LLM 的 prompt 里作为上下文——这就是 **RAG（检索增强生成）**。向量数据库就是专门干"找最近向量"这件事的。

### 2.3.3 三者的本质区别

```
              Chroma              FAISS               Milvus
             (向量数据库)        (向量索引库)        (分布式向量数据库)
             
本质：     轻量级嵌入式 DB       Facebook 开源       Zilliz 开源的
           一键 pip install    的向量检索库        分布式系统

部署：     pip install即可      无独立进程，        独立服务，需要
          无独立服务             只是一段 Python 代码  docker/k8s 部署

适用：     原型/DEMO           本地数据集          生产环境
           (<10万条向量)        (单机十亿级)         (分布式亿级)
```

**FAISS 不是数据库。**

FAISS 不提供数据持久化、不提供 CRUD、不提供分布式部署、不提供权限控制。它就是一堆 C++ 实现的向量索引算法，你得自己管理数据存哪、怎么增删改查。把它类比：FAISS 是"手搓的排序算法"，Milvus 是"数据库管理系统"。

注意：**容量不是 FAISS 的短板**——它是 Meta 专为十亿级向量检索设计的索引库（IVF/HNSW+PQ，GPU 加速可承载亿级以上）。FAISS 与 Milvus 的真正差异是"单机索引库 vs 分布式系统"、"库 vs 索引库"，而非百万级上限。

**Chroma 不适合高并发 C 端。**

Chroma 设计目标是"开发体验优先"——pip install 零配置就能跑，非常适合 DEMO。但它：

- 开源/单机版不支持真正的水平扩展（Chroma 另有分布式与托管版本；单机版不能像 Milvus 那样加节点扩容）
- 索引算法单一，海量数据下召回率和速度都不如 Milvus
- 缺乏多租户隔离、资源配额等生产特性

### 2.3.4 核心对比

| 维度         | FAISS               | Chroma        | Milvus           |
| ------------ | ------------------- | ------------- | ---------------- |
| 部署模式     | 嵌入代码            | 嵌入/独立进程 | 分布式集群       |
| 持久化       | ❌ 需手写           | ✅ 半自动     | ✅ 原生支持      |
| 水平扩展     | ❌                  | ❌            | ✅ 分片+副本     |
| 索引类型     | 多种（IVF/HNSW/PQ） | 有限          | 丰富（11种+）    |
| 混合检索     | ❌                  | ⚠️ 实验性   | ✅ 标量过滤+向量 |
| 一致性保证   | 无                  | 弱            | 强一致性可选     |
| 数据规模上限 | 十亿级（单机） | ~100 万 | 亿级+（分布式） |
| QPS 上限     | 受限于单机          | 受限于单机    | 数千 QPS         |

### 2.3.5 三个决定性的理由

**理由一：高并发 C 端需要分布式能力。**

C 端场景下，同时可能有数千用户在做 RAG 问答。Milvus 支持分片（把一个集合的数据拆到多台机器）和副本（同一份数据存多份），既扛高 QPS，又保证高可用。Chroma 和 FAISS 都是单机方案，一台机器撑不住就只能改代码。

**理由二：混合检索（标量 + 向量）是 Agent 的刚需。**

Agent 的知识库检索往往带过滤条件：

- "只搜索我团队内部的文档"（tenant_id 过滤）
- "只搜最近 30 天更新的产品手册"（时间过滤）
- "只搜状态为'已发布'的知识条目"（状态过滤）

Milvus 支持在向量检索的同时做标量过滤，且分区键（partition key）可以显著加速这类过滤。Chroma 的过滤功能是附加的，性能不可比。

**理由三：pgvector 不够用的时候，Milvus 是出路。**

你可能会问：PostgreSQL + pgvector 不是也能做向量检索吗？对，**百万级以内 pgvector 完全够用**——pgvector 自 **0.5.0（2023-08-28）** 起就引入了 HNSW 索引（0.7.0 / 2024-04 加的是 `halfvec` / `sparsevec` 类型及对应索引，以及 HNSW / IVFFlat 对低精度向量的支持），配合 IVFFlat，百万级数据用 HNSW 仍可胜任。真正限制 pgvector 的是：它是单体扩展，没有分布式能力——PostgreSQL 是一个单体数据库，你不可能把一张表的向量拆分到多台机器上。当数据量达到千万/亿级、需要横向扩展与独立运维时，Milvus 是出路。

> **"百万级"是经验值，不是保证**：它默认 1024 维左右、过滤条件不太苛刻（过滤后仍有足够候选）、召回率要求常规、并发不高。维度更高（1536 / 3072）、过滤选择性很强导致索引失效、或者召回率要求高到必须全量扫描时，这个数字会明显缩水（可能只剩十万级）。**本章其它地方（2.7 部署表、2.8 小结）提到的向量规模口径与此一致：默认按百万级以内，实际阈值必须用自己的数据和查询压测校准。**

## 2.4 为什么需要 Redis

### 2.4.1 结论

**Redis 在高并发系统中承担三个角色：缓存加速、分布式锁、令牌桶限流。**

### 2.4.2 什么是 Redis？（概念）

Redis 是一个**基于内存的键值存储系统**。数据存在内存而非磁盘，所以读写极快（微秒级）。它支持字符串、列表、哈希、集合、有序集合等多种数据结构，还支持设置过期时间、发布订阅、Lua 脚本等高级能力。

### 2.4.3 Redis 在这个 Agent 系统中的四个具体用途（其实不止，还有session_id存储与区分等，可以具体问AI）

#### ① 对话缓存

用户和 Agent 的对话上下文每次请求都要读取，直接查 PostgreSQL 太慢：

```
请求 → Redis（命中，0.5ms）→ 返回  ✅
请求 → PostgreSQL（未命中，8ms）→ 写入 Redis → 返回  ⚠️
```

C 端场景下，同一用户可能在短时间内连续发送多条消息，缓存命中率极高。Redis 把 P99 延迟从几十毫秒压到个位数毫秒。

#### ② Token 限流（令牌桶）

高并发下必须限制每个用户调用 LLM 的频率，避免 API 费用爆炸：

```
Key: rate_limit:user:10086
Value: {"tokens": 50, "last_refill": "2026-05-09T10:00:00Z"}
TTL: 60s
```

Redis 的原子性操作（`INCR`、`EXPIRE`）只是计数器原语。令牌桶的完整逻辑——"读余量 → 按时间补充 → 扣减"——是多个命令的组合，必须用 **Lua 脚本（`EVAL`）** 包成原子操作，否则并发请求下会超发。每次请求到达时：

1. 读取当前令牌数与上次补充时间
2. 按时间间隔补充令牌（Lua 内完成）
3. 如果余量 > 0，扣减 1 放行；否则返回 429（Too Many Requests）

整个过程在 Redis 内存中原子完成，单次检查 < 1ms。注意：令牌桶的 `TTL` 不应等于窗口长度，而应足够长以保留 `last_refill` 时间戳（或干脆不设 TTL，依靠 Lua 逻辑按时间补充）。

#### ③ 分布式锁

Agent 的某些操作（比如：同一个 session 的对话不能并发处理；定时任务不能多实例重复执行）需要锁：

```python
# ❌ 只有加锁、没有释放，且 TTL 明显短于任务耗时
lock_key = "lock:session:abc123"
# SET lock_key random_value NX EX 10
# 拿到锁的执行，拿不到的等待或跳过
```

`NX` 表示"key 不存在才创建"，`EX 10` 表示 10 秒后自动释放，防止死锁。**但这段代码在本章的 Agent 场景里有三个坑**（前两个是这段实现的 bug，第三个是这类锁的固有局限）：

| 坑 | 现象 | 原因 | 解法 |
| --- | --- | --- | --- |
| TTL 短于任务耗时 | 任务跑到第 11 秒锁已自动释放，另一个 Worker 立刻拿到同一 session 的锁——**恰恰破坏了"同一 session 不并发"** | 本文 2.5.3 ① 明确写"一次 Agent 调用耗时 3~30 秒"，`EX 10` 覆盖不了 | TTL 取任务最大耗时的 1.5~2 倍（如 120s），超长任务用看门狗续期 + fencing token |
| 释放用 `DEL` | 删掉了**别人持有**的锁（自己已超时，锁被他人重取） | `DEL` 不校验持有者 | Lua 脚本：`GET` 出来的值等于自己的 token 才 `DEL` |
| 锁不是"加一次就安全" | 持有者进程 STW / 网络分区时，锁可能已过期而它自己不知道，仍往下写 | 锁的过期是单方面的 | 下游写入带 fencing token（单调递增版本号），旧 token 的写被拒绝 |

正确写法（加锁 + 原子释放）：

```python
import uuid

from core.cache import get_redis

# 释放必须是"比较持有者再删"，直接 DEL 会删掉别人的锁
_RELEASE_LUA = """
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
"""


async def acquire_session_lock(session_id: str, ttl: int = 120) -> str | None:
    """拿到锁返回持有者 token，拿不到返回 None。

    ttl 必须大于任务最大耗时：本章的 Agent 调用是 3~30 秒，
    所以 10 秒这种 TTL 一定会中途失效。
    """
    token = uuid.uuid4().hex
    ok = await get_redis().set(f"lock:session:{session_id}", token, nx=True, ex=ttl)
    return token if ok else None


async def release_session_lock(session_id: str, token: str) -> bool:
    """只有 token 匹配才删除，避免释放别人的锁。"""
    return bool(
        await get_redis().eval(_RELEASE_LUA, 1, f"lock:session:{session_id}", token)
    )
```

**长任务还要"续期"**：如果任务可能超过 TTL，起一个后台任务每 `TTL/3` 续期一次（同样要用 Lua 比较 token 再 `PEXPIRE`，续期只能由持有者做）。但看门狗不是万能的——持有者进程卡死（GC 停顿、网络分区）时它可能仍在续期，等于锁永远不释放，所以续期必须和 **fencing token** 配合：每次成功加锁生成一个单调递增的版本号写进锁值和下游存储，写数据时带上版本号，旧持有者的写请求因版本号落后被拒绝。

**一句话：锁的三件套是"TTL 覆盖任务耗时 + Lua 原子释放 + 续期/fencing token"，只写 `SET NX EX` 只是三件套里的第一件。**

#### ④ 短时间窗口统计（固定窗口）

C 端需要统计"过去 1 分钟内某接口被调用了多少次"用于熔断：

```
Key: window:agent_chat:1715251200（Unix 分钟时间戳）
INCR → 返回当前计数
TTL: 120s（自动清理）
```

注意：`INCR` + 按分钟时间戳分桶实现的是**固定窗口**（按分钟分桶），不是滑动窗口——固定窗口在边界处允许"双倍突发"（例如 10:00:59 与 10:01:00 各打满一次配额）。真正的滑动窗口需要把每次请求的时间戳写入 ZSET（`ZADD` + `ZCOUNT`），或用 Lua 脚本实现。`INCR` + `EXPIRE` 组合是计数器场景的事实标准解决方案，但语义上属于固定窗口。

### 2.4.4 不用 Redis 会怎样？

| 场景     | 无 Redis                   | 有 Redis               |
| -------- | -------------------------- | ---------------------- |
| 对话读取 | 每次查 PostgreSQL（8ms）   | 缓存命中时 0.5ms       |
| 限流     | 查 DB 做计数（慢且不准）   | 内存原子操作（准且快） |
| 分布式锁 | 用数据库表模拟（死锁风险） | SET NX EX，配 Lua 保证"只释放自己的锁" |
| 窗口统计 | 查 DB COUNT（大表扫描）    | 内存计数器实时更新     |

## 2.5 为什么需要 RabbitMQ（消息队列）

### 2.5.1 结论

**消息队列解决三个问题：削峰、解耦、异步。Agent 的 LLM 调用是慢操作，必须用队列做生产-消费模式。**

### 2.5.2 什么是消息队列？（给大学生）

消息队列是一种**生产者-消费者**模式的中间件。生产者把任务消息扔到队列里就完事了，不用等任务真正执行完。消费者从队列里取任务来处理，处理完再通知结果。

```
[生产者 FastAPI] ──发送消息──▶ [RabbitMQ 队列] ──消费──▶ [Worker 进程]
   ↓ 立刻返回 "处理中"                                       ↓ 慢慢调 LLM
```

### 2.5.3 RabbitMQ 在这个 Agent 系统中的四个具体用途

#### ① 异步 Agent 执行（削峰）

一次 Agent 调用可能包括多轮 LLM 推理 + 多次工具调用，耗时 3~30 秒不等。HTTP 请求不可能同步等这么久。长耗时 Agent 任务有两种模式：

- **在线 SSE 流式返回**：FastAPI 用 `StreamingResponse` 把 Agent 执行过程逐段推送给前端（与第 1 章"SSE 流式"一致），用户实时看到"正在思考 / 正在调用工具"
- **MQ 异步 + 完成后通知**：FastAPI 把任务写入 RabbitMQ 立即返回，Worker 执行完再通过 WebSocket / 轮询通知结果

离线/批处理/削峰（并发瞬间从 100 飙到 10000）这类场景才需要选队列：

```
用户发送消息
   │
   ▼
FastAPI 接收请求 → 写入 RabbitMQ → 立即返回 "ok"（200ms 内）
                                             │
                                      ┌──────▼───────┐
                                      │  Worker 进程   │
                                      │  Agent 执行中  │  ← 耗时 3~30s
                                      │  结束后通知前端 │
                                      └──────────────┘
```

当并发请求瞬间从 100 飙到 10000，消息队列在中间当缓冲——所有请求先进队列排队，Worker 按自己的节奏消费，后端不会被打崩。

#### ② 服务解耦

Agent 执行结束后可能有多个后续动作：保存对话记录、更新用户统计数据、触发通知推送。用消息队列做事件驱动，Agent Worker 只负责"发事件"，具体谁消费它不管：

```
Agent 执行完成
   │
   ▼
发布 "agent.run.completed" 事件到 Exchange
   │
   ├──▶ 队列 A → 消费者：记录对话日志到 PostgreSQL
   ├──▶ 队列 B → 消费者：更新用户配额
   └──▶ 队列 C → 消费者：异步通知（WebSocket 推送给前端）
```

每个消费者都是独立进程，挂了不影响其他逻辑。新增消费者也不需要改 Agent Worker 的代码。

#### ③ 失败重试与死信

LLM 调用可能因网络抖动、API 限流等原因失败。但**"消息队列天然支持重试"是个需要拆开讲的印象**——队列给你的是"消息能回到队列、能路由到死信队列"的机制，重试策略本身要自己配：

- **`basic_nack(requeue=True)` 不是重试**：消息会**立即**回到队头重新投递，没有退避、没有次数上限，等于一个热循环——poison message 会瞬间打满 CPU 和日志（同一条毒消息被无限重投）。
- **"重试 N 次进死信"不是原生的**：要么自己声明 `x-dead-letter-exchange` / `x-dead-letter-routing-key` 并给队列挂上策略，要么在 RabbitMQ 4.0+ 用 quorum 队列原生的 `x-delivery-limit`（投递次数上限，默认 20，超过后按 `dead-letter-strategy` 丢弃或进死信——注意 4.0 起这个默认值本身是行为变更，老集群升级后要复核）。
- **延迟重试（第 1s / 5s / 30s 后再试）同样要自己做**：RabbitMQ 没有内置延迟队列，要么用"TTL 队列 + DLX"曲线实现，要么装 `rabbitmq_delayed_message_exchange` 插件。
- **幂等要自己在业务层做**：at-least-once 语义下同一条消息可能被处理多次（消费者 ack 前崩溃），重试次数越多越要防重复扣费、重复写库。

**结论：重试次数、退避间隔、死信去向、幂等、死信后的告警处理，全部要自己配置或写代码。** 队列省掉的是"怎么把消息可靠地搬运"这段，不是"失败之后怎么办"这段。

#### ④ 优先级调度（生产环境要换实现方式）

C 端场景下，付费用户的 Agent 请求应该优先于免费用户。直觉写法是用 classic 队列的 `x-max-priority`：

```
RabbitMQ 优先级队列（classic 队列特性）：
  VIP 用户消息   → priority=10 → 优先消费
  普通用户消息   → priority=0  → 正常排队
```

**但生产环境（见 2.7 的 quorum 队列方案）用不了这个写法**：`x-max-priority` 是 **classic 队列**的特性，quorum 队列不支持（RabbitMQ 3.13.4 起还会直接拒绝在 quorum 队列上声明该参数），而 4.x 已移除镜像队列，生产上高可用基本只能靠 quorum 队列——两处不能并存。可选方案：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| classic + `x-max-priority` | 优先级严格按数值生效 | 没有镜像队列，节点故障即队列不可用，和"生产要高可用"直接冲突 |
| quorum + AMQP 1.0 优先级 | RabbitMQ 4.0+ 支持，但只有两级：0–4 视为 normal、>4 视为 high，且官方是按 **2:1 的比例**（2 条 high 配 1 条 normal）投递而非严格优先 | `priority=10` 这种"多级 VIP"语义不成立，只能表达"高/普通"两档 |
| **多队列分级（推荐）** | 建 `agent.vip` / `agent.normal` 两条 quorum 队列，Worker 侧用 `basic_qos(prefetch=N)` 控制预取量，并按设定比例（例如 5:1）轮询这两条队列；VIP 队列单独配更大的消费者并发 | 要多写一段"按比例消费"的调度逻辑，但优先级语义可控、积压情况可观测 |

**落到本章的部署建议：生产用 quorum 队列承载 `agent.vip` / `agent.normal` 两条队列，用"多队列分级 + 按比例消费"实现 VIP 通道**；如果业务确实需要严格的多级优先级，就把分级做到上层（按用户等级选不同队列、不同 Worker 池），而不是指望 `x-max-priority`。

### 2.5.4 RabbitMQ vs Kafka vs Redis Pub/Sub vs Redis Streams

| 维度            | RabbitMQ      | Kafka              | Redis Pub/Sub                | Redis Streams                  |
| --------------- | ------------- | ------------------ | ---------------------------- | ------------------------------ |
| 消息确认（ACK） | ✅ 原生支持   | ✅ 支持            | ❌ 不支持（fire-and-forget） | ✅ `XREADGROUP` + `XACK`，PEL 记录未确认消息 |
| 死信队列        | ✅ 原生支持   | ⚠️ 需手动实现    | ❌ 不支持                    | ❌ 需自建（PEL + 重投逻辑）    |
| 优先级队列      | ✅ 原生支持（classic）/ 两级（quorum） | ❌ 不支持          | ❌ 不支持                    | ❌ 不支持                      |
| 消息持久化      | ✅            | ✅                 | ❌                           | ✅（随 AOF / RDB）             |
| 吞吐量          | 万级/秒       | 百万级/秒          | 十万级/秒                    | 十万级/秒（单键，受单线程模型限制） |
| 适用场景        | 任务分发、RPC | 日志流、大数据管道 | 即时通知（丢了也无所谓）     | 轻量任务队列、消费组回放       |

**先别用 Redis Pub/Sub 当靶子**：Redis 侧的对应物其实是 **Streams**。`XADD` 写入的消息可以随 AOF / RDB 持久化，消费者组（`XREADGROUP`）+ `XACK` 提供 ACK，PEL（Pending Entries List）记录"已投递未确认"的消息，`XAUTOCLAIM` 能把超时未确认的消息转给其它消费者——语义就是一个 at-least-once 的任务队列。所以选 RabbitMQ 的理由**不是"Redis 会丢消息"，而是这四点**：

- Streams 是单键结构，吞吐受 Redis 单线程模型约束（十万级/秒），量级低于 RabbitMQ 的多队列并行
- 没有优先级
- 没有原生死信，重试次数 / 退避 / 死信都要自己写（和 2.5.3 ③ 里 RabbitMQ 的短板是同一类问题，但 RabbitMQ 至少有 `x-delivery-limit` 和 DLX 可配）
- 没有 Exchange 那种"一条消息按路由键扇出到多个队列"的成熟模型，多消费者场景要自己维护多个消费者组

**Agent 的消息模型是"任务分发"而非"数据流"**——每条消息代表一个需要执行的任务，每条都要保证被处理、允许失败重试、支持优先级。这套"任务分发 + 优先级 + 死信"的组合里，RabbitMQ 的配置成本最低；而 Pub/Sub 只适合"即时通知，丢了也无所谓"的场景。

Kafka 适合"日志采集、事件溯源"这类海量数据流场景，但在"一对一任务分发 + 失败重试 + 优先级"的场景下，RabbitMQ 更合适。

以一个典型的用户对话为例，展示四个中间件如何协作：

```
用户： "帮我查一下最新的退货政策"
   │
   ▼
┌──────────────────────────────────────────────────┐

                   │
                   ▼
┌──────────────────────────────────────────────────┐
│ ② Worker 从 RabbitMQ 取出任务                     │
│    Redis 加锁（lock:session:xxx）                 │

└──────────────────┬───────────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────────┐
│ ③ Agent 执行（LangGraph）                         │
│    LLM 判断：需要检索知识库 → 调用 search_docs    │
│    search_docs 工具：将问题转为向量               │

                   │
                   ▼

                   ▼

│ ⑤ 结果回写                                       │
│    PostgreSQL 保存完整对话记录                     │

```

## 2.8 本章小结

四个中间件各有不可替代的职责：

- **PostgreSQL**：存业务数据 + JSON 查询 + 全文搜索 + 向量检索（百万级以内，维度/过滤选择性/并发不同会明显浮动），替代 MySQL 的理由是 JSONB / tsvector / pgvector 三个能力刚好是 Agent 刚需。
- **Milvus**：海量向量检索（百万级及以上、需要分布式与独立扩容时），替代 Chroma/FAISS 的理由是分布式、混合检索、生产级稳定性。
- **Redis**：缓存加速 + 限流 + 分布式锁（TTL 覆盖任务耗时 + Lua 原子释放 + 续期/fencing token）+ 窗口统计，高并发下保护数据库和 LLM API 不被击穿。
- **RabbitMQ**：异步任务 + 削峰 + 服务解耦 + 可配置的失败重试与死信（重试次数、退避、死信去向都要自己配，不是开箱即得），解决"LLM 调用太慢不能同步返回"这个 Agent 后端最核心的架构问题。
