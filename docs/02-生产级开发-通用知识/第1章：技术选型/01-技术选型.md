# 第一章：技术选型

## 1.1 技术栈概览

| 组件       | 选型            | 版本            |
| ---------- | --------------- | --------------- |
| 编程语言   | Python          | 3.14（3.13 亦可）|
| Web 框架   | FastAPI         | ≥0.136        |
| Agent 编排 | LangGraph       | ≥1.2          |
| LLM 工具层 | LangChain       | ≥1.3（稳定版）|
| 数据验证   | Pydantic        | ≥2.13         |
| 异步运行时 | uvicorn + asyncio（Linux 上可用 uvloop） | - |
| 异步兼容层 | anyio（Starlette/FastAPI 的跨实现抽象层，本身不是运行时） | - |

## 1.2 这个搭配在工业界正确吗？

**结论：正确，且是当前（2025-2026）的主流推荐组合。**

几个事实支撑：

1. **LangChain 1.0 的发布标志着 API 成熟稳定**。2025 年 LangChain 正式发布 1.0 稳定版，核心接口（ChatModel、Tool、PromptTemplate、Message 体系）进入长期稳定承诺，不再有 0.x 时代频繁的 breaking change。官方明确 LangGraph 是多 Agent、有状态编排的首选方案，LangChain 定位为"模型调用 + 工具定义"的基础层。
2. **FastAPI 是 Python 异步 Web 框架的事实标准**。LangGraph 的 Agent 执行是异步的（`ainvoke`、`astream`），FastAPI 的路由也是 `async def`，两者跑在同一个 asyncio 事件循环上，异步模型**可以**对齐——但前提是**全链路异步**：异步数据库驱动（`asyncpg` / SQLAlchemy async）、async checkpointer、`httpx.AsyncClient` 而非 `requests`、不出现 `time.sleep`。链路里只要有任意一个同步环节，它就会阻塞整个事件循环（同一进程上的所有请求一起卡住），这正是第 2 章 1.4.5 节花篇幅讲的问题。**"天然匹配"不等于"自动不阻塞"，对齐异步模型是设计约束，不是免费获得的属性。**
3. **Pydantic v2 是共同依赖**。LangChain 1.0、LangGraph、FastAPI 三方都基于 Pydantic v2 做数据序列化和校验，类型体系统一，无适配成本。
4. **工业界案例**：部分大厂与 AI 初创公司在工程博客中公开了类似组合（例如以 FastAPI + LangGraph 构建 Agent 后端）；LangChain 官方自身发布的模板项目（如 `langgraph/examples`）也采用 FastAPI 做 API 服务。

如果非要挑一个需要留意的点：**LangChain 包体积较大、抽象层较厚**。在简单场景下可以只用 LangGraph + 直接调模型 SDK（如 `openai` 包），但既然你要用 LangChain 的 tool 定义、prompt template、output parser 等能力，那就没有多余成本。

## 1.3 为什么选 Python 3.14

- **asyncio 性能提升**：自 3.11 起，asyncio 的任务调度和异常处理得到显著优化，高并发 Agent 场景收益直接，3.13 / 3.14 延续并巩固了这些改进。
- **异常组（ExceptionGroup）**：3.11 引入的 `ExceptionGroup` 让并发 Agent 任务的异常聚合更干净，**但要注意它和 `gather(..., return_exceptions=True)` 是两回事**——后者不抛异常组，只是把异常当成返回值收集；真正抛 `ExceptionGroup` 的是 `asyncio.TaskGroup`。两种写法对照如下：
- **tomllib 标准库**：配置文件可以用标准库读取，不需要额外依赖 `toml` 包（tomllib 是 **3.11** 引入的，3.12 及以后只是"已有"，不构成选 3.13/3.14 的独有理由）。
- **3.14 的能力增量**：注解默认延迟求值（PEP 649 / 749，对重度依赖类型注解的 Pydantic v2 + FastAPI 栈更可预测）、`compression.zstd` 进入标准库、t-string 模板。属于锦上添花，不是选型的决定因素。
- **生态兼容性**：截至 2026 年 9 月，Python 3.14.x 已是当前稳定版（3.14.0 于 2025-10-07 发布），生态也已跟上（LangChain 1.x / LangGraph / FastAPI 均兼容，本手册各章依赖的下限都是 `>=3.10`，不存在兼容障碍）。**新项目建议直接用 3.14；3.13 可用，但它的 bugfix 窗口在 2026-10 结束，之后只剩安全修复。** 3.12 可用，3.11 不再是首选。

```python
import asyncio


async def retrieve(q: str) -> dict:
    ...  # 项目骨架里的检索函数


# ❌ 写法一：gather(return_exceptions=True) —— 不抛异常组，配的是手工遍历
tasks = [asyncio.create_task(retrieve(q)) for q in ("退货政策", "物流时效")]
results = await asyncio.gather(*tasks, return_exceptions=True)
# 实测（Python 3.13）：results == [ValueError('...'), {'docs': [...]}]
# 异常只是列表里的"返回值"，没有 except* 可用
for r in results:
    if isinstance(r, Exception):
        logger.error("一路检索失败，降级为空上下文: %s", r)

# ✅ 写法二：TaskGroup —— 真正抛 ExceptionGroup，可被 except* 分组捕获
try:
    async with asyncio.TaskGroup() as tg:
        for q in ("退货政策", "物流时效"):
            tg.create_task(retrieve(q))
except* ValueError as eg:  # 只处理 ValueError 那一组
    logger.warning("参数类错误，降级返回空上下文: %s", eg.exceptions)
except* TimeoutError:
    logger.warning("超时，降级返回空上下文")
```

**选哪个：** 需要"谁失败就单独处理谁、其余继续"用 `gather(return_exceptions=True)` + 手工遍历；需要"一个失败就整组取消并统一兜底"用 `asyncio.TaskGroup` + `except*`。**两者不可混为一谈——写 `except*` 去接 `gather(return_exceptions=True)`，异常永远不会被捕获，因为根本没有异常被抛出。**

## 1.4 为什么选 LangChain 1.0 稳定版

LangChain 从 0.x 跨越到 1.0 带来的关键变化：

### 1.0 之前（0.x 时代）的问题

- API 不稳定，版本间频繁 breaking change
- 过度抽象（LCEL、Runnable 体系对新手心智负担重）
- 包体积膨胀，`langchain` 包耦合了大量社区插件

### 1.0 的改进

- **接口稳定承诺**：核心模块（`langchain-core`）进入语义化版本管理，不再随意破坏 API。`ChatModel.invoke()`、`BaseTool`、`BaseMessage` 等关键接口已冻结。
- **包拆分明确**：`langchain-core`（核心抽象）、`langchain`（高级封装）、`langchain-openai`（OpenAI 集成）、`langchain-community`（社区贡献）各司其职，安装时按需引入。
- **与 LangGraph 的协作模式成熟**：1.0 后官方确立了"LangChain 提供工具和模型调用，LangGraph 负责状态编排"的分工。两边的接口配合已经过大量生产验证。
- **向后兼容保证**：1.x 主版本内不会引入 breaking change，这对工业项目至关重要。

### 何时可以不用 LangChain

如果你只用一个模型供应商（比如只用 OpenAI），且不需要复杂的 prompt 模板、output parser、社区工具生态，那可以只用 `openai` + `langgraph`，无需引入 LangChain。但多模型切换、工具定义（`@tool` 装饰器）、标准化消息格式这些需求一旦出现，LangChain 就是最省力的选择。

## 1.5 为什么选 FastAPI

### 对比 Flask

| 维度              | FastAPI                          | Flask                   |
| ----------------- | -------------------------------- | ----------------------- |
| 异步原生支持      | ✅ async/await 一等公民          | ❌ 需要扩展（quart 等） |
| 自动 OpenAPI 文档 | ✅ 内置 swagger / redoc          | ❌ 需要插件             |
| 请求/响应校验     | ✅ Pydantic v2 原生集成          | ❌ 需要 marshmallow 等  |
| 流式响应（SSE）   | ✅`StreamingResponse` 直接支持 | ⚠️ 需要额外处理       |
| 性能              | 异步 + uvloop，接近 Node.js      | 同步模式，多线程        |

Agent 后端的核心场景——**流式输出（SSE/WebSocket）、长时间运行的 Agent 任务、高并发工具调用**——FastAPI 全部原生支持，Flask 则需要大量额外工作。

### 对比 Django / Django-Ninja

Django 适合全栈 Web 应用，做纯 API + Agent 场景太重了。ORM、模板引擎、中间件体系在纯 Agent 后端中有 80% 用不到。Django-Ninja 缩小了差距，但社区体量仍远小于 FastAPI。

### 对比纯 gRPC

gRPC 对 Agent 后端不是好选择。Agent 的输入输出以自然语言为主，可调试性比传输效率更重要。REST + SSE 的 HTTP 方案在开发效率和可观测性上明显胜出。如果未来内部服务间有强类型通信需求，可以在 FastAPI 之上额外暴露 gRPC 端口。

## 1.6 LangChain vs LangGraph 的职责划分

这是最容易混淆的地方。一句话总结：

> **LangChain 管"调用模型"，LangGraph 管"编排流程"。**

```
┌─────────────────────────────────────┐
│           LangGraph                  │
│  ┌──────┐   ┌──────┐   ┌──────┐    │
│  │ Node │──▶│ Node │──▶│ Node │    │
│  │  A   │   │  B   │   │  C   │    │
│  └──────┘   └──────┘   └──────┘    │
│     │           │           │       │
│     ▼           ▼           ▼       │
│  ┌──────────────────────────────┐   │
│  │        LangChain 1.0          │   │
│  │  • ChatModel（模型调用）      │   │
│  │  • Tool（工具定义）           │   │
│  │  • PromptTemplate（提示词）   │   │
│  └──────────────────────────────┘   │
└─────────────────────────────────────┘
```

**LangChain 做的事：**

- 统一的模型调用接口（`ChatOpenAI`、`ChatAnthropic` 等）
- 工具定义和 Schema 生成（`@tool` 装饰器，Pydantic 参数）
- Prompt 模板管理
- 消息格式标准化（SystemMessage、HumanMessage、AIMessage、ToolMessage）
- 输出解析器（JSON、结构化提取等）

**LangGraph 做的事：**

- 有状态图（StateGraph）—— Agent 执行的状态管理
- 条件边（conditional edges）—— 根据 LLM 输出决定下一步
- 循环和分支 —— 工具调用循环、多步推理
- 检查点（checkpointer）—— 持久化执行状态，支持断点续跑和回溯
- 人工介入（human-in-the-loop）—— 在关键节点暂停等待人工审批
- 流式输出 —— 两条路径：`astream(..., stream_mode="messages")` 直接拿逐 token 的 message chunk，是官方文档里做"逐 token 推送"的主力 API（`stream_mode` 还可选 `"updates"`：每个节点跑完即推一次，用来推"步骤进度"；`"custom"`：节点内用 `get_stream_writer()` 推自定义事件）；`astream_events` 则按事件类型（`on_chat_model_stream`、`on_tool_start`…）过滤，适合"步骤进度 + 逐 token"混合推送

### 一个必须知道的 API 更替：用 `create_agent`，别再用 `create_react_agent`

上面的职责分工在 1.x 时代仍然成立，但**"开箱即用的 ReAct Agent"由谁提供变了**：

- LangGraph v1 起，`langgraph.prebuilt.create_react_agent` **已弃用**（照旧文档写会拿到 Deprecation 警告，未来版本会移除）
- 官方替代是 LangChain 1.x 的 `langchain.agents.create_agent`：参数由 `prompt=` 改为 `system_prompt=`，并附带 middleware 体系（摘要、人工审批、错误重试等横切能力都挂在 middleware 上）

```python
from langchain.agents import create_agent

# 1.x 的默认姿势：一个函数拿到"开箱 ReAct Agent"
agent = create_agent(
    model="openai:gpt-5-mini",     # 也可直接传 ChatOpenAI 实例
    tools=ALL_TOOLS,                # 项目内统一的工具清单
    system_prompt="你是电商客服 Agent，回答前先检索知识库。",  # 旧 API 里这个参数叫 prompt=
)
```

**选型判据：默认 `create_agent`（工具调用循环 + 消息状态 + middleware 已经够用）；需要自定义状态字段、条件边、人工介入节点这类"状态机"能力时，再落到 `StateGraph` 手写图。** 两者不冲突——`create_agent` 返回的本身就是一张编译好的图，可以作为一个节点嵌进更大的 `StateGraph`。

## 1.8 本章小结

FastAPI + LangGraph + LangChain 1.x + Python 3.14（3.13 亦可）是 2025-2026 年工业界开发 Agent 后端的最主流、经过充分验证的技术组合。LangChain 1.x 解决了 0.x 时代 API 不稳定的核心痛点，进入了长期维护的稳定轨道，并且 `langchain.agents.create_agent` 已经成为"开箱 ReAct Agent"的官方入口（`create_react_agent` 已弃用）。三者都基于 Pydantic v2 和 asyncio，类型体系统一，异步模型一致——但这份"一致"要靠全链路异步来兑现，同步环节一旦混入就会阻塞事件循环。
