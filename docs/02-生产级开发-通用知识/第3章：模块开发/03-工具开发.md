# 第三章：工具集

> **核心论点**：工具是 Agent 的手和脚。没有工具，模型只能"说说而已"；有了工具，模型能查数据库、调 API、发邮件、操作文件。但工具调用也是最容易失控的环节——模型可能反复重试一个注定失败的工具、可能误解用户意图乱调工具、可能陷入无限循环。本章逐一拆解工具的注册、调用、意图识别和失控防范。

---

## 3.1 LangChain 的工具定义：三种方式与选择

### 3.1.1 方式一：`@tool` 装饰器（推荐，最常用）

```python
from langchain_core.tools import tool
from pydantic import BaseModel, Field


# 最简单的用法：装饰一个 async 函数，参数说明写在 Args: 段里
@tool(parse_docstring=True)
async def get_weather(city: str, date: str = "today") -> str:
    """查询指定城市指定日期的天气。

    Args:
        city: 城市名称，支持中文或英文（如“北京”、“Shanghai”）。
        date: 日期，格式 YYYY-MM-DD，默认今天。
    """
    # 实际调天气 API...
    return f"{city} {date}：晴，22°C，湿度 45%"


# 需要更复杂的约束（正则、范围、条件必填）时，改用 Pydantic args_schema
class WeatherInput(BaseModel):
    city: str = Field(description="城市名称，支持中文或英文")
    date: str = Field(default="today", description="日期，格式 YYYY-MM-DD，默认今天")


@tool(args_schema=WeatherInput)
async def get_weather_v2(city: str, date: str) -> str:
    """查询指定城市指定日期的天气。"""
    return f"{city} {date}：晴，22°C"
```

`@tool` 装饰器做了什么：
1. 读取函数名作为工具名（`get_weather`）
2. 确定工具描述（发给 LLM 看的那段话）
3. 读取参数定义，生成参数 JSON Schema
4. 包装为 `BaseTool` 子类实例

**描述与参数的归属，是新手最容易写错的一处。** 工具描述（`description`）和参数说明（每个参数的 `description`）是两件事，写错位置会直接影响模型的选择准确率：

| 位置 | 进到哪里 | 该写什么 |
|------|---------|---------|
| `description=` 参数 | 工具描述 | 只在需要覆盖 docstring 时用 |
| 整段 docstring | 工具描述 | "这个工具是干什么的、什么时候该用、什么时候别用" |
| docstring 的 `Args:` 段（配合 `parse_docstring=True`） | **每个参数的 JSON Schema** | 参数格式、单位、取值范围、默认值 |
| `args_schema` 各字段的 `description` | 每个参数的 JSON Schema | 同上（用 Pydantic 时的等价写法） |

优先级是 `description=` 参数 > 整段 docstring > `args_schema` 的 docstring：一旦显式传了 `description=`，docstring 就不再作为工具描述。

早期写法（把参数说明塞进 docstring 首行）是这样的：

```python
# ❌ 参数说明混进工具描述：模型看到的是"一段话"，而不是"结构化参数"
@tool
async def get_weather(city: str, date: str = "today") -> str:
    """查询城市的实时天气。city: 城市名称；date: 日期，格式 YYYY-MM-DD。"""
    ...
```

问题在于：参数说明占用了本该描述"何时调用"的工具描述位置，模型在选择工具时要先读完一段"选择 + 参数"混合文本；而 `Args:` 段会让参数说明直接落到参数自己的 schema 里（`parameters.properties.date.description`），模型在填参数时看到的是紧贴参数的提示。**一句话：工具描述回答"要不要用"，参数说明回答"怎么填"，别混在同一个位置。**

**`args_schema` 与函数签名的取舍：** 一旦传了 `args_schema`，参数 schema 就以它为准，`@tool` 不再从函数签名推导也不再校验签名与 schema 是否一致——两处默认值写得不一致不会报错，只会在运行期悄悄按 `args_schema` 走（上例中 `get_weather_v2` 的签名故意不带默认值，就是为了不出现两份默认值）。所以二选一：

- 参数简单、校验规则少 → 只写函数签名 + `Args:` 段（第一种写法）
- 参数需要正则/范围/条件校验，或要复用到别处 → 用 `args_schema`，并把参数默认值只写在 `Field(default=...)` 里，函数签名保持"必填形态"

### 3.1.2 方式二：继承 `BaseTool`（需要更多控制时用）

```python
from langchain_core.tools import BaseTool
from pydantic import BaseModel, Field
from typing import Type


class OrderSearchInput(BaseModel):
    order_id: str = Field(description="订单号，格式 ORD-XXXXX")


class OrderSearchTool(BaseTool):
    name: str = "search_order"
    description: str = "根据订单号查询订单详情，返回订单状态、金额和物流信息。"
    args_schema: Type[BaseModel] = OrderSearchInput

    async def _arun(self, order_id: str) -> str:
        """异步执行（Agent 调用入口）"""
        return await self._search(order_id)

    def _run(self, order_id: str) -> str:
        """同步执行（异步工具本就走 _arun，不提供同步实现）"""
        raise NotImplementedError("请使用异步调用 _arun")

    async def _search(self, order_id: str) -> str:
        # 实际查询逻辑
        ...
```

**什么时候用继承而不是装饰器：**
- 需要工具内部维护状态（如连接池、计数器）
- 需要 `name` 和函数名不同
- 需要在 `_arun` 前后做统一的预处理/后处理
- 需要动态决定是否返回异常或结果

### 3.1.3 方式三：`StructuredTool`（从普通函数快速构造）

```python
from langchain_core.tools import StructuredTool


async def search_docs(query: str, source: str = "all") -> str:
    """在内部文档库中搜索。

    Args:
        query: 搜索关键词。
        source: 来源，可选 all/wiki/faq，默认 all。
    """
    ...


# 如果已有普通函数，用 StructuredTool 包装；parse_docstring=True 才会解析 Args: 段
doc_tool = StructuredTool.from_function(
    coroutine=search_docs,
    name="search_documents",
    description="在内部文档库中搜索产品手册、FAQ 与运维手册。",
    parse_docstring=True,
)
```

**三种方式的选择：**

| 方式 | 适用场景 | 代码量 |
|------|---------|--------|
| `@tool` 装饰器 | 绝大多数工具 | 最少 |
| 继承 `BaseTool` | 需要内部状态、复杂初始化 | 最多 |
| `StructuredTool` | 已有函数不想改签名、动态创建工具 | 中等 |

## 3.2 工具如何绑定到模型——`bind_tools` 的机制

### 3.2.1 核心流程

```
定义工具 → bind_tools 绑定到 ChatModel → Agent 调用时 LLM 决定是否调工具
                                              │
                                    返回 tool_calls ↓
                                              │
                                    执行工具 → 结果返给 LLM → 继续推理
```

```python
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool

# 1. 定义工具
@tool(parse_docstring=True)
async def calculator(expression: str) -> str:
    """执行数学计算。用户要求精确算数、算金额、算比例时使用。

    Args:
        expression: 数学表达式，如 '2+3*4'。
    """
    ...

@tool(parse_docstring=True)
async def search_web(query: str) -> str:
    """搜索互联网。仅在需要外部实时信息（新闻、价格、天气）时使用。

    Args:
        query: 搜索关键词。
    """
    ...

tools = [calculator, search_web]

# 2. 绑定到模型
llm = ChatOpenAI(model="gpt-5.1")
llm_with_tools = llm.bind_tools(tools)

# 3. 调用 —— LLM 会自动判断是否需要工具
response = await llm_with_tools.ainvoke([
    {"role": "user", "content": "计算 123 * 456 等于多少"}
])
# → response.tool_calls = [{"name": "calculator", "args": {"expression": "123*456"}}]
```

### 3.2.2 `bind_tools` 实际做了什么

`bind_tools` 并不是把工具代码"塞给"模型。它做的是：

1. 把每个工具的 `name`、`description`、`args_schema`（参数 JSON Schema）转为 OpenAI function calling 格式
2. 在每次 API 请求时把这些工具定义作为 `tools` 参数发送
3. LLM 根据用户消息和工具描述，决定是否返回 `tool_calls`

```
发送给 OpenAI 的请求体（简化）：
{
  "model": "gpt-5.1",
  "messages": [{"role": "user", "content": "计算 123 * 456"}],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "calculator",
        "description": "执行数学计算。用户要求精确算数、算金额、算比例时使用。",
        "parameters": {
          "type": "object",
          "properties": {
            "expression": {"type": "string", "description": "数学表达式，如 '2+3*4'"}
          },
          "required": ["expression"]
        }
      }
    },
    // ... 其他工具
  ]
}
```

**关键认知：工具定义是跟着每一次 LLM 请求发送的。** 10 个工具，每次请求都在消耗工具定义开销（经验量级在千 token 上下，随描述长度线性变化）。这就是为什么工具描述要简洁、工具数量要控制。

### 3.2.3 `tool_choice` —— 控制模型是否必须调工具

```python
# ---------- OpenAI（ChatOpenAI）：字符串 + OpenAI 形状的 dict ----------
llm.bind_tools(tools, tool_choice="auto")        # 默认：LLM 自己判断要不要调工具
llm.bind_tools(tools, tool_choice="required")    # 强制必须调工具（至少一个）
llm.bind_tools(tools, tool_choice="none")        # 禁止调工具（纯文本回复）
llm.bind_tools(tools, tool_choice={"type": "function", "function": {"name": "calculator"}})

# ---------- Anthropic（ChatAnthropic）：字符串只有 auto / any，指定工具用另一种形状 ----------
llm.bind_tools(tools, tool_choice="auto")                                  # → {"type": "auto"}
llm.bind_tools(tools, tool_choice="any")                                   # → {"type": "any"}：至少调一个
llm.bind_tools(tools, tool_choice={"type": "tool", "name": "calculator"})  # 强制调指定工具
```

**这套写法不跨厂商通用。** 本章既推荐 GPT-5.1 也推荐 Claude，所以必须把适用边界讲清楚：

| 意图 | OpenAI 写法 | Anthropic 写法 |
|------|------------|----------------|
| 让模型自己判断 | `"auto"` | `"auto"` 或 `{"type": "auto"}` |
| 必须调工具（至少一个） | `"required"` | `"any"`（部分旧版本不认 `"required"`） |
| 禁止调工具 | `"none"` | 无此选项：不绑工具，或直接用没绑工具的模型 |
| 强制调某个工具 | `{"type": "function", "function": {"name": "x"}}` | `{"type": "tool", "name": "x"}` |

`ChatAnthropic` 只把字符串 `"auto"` / `"any"` 翻译成 `{"type": "auto"}` / `{"type": "any"}`；**其他任意字符串都会被当成"工具名"**，`tool_choice="required"` 会变成 `{"type": "tool", "name": "required"}`、`tool_choice="none"` 会变成 `{"type": "tool", "name": "none"}`，Anthropic 侧报"没有这个工具"。同理，OpenAI 形状的 dict（`{"type": "function", ...}`）会被原样透传，Anthropic 只认 `{"type": "auto" | "any" | "tool", ...}`，一样报错。

另外两点容易踩的边界：

- **工具 schema 的字段名不同**：OpenAI 是 `parameters`，Anthropic 原生 API 是 `input_schema`。用 `bind_tools` 时框架会自动从 `args_schema` 转换，不用手写；但如果你直接拼请求体调原生 API，字段名写错就会被拒。
- **开启 extended thinking 时，强制 `tool_choice` 会被丢弃**：Anthropic 不支持"思考 + 强制指定工具"同时生效，框架会打 warning 后忽略你的 `tool_choice`（退化为 `auto`）。所以"必须走某个工具"的关键节点，别把希望寄托在 thinking 模型的 `tool_choice` 上。

**使用建议：**
- C 端对话 Agent：用 `"auto"`，让 LLM 自然判断
- 特定任务节点（如"查询订单"节点）：用"必须调工具"（OpenAI `"required"` / Anthropic `"any"`），或直接指定工具名
- 纯文本回复阶段（Agent 已拿到工具结果，需要整合输出）：OpenAI 用 `"none"`；Anthropic 换成"不绑工具的那个模型实例"
- 路由/分发节点：**不要**靠 `tool_choice` 硬编码"该调哪个工具"，也**不要**把全量工具都绑上去。正确顺序是先做意图识别（见 3.5 节），再按场景只绑该场景的工具子集（见 3.6.3 节）；子集内的"选哪个工具"交给 `"auto"`

## 3.3 工具调用的准确性问题

### 3.3.1 第一类问题：参数填错

LLM 可能传了不符合工具预期的参数：

```python
from datetime import datetime, timedelta

from langchain_core.tools import tool, ToolException

# 防线 0（最早、成本最低）：让模型侧就按 JSON Schema 生成参数
# OpenAI 的 strict function calling：langchain_openai 的 bind_tools 支持 strict=True
llm_with_tools = llm.bind_tools(tools, strict=True)

# LLM 产生了这样的 tool_call：
{"name": "get_weather", "args": {"city": "北京", "date": "明天"}}
#                                                         └─ 工具要求 "YYYY-MM-DD"

# 防线 1（工具内）：不可解析的输入抛 ToolException，由框架转成"失败消息"
@tool(parse_docstring=True)
async def get_weather(city: str, date: str = "today") -> str:
    """查询指定城市指定日期的天气。

    Args:
        city: 城市名称。
        date: 日期，格式 YYYY-MM-DD，默认今天。
    """
    if date in ("today", "今天"):
        date = datetime.now().strftime("%Y-%m-%d")
    elif date in ("tomorrow", "明天"):
        date = (datetime.now() + timedelta(days=1)).strftime("%Y-%m-%d")

    try:
        datetime.strptime(date, "%Y-%m-%d")
    except ValueError as e:
        # 关键：抛异常，而不是 return 一段中文文本（原因见 3.3.2）
        raise ToolException(f"日期格式错误：'{date}'，请按 YYYY-MM-DD 重新调用本工具") from e
    ...
```

**为什么先试 `strict=True`：** 它是"参数填错"里生效最早的一道防线——约束加在模型生成侧，而不是等参数传回来再容错。开启后工具 schema 会交给 OpenAI 的 structured outputs 严格校验，模型的参数不再出现类型不符、缺必填项、枚举值瞎编的情况。两个限制要知道：

- 只对 OpenAI 系模型有效，`ChatAnthropic` 等没有等价开关；
- strict 模式对 schema 有额外要求（`required` 要覆盖全部属性、`additionalProperties` 为 false），带默认值的可选参数会被要求显式给出——所以它更适合"参数少、必填明确"的工具。

`strict=True` 替代不了工具内的容错：模型传的值可能"格式合法但语义不对"（把"明天"当日期字符串传进来），仍要在工具里兜。**一句话：能靠 schema 拦住的别留到工具里容错，schema 拦不住的才写容错代码。**

### 3.3.2 第二类问题：工具执行失败后模型反复重试（最重要）

这是 Agent 工具调用最常见的生产事故：

```
用户："帮我查订单 ORD-12345"
  → LLM 调用 search_order("ORD-12345")
  → 数据库连接池满了，工具抛异常
  → LLM 看到异常，再次调用 search_order("ORD-12345")
  → 再次失败
  → LLM 再次调用...
  → 循环 10 次，每次都是同样的失败，Token 全浪费
```

**根本原因：LLM 不知道"这个失败是不可恢复的"。** 它看到一个错误，本能反应是"我再试一次"，就像人类看到网页加载失败会刷新一样。

解法分三层：

**第一层：让失败"显式失败"——用框架的错误语义，而不是压成普通文本**

（工具内 try-catch 的做法见《开发基本要求》章"接口边界和工具函数必须 try-catch"一节，这里讲的是它如何与框架的失败语义对接）

LangChain / LangGraph 已经把"失败"建模成一等公民，不需要自己发明一段中文文本：

| 机制 | 位置 | 作用 |
|------|------|------|
| `ToolException` | 工具内 `raise` | 声明"这是可预期的失败"（业务失败、依赖不可用），与代码 bug 区分开 |
| `handle_tool_error` | `@tool(handle_tool_error=...)` | 把 `ToolException` 转成工具输出：`True`（用异常消息）/ 固定字符串 / 回调函数 |
| `handle_validation_error` | `@tool(handle_validation_error=...)` | 把参数校验失败（Pydantic `ValidationError`）转成工具输出 |
| `handle_tool_errors` | `ToolNode(handle_tool_errors=...)` | 节点级兜底：按异常类型、异常元组或回调统一转换 |
| `ToolMessage.status` | 消息层 | `Literal["success", "error"]`：失败可统计、可识别、可区分于正常返回 |

```python
# tools/order_tools.py
from langchain_core.tools import tool, ToolException


def _order_error_output(e: ToolException) -> str:
    """把 ToolException 翻成“模型能执行的指令”；不要泄露连接串、内网地址等内部细节。"""
    return (
        f"订单查询失败：{e}。\n"
        f"重复调用同一参数不会改变结果：请勿再次调用本工具，"
        f"改为告知用户“订单系统暂时不可用，请稍后再试”。"
    )


@tool(parse_docstring=True, handle_tool_error=_order_error_output)
async def search_order(order_id: str) -> str:
    """按订单号查询订单详情。仅在用户给出明确订单号时调用。

    Args:
        order_id: 订单号，格式 ORD-XXXXX。
    """
    try:
        result = await db_query(order_id)
    except (ConnectionError, TimeoutError) as e:
        # 可预期的依赖失败 → 转成 ToolException，交给 handle_tool_error 处理
        raise ToolException(f"订单库不可用（{type(e).__name__}）") from e

    if result is None:
        raise ToolException(f"未找到订单 {order_id}，请确认订单号是否正确")
    return render_order(result)
```

交给框架处理后，这条工具结果会带上 `status="error"`（以带 `tool_call_id` 的方式调用时，`langchain-core` 会把 `handle_tool_error` 的处理结果包成 `status="error"` 的 `ToolMessage`）。相比"返回一段以 `[工具执行失败]` 开头的中文"，差别是实打实的：

- **可观测**：监控能按 `status="error"` 统计失败率；压成普通文本就只能靠字符串匹配，改了文案就断
- **可区分**：压成普通文本后，下游分不清"工具失败了"和"工具正常返回了这段文字"，前端提示、降级按钮、审计日志会全部失真
- **可重试**：只有 `status="error"` 的调用才该走换工具/降级逻辑，成功调用不会被误伤

工具内挂 `handle_tool_error` 与节点级配 `handle_tool_errors` 二选一即可：前者能给出更贴业务的文案，后者所有工具共用一套文案、省事。参数格式错误的文案用同一个工具上的 `handle_validation_error` 定制（它比在工具内 `try/except ValidationError` 更早生效——校验发生在进入函数体之前）。

**一句话：失败要用框架的失败语义表达；"把异常吞掉、返回一段中文"等于把失败降级成了正常输出。**

**第二层：只在"失败"时计数的重复调用守卫**

第一层解决了"模型不知道这是失败"，但模型仍可能反复试。守卫的作用是：同一个 thread 里，同一工具 + 同一组参数**连续失败**到阈值，就不再执行，直接短路成错误消息。

三个关键设计（对照下面的代码）：

1. **只统计失败**：成功的调用不计数，还会清零。用户追问同一订单、轮询型工具、同一查询在后续轮次复用，都是合法的重复调用——判定只看"失败过几次"，不看"参数是不是一样"
2. **状态放 Redis**：多 worker 下所有进程看到同一份计数（进程内 `dict` 会因为请求落到哪个进程而表现不一致）；key 带 TTL，长生命周期进程不会累积
3. **拦截必须终止该条 tool_call**：返回 `status="error"` 的 `ToolMessage` 并带上 `tool_call_id`，否则模型每轮拿到同一条文本、循环照旧，最后还是靠 `recursion_limit` 兜底

```python
# core/tool_guard.py —— 只看"失败"的重复调用守卫，状态在 Redis（多 worker 一致 + 自动过期）
import hashlib
import json

from core.cache import get_redis
from core.logger import get_logger

logger = get_logger(__name__)

MAX_SAME_FAILURE = 3
FAIL_TTL_SECONDS = 600  # 失败计数 10 分钟过期，Redis 与进程都不会无限累积


def _fail_key(thread_id: str, tool_name: str, tool_args: dict) -> str:
    """同一 thread + 同一工具 + 同一参数 → 同一个 key（参数顺序无关）。"""
    payload = json.dumps(tool_args, sort_keys=True, ensure_ascii=False, default=str)
    digest = hashlib.sha256(payload.encode()).hexdigest()[:16]
    return f"tool_fail:{thread_id}:{tool_name}:{digest}"


class ToolFailureGuard:
    """重复"失败"守卫：成功不计数、失败累加、成功即清零。"""

    def __init__(self, max_failures: int = MAX_SAME_FAILURE, ttl_seconds: int = FAIL_TTL_SECONDS):
        self.max_failures = max_failures
        self.ttl = ttl_seconds

    async def block_reason(self, thread_id: str, tool_name: str, tool_args: dict) -> str | None:
        """执行前检查：返回拦截原因（None 表示放行）。"""
        redis = get_redis()
        failures = await redis.get(_fail_key(thread_id, tool_name, tool_args))
        if failures is None or int(failures) < self.max_failures:
            return None

        logger.warning(
            "重复失败调用被拦截 | thread=%s | tool=%s | failures=%s",
            thread_id, tool_name, failures,
        )
        return (
            f"[同一调用已连续失败 {int(failures)} 次]\n"
            f"重复调用同一参数不会改变结果：请停止调用 {tool_name}，"
            f"基于已有信息回答用户，或告知用户当前操作无法完成。"
        )

    async def record(self, thread_id: str, tool_name: str, tool_args: dict, *, ok: bool, error: str = "") -> None:
        """执行后记账：成功清零，失败 +1 并续期 TTL。"""
        redis = get_redis()
        key = _fail_key(thread_id, tool_name, tool_args)

        if ok:
            await redis.delete(key)
            return

        failures = await redis.incr(key)
        await redis.expire(key, self.ttl)
        logger.warning(
            "工具失败计数 | thread=%s | tool=%s | failures=%d | error=%s",
            thread_id, tool_name, failures, error,
        )


# 进程内只有这一个无状态对象，计数全在 Redis——多 worker 下行为一致
tool_guard = ToolFailureGuard()
```

**第三层：Agent 层面设置 `recursion_limit`**

```python
from langgraph.graph import StateGraph

graph = StateGraph(...)
# ...
compiled = graph.compile()

# 调用时限制最大步数
result = await compiled.ainvoke(
    {"messages": [...]},
    config={"recursion_limit": 15},  # 最多 15 个 super-step（一轮 ReAct：LLM→Tool→LLM 约占 2~3 个）
)
```

`recursion_limit` 不是专门针对工具调用的，但它是不依赖任何业务逻辑的硬上限：前两层都失效时，它保证请求一定能结束。当 Agent 步数超限，LangGraph 会抛出 `GraphRecursionError`，被路由层的 try-catch 兜住。

**把守卫接到 `ToolNode` 上——不要自己写工具执行器**

守卫和超时要挂在 `ToolNode` 的 `awrap_tool_call` 钩子上，而不是另写一个 `execute_tool` 执行器。原因很实际：`ToolNode` 已经负责了一轮里多个 `tool_calls` 的**并行执行**、结果与 `tool_call_id` 的**一一配对**，以及 `InjectedState` / `InjectedStore` / `ToolRuntime` 的**参数注入**。自建执行器（`await tool_func.ainvoke(args)` 再 `return str(result)`）这三样全丢：返回裸字符串没有 `tool_call_id` 可回填，消息流会缺配对；一轮里的多个工具只能串行；注入类工具直接报错。

```python
# core/tool_node.py —— 唯一一条工具执行路径：ToolNode + 失败守卫 + 超时
import asyncio

from langchain_core.messages import ToolMessage
from langchain_core.tools import ToolException
from langgraph.prebuilt import ToolCallRequest, ToolNode

from core.logger import get_logger
from core.tool_guard import tool_guard

logger = get_logger(__name__)

TOOL_TIMEOUT_SECONDS = 20.0


async def guard_and_timeout(request: ToolCallRequest, execute) -> ToolMessage:
    """
    ToolNode 的 awrap_tool_call 钩子：一轮里的每个 tool_call 各走一次。

    执行前查守卫 → 执行时加超时 → 执行后按结果记账。
    """
    call = request.tool_call          # {"id": ..., "name": ..., "args": {...}}
    tool_name, tool_args = call["name"], call["args"]
    thread_id = (request.state or {}).get("session_id", "")   # 本项目 session_id == thread_id

    blocked = await tool_guard.block_reason(thread_id, tool_name, tool_args)
    if blocked is not None:
        # 关键：短路也必须返回带 tool_call_id 的失败消息，消息流才不会错位
        return ToolMessage(
            content=blocked, tool_call_id=call["id"], name=tool_name, status="error",
        )

    try:
        async with asyncio.timeout(TOOL_TIMEOUT_SECONDS):
            result = await execute(request)
    except TimeoutError:
        await tool_guard.record(thread_id, tool_name, tool_args, ok=False, error="timeout")
        return ToolMessage(
            content=(
                f"工具 '{tool_name}' 超过 {TOOL_TIMEOUT_SECONDS:.0f} 秒未返回，已取消执行。"
                f"请勿重复调用，改用其他信息回答，或告知用户稍后重试。"
            ),
            tool_call_id=call["id"], name=tool_name, status="error",
        )
    except Exception as e:            # 兜底：不让一个工具把整张图带崩
        logger.exception("工具执行异常 | tool=%s | args=%s", tool_name, tool_args)
        await tool_guard.record(thread_id, tool_name, tool_args, ok=False, error=type(e).__name__)
        return ToolMessage(
            content=f"工具 '{tool_name}' 执行失败（{type(e).__name__}）。请勿重复调用同一参数。",
            tool_call_id=call["id"], name=tool_name, status="error",
        )

    ok = not (isinstance(result, ToolMessage) and result.status == "error")
    await tool_guard.record(thread_id, tool_name, tool_args, ok=ok)
    return result


# 工具节点：全项目只有这一个执行入口（3.6.3 按场景分组时也复用它）
tool_node = ToolNode(
    ALL_TOOLS,
    # 参数校验失败由框架默认处理；这里显式声明哪些执行期异常要转成失败消息
    handle_tool_errors=(TimeoutError, ConnectionError, ToolException),
    awrap_tool_call=guard_and_timeout,
)
```

两个细节：

- **`asyncio.timeout` 与取消**：超时会向工具协程注入 `CancelledError`。`CancelledError` 继承自 `BaseException`，所以上面的 `except Exception` 不会把它当普通异常吞掉——客户端断开或上游取消时，取消照常向上传播。兜底**不要**写成 `except BaseException`，那会把取消也吞掉，协程变成"假装成功"。
- **`handle_tool_errors` 的默认行为**：框架默认的 `_default_handle_tool_errors` 只把参数校验类错误（`ToolInvocationError`）转成 `status="error"` 的消息，其他异常照旧向上抛——这是合理的，代码 bug 不该被静默吞掉。生产里再按自己的异常分类显式声明（如上面的元组），或传一个回调函数定制文案；传字符串/回调时，内容会进入模型上下文，注意别带内部细节。

三层的关系是"从里到外"：工具用 `status="error"` 把话说清楚（第一层，让模型有机会自己改）→ 连续失败到阈值就物理降温（第二层）→ 硬上限收尾（第三层）。**一句话：守卫要拦的是"反复失败"，不是"重复调用"；拦截时还必须把这次调用明确标成失败（`status="error"`），否则前两层白做，最后还是靠步数上限兜底。**

### 3.3.3 第三类问题：工具返回的信息太多，淹没了 LLM 的注意力

```python
# ❌ 工具返回了 5000 字的知识库搜索结果
@tool
async def search_knowledge_base(query: str) -> str:
    results = await vector_search(query, top_k=20)
    return "\n".join(r["content"] for r in results)  # 可能 10000+ 字符
```

LLM 面对一堵文本墙，很容易忽略关键信息，或者直接"忘记"用户最初问的是什么。

**解法：工具自己做摘要、截断，只返回最相关部分。**

```python
@tool(parse_docstring=True)
async def search_knowledge_base(query: str, top_k: int = 5) -> str:
    """搜索内部知识库。用户询问产品功能、政策、操作步骤时使用。

    Args:
        query: 搜索关键词。
        top_k: 返回条数，最多 5。
    """
    results = await vector_search(query, top_k=min(top_k, 5))
    
    if not results:
        return "未找到相关内容。"
    
    formatted = []
    for i, r in enumerate(results, 1):
        # 每条结果截断到 300 字符
        content = r["content"][:300]
        if len(r["content"]) > 300:
            content += "..."
        formatted.append(f"{i}. [{r.get('title', '无标题')}] {content}")
    
    return "\n".join(formatted)
```

**经验值：单个工具返回值控制在 1500 字符以内（经验观察，不是测量结论，按模型上下文预算调整）。** 如果确实需要返回大量数据（如报表），让工具写入 Redis 并返回一个引用 key，让后续代码从 Redis 读取，而不是让 LLM 处理原始数据。

### 3.3.4 第四类问题：工具挂死、永不返回（超时与取消）

上面的问题都发生在"工具返回了"之后。还有一类更阴的事故：工具根本不返回——HTTP 客户端没设超时、下游接口假死、数据库锁等待。表现是"日志不动、CPU 不高、QPS 归零"，8 个 worker 被 8 个挂死的请求占满，比抛异常难排查得多。

```python
import asyncio

import httpx

from langchain_core.tools import ToolException, tool


# ❌ 没有超时的工具：下游假死就把这个 worker 占死
@tool(parse_docstring=True)
async def fetch_shipment(order_id: str) -> str:
    """查询物流轨迹。

    Args:
        order_id: 订单号。
    """
    async with httpx.AsyncClient() as client:
        resp = await client.get(f"https://logistics.internal/track/{order_id}")  # 可能永远不返回
        return resp.text


# ✅ 两层超时：客户端超时保证连接层不挂，asyncio.timeout 保证整段逻辑不超预算
@tool(parse_docstring=True)
async def fetch_shipment(order_id: str, timeout_seconds: float = 5.0) -> str:
    """查询物流轨迹。

    Args:
        order_id: 订单号。
        timeout_seconds: 超时秒数，默认 5，最大 10。
    """
    budget = min(timeout_seconds, 10.0)
    try:
        async with asyncio.timeout(budget):
            async with httpx.AsyncClient(timeout=budget) as client:
                resp = await client.get(f"https://logistics.internal/track/{order_id}")
                return resp.text
    except TimeoutError as e:
        # 超时是"不可判定的失败"（请求可能已送达下游）→ 抛 ToolException，由框架转成失败消息
        raise ToolException(f"物流接口 {budget:.0f} 秒未响应") from e
```

超时要有预算层级，三层的值必须"外大内小"：

| 层 | 谁设 | 典型值 | 超时后 |
|----|------|--------|--------|
| 单次下游请求 | `httpx` / `asyncpg` 客户端参数 | 3~5 秒 | 抛 `TimeoutError` |
| 单个工具 | `asyncio.timeout`（挂在 `ToolNode` 的 wrap 钩子里，见 3.3.2） | 10~20 秒 | 取消协程 → `status="error"` |
| 整个请求 | 路由层 / 网关 | 30~60 秒 | 返回 503，让客户端重试 |

**规则：外层预算要大于内层之和的期望值。** 否则内层的失败处理还没跑完，外层就把整条链路取消了，工具看起来"什么也没发生"。并发上限与超时是一套东西：全局并发控制见同目录《对话接口》的 1.3.4"并发控制：别把 LLM API 打爆"，工具侧再叠加工具级超时，worker 才不会被挂死请求占满。

取消这件事还有个容易写反的地方：`asyncio.timeout` 超时会向工具协程注入 `CancelledError`，而 `CancelledError` 继承自 `BaseException`——所以工具里写 `except Exception` 是安全的（不会吞掉取消），但**绝不要**写 `except BaseException` 或裸 `except:`，那会把取消当成普通异常处理，协程变成"假装完成"。工具里若启动了子任务或写了一半的写操作，用 `finally` 收尾，或靠 3.3.5 的幂等键兜住。

最后统一到失败语义上：**超时必须转成 `ToolException` 或 `status="error"` 的消息，不要抛裸异常穿透到图里**——除 `GraphRecursionError` 之外的裸异常会直接终止整个工作流。

### 3.3.5 第五类问题：写操作的"已送达但响应超时"（幂等键）

前面反复出现的"请勿重试"其实是一个保守策略，而不是解法。写操作（create / cancel / charge / send）真正的风险是**请求已送达下游、响应超时**——Agent 无法判定到底成没成：

```
        ┌─ 重试 → 可能重复扣款、重复发货、重复发券
无法判定 ─┤
        └─ 不重试 → 可能业务根本没做，用户以为取消成功了
```

只有幂等键能把这件事变成确定问题：给同一个"业务意图"一个稳定的 key，下游按 key 去重——同一个 key 第二次请求直接返回首次的结果。于是重试从危险动作变成安全动作。

```python
# tools/payment_tools.py
import hashlib
import json
from typing import Annotated

from langchain_core.tools import ToolException, tool
from langgraph.prebuilt import InjectedState


def _idempotency_key(thread_id: str, tool_name: str, args: dict) -> str:
    """
    幂等键由服务端派生，不要交给模型自由编造——
    模型每一轮可能编出不同的 key，重试就退化成了重复提交。
    """
    payload = json.dumps({"t": thread_id, "n": tool_name, "a": args}, sort_keys=True, ensure_ascii=False, default=str)
    return f"{tool_name}:{hashlib.sha256(payload.encode()).hexdigest()[:24]}"


@tool(parse_docstring=True)
async def charge_user(
    user_id: str,
    amount: float,
    state: Annotated[dict, InjectedState],   # 由框架注入图状态，不计入参数 schema
) -> str:
    """给用户扣款。仅在用户明确确认金额后调用。

    Args:
        user_id: 用户 ID。
        amount: 金额，单位元。
    """
    key = _idempotency_key(
        state.get("session_id", ""), "charge_user", {"user_id": user_id, "amount": amount}
    )
    # 同一个 key 重复提交，支付网关只会扣一次：第二次直接返回首次结果
    result = await payment_client.charge(user_id=user_id, amount=amount, idempotency_key=key)

    if result.status == "failed":
        raise ToolException(f"扣款失败：{result.reason}")
    return f"扣款成功，流水号 {result.txn_id}"
```

四条实操规则：

- **键从"业务意图"派生**：thread_id + 工具名 + 业务参数（上例用 `hashlib` 压成定长 key）。用随机值、时间戳或让模型自己编，等于没有幂等
- **TTL 要覆盖用户可能重试的最长窗口**（比如 24 小时），比 600 秒的失败计数 TTL 长得多——两者解决的不是同一个问题
- **下游不支持幂等键时，自己在 Redis 上兜一层**：用 `SET nx` 保证"同一 key 只提交一次"，重复请求改为查询结果
- **读操作不需要幂等键**（search / list 天然幂等），写操作必须有

```python
# 下游不支持幂等键时的兜底：同一 key 只提交一次，重复请求改为查状态
async def submit_once(key: str, submit, query_result):
    """submit: 真正提交的业务协程；query_result: 按 key 查询最终结果。"""
    redis = get_redis()
    if not await redis.set(f"idem:{key}", "pending", nx=True, ex=86400):
        return await query_result(key)      # 已经提交过：查最终结果，不要再提交
    return await submit()
```

有了幂等键，"请勿重试"这句话就可以按操作性质分开写了：读操作随便重试；**带幂等键的写操作可以安全重试**；只有"下游既不支持幂等键、又发生了不可判定超时"才需要保守处理。**一句话：能用幂等键解决的，不要让模型去猜"要不要重试"。**

问题：

- 每加一个新系统，要新写 5 个工具
- 工具描述维护成本高

### 3.4.2 方案：一个系统一个通用工具，用 `action` 参数分发

```python
from typing import Literal, Optional
from pydantic import BaseModel, Field
from langchain_core.tools import tool, ToolException


# ============ 订单系统的通用工具 ============

class OrderToolInput(BaseModel):
    action: Literal["search", "create", "update", "cancel", "list"] = Field(
        description="操作类型：search=查询单个订单, create=创建订单, update=更新订单, cancel=取消订单, list=列出订单"
    )
    order_id: Optional[str] = Field(default=None, description="订单号，search/update/cancel 时必填")
    keyword: Optional[str] = Field(default=None, description="搜索关键词，list 时可选")
    data: Optional[dict] = Field(default=None, description="订单数据，create/update 时必填")


WRITE_ACTIONS = {"create", "update", "cancel"}   # 写操作：失败重试要靠幂等键（见 3.3.5）


@tool(args_schema=OrderToolInput)
async def order_tool(
    action: str,
    order_id: Optional[str] = None,
    keyword: Optional[str] = None,
    data: Optional[dict] = None,
) -> str:
    """
    订单管理工具。支持查询、创建、更新、取消和列出订单。
    
    使用场景：
    - 用户询问某个订单的状态 → action='search'，传入 order_id
    - 用户要下订单 → action='create'，传入 data
    - 用户要取消订单 → action='cancel'，传入 order_id
    - 用户要查看所有订单 → action='list'
    """
    try:
        if action == "search":
            return await _search_order(order_id)
        elif action == "create":
            return await _create_order(data)
        elif action == "update":
            return await _update_order(order_id, data)
        elif action == "cancel":
            return await _cancel_order(order_id)
        elif action == "list":
            return await _list_orders(keyword)
        raise ToolException(f"未知操作 '{action}'，支持：search, create, update, cancel, list")
    except (ConnectionError, TimeoutError) as e:
        # 失败要抛出去（由 handle_tool_error / ToolNode 转成 status="error"），
        # 而不是 return 一段"失败文本"——那是把失败降级成正常输出（见 3.3.2）
        hint = (
            "该写操作已带幂等键提交，重试不会重复执行"     # 见 3.3.5
            if action in WRITE_ACTIONS
            else "读操作可直接重试"
        )
        raise ToolException(f"订单操作失败（{action}，{type(e).__name__}）。{hint}") from e


# 同样模式：库存系统
```

用 `args_schema` 时，参数说明写在 `Field(description=...)` 里，docstring 只留"工具干什么、什么时候用"——正好对应 3.1.1 讲的分工。

对比效果：

| 维度 | 15 个独立工具 | 3 个通用工具 + action 分发 |
|------|-------------|--------------------------|
| 工具定义 token 开销 | 高（每个工具一份 name + description + schema） | 约为前者的 1/3（3 份描述代替 15 份） |
| 新增操作 | 写新工具 + 注册 | 在 action 枚举里加一项 |
| LLM 选择准确率 | 候选多、描述相似时容易混淆 | 候选少、枚举取值互斥，更稳（经验观察） |
| 工具描述维护 | 15 个 docstring | 3 个 docstring |

### 3.4.3 `action` 枚举的设计要点

**要点一：`Literal` 类型让参数更精确**

```python
# ✅ Literal 告诉 LLM 只能选这些值
action: Literal["search", "create", "update", "cancel", "list"]

# ❌ 普通 str，LLM 可能传 "find" 或 "query" 导致匹配不到
action: str
```

**要点二：description 里写清楚使用场景**

LLM 是靠工具描述来判断"什么时候该调哪个工具"的。`action` 的每个值对应什么场景，必须在描述里写明白：

```python
action: Literal["search", "create", "cancel"] = Field(
    description="操作类型：search=查询单个订单（用户问某订单状态时）, "
                "create=创建新订单（用户要下单时）, "
                "cancel=取消订单（用户要取消时）"
)
```

**要点三：可选参数通过 `Optional` + `default=None` 区分必填和选填**

```python
order_id: Optional[str] = Field(default=None, description="订单号，search/cancel 时必填")
keyword: Optional[str] = Field(default=None, description="搜索关键词，list 时可选")
```

LLM 看到 `required` 属性会自动判断哪些参数必须传。

### 3.4.4 更激进的方案：一个服务一个透传工具（弱 schema）

如果工具种类非常多（比如对接了 20+ 个微服务），可以退一步，为每个服务只写一个透传工具，参数压成 `service + method + params` 三个字段：

```python
from typing import Any
from pydantic import BaseModel, Field

from langchain_core.tools import ToolException, tool


class ServiceCallInput(BaseModel):
    service: str = Field(description="服务名称：order / inventory / logistics / notification / billing")
    method: str = Field(description="方法名。如 order 服务支持: get_by_id, create, cancel, list_by_user")
    params: dict[str, Any] = Field(default_factory=dict, description="方法参数，键值对形式")


@tool(args_schema=ServiceCallInput)
async def service_call(service: str, method: str, params: dict[str, Any]) -> str:
    """
    通用微服务调用工具。
    
    可用服务及方法：
    - order: get_by_id(需要order_id), create(需要data), cancel(需要order_id), list_by_user(可选keyword)
    - inventory: check(需要product_id), adjust(需要product_id,quantity), list()
    - logistics: track(需要order_id), estimate(需要order_id)
    - notification: send(需要user_id,message,channel)
    - billing: get_balance(需要user_id), charge(需要user_id,amount,description)
    """
    service_func = SERVICE_REGISTRY.get(service)
    if not service_func:
        raise ToolException(f"服务 '{service}' 不存在。可用：{list(SERVICE_REGISTRY.keys())}")

    method_func = getattr(service_func, method, None)
    if not method_func:
        raise ToolException(f"方法 '{service}.{method}' 不存在，可用方法见工具描述")

    try:
        return await method_func(**params)
    except (ConnectionError, TimeoutError) as e:
        raise ToolException(f"服务调用失败 [{service}.{method}]（{type(e).__name__}）") from e
```

**代价必须说清楚：** `params: dict` 没有结构化的 JSON Schema，模型要自己拼这个对象——参数名、类型、必填项全靠 `method` 的约定，填错的概率明显高于具名参数。所以它只适合"工具数量实在太多、且每个方法都很独立"的场景。另外要澄清一个常见误解：**本节和 3.4.2 的弱化方案都不是"用 `**kwargs` 写通用工具"**——`**kwargs` 本身不是一条可用的路：

- 想让 `@tool` 用 `**kwargs` 接结构化参数是做不到的——langchain-core 在有 `**kwargs` 时只会保留一个名为 `kwargs` 的合成字段，模型在 schema 里只看得到一个结构不明的对象，效果不比 `params: dict` 好，描述还更难写
- 所以参数形态的优先级是：具名参数工具（最好）→ `action` 枚举（3.4.2）→ `params: dict` 透传（本节的弱 schema，最差）；工具再多就该走 3.6.4 的检索式选择，而不是把 schema 继续弱化

## 3.5 意图识别：到底要不要调工具

### 3.5.1 意图识别为什么重要

看这两句话：

> 用户 A："帮我查一下我昨天的订单" → 需要调工具
> 用户 B："我想了解一下什么是订单号" → 不需要调工具

如果 Agent 对 B 也调了 `search_order`，返回一个空结果，然后 LLM 看着空结果强行编造回复——用户体验极差。

**意图识别的目标：在调用工具之前，先判断"用户是在要求做事，还是在聊天/提问"。**

### 3.5.2 方案一：靠 LLM 原生判断（`tool_choice="auto"`）

大多数情况下，GPT-5.1 / Claude 等强模型自带的判断能力已经很好了。写清楚工具描述，LLM 会在该调的时候调，不该调的时候不调。

```python
# 工具描述写好了，LLM 自己会判断
@tool
async def search_order(order_id: str) -> str:
    """
    查询指定订单号的订单详情。仅在用户明确提到一个订单号并要求查询时使用。
    如果用户只是在聊订单相关的一般性话题，不要调用此工具。
    """
    ...
```

但单靠 LLM 判断有两个风险：
- 弱模型（如 5-mini）可能判断失误
- 边界模糊的场景（用户说"你觉得我应该取消这个订单吗"——这是要调工具查订单状态，还是纯聊天给建议？）

### 3.5.3 方案二：前置意图分类（双阶段路由）

用一次轻量级 LLM 调用先做意图分类，再决定走工具调用路径还是纯对话路径：

```python
# core/intent_classifier.py
import json
from enum import Enum
from pydantic import BaseModel, Field
from langchain_core.prompts import ChatPromptTemplate
from core.llm import call_llm_with_retry


class Intent(str, Enum):
    ACTION = "action"           # 需要执行操作（查订单、发邮件、改设置）
    QUESTION = "question"        # 知识性问题（什么是XX、怎么理解XX）
    CHITCHAT = "chitchat"        # 闲聊（你好、谢谢、今天心情怎么样）
    CLARIFICATION = "clarification"  # 用户消息不明确，需要追问


class IntentResult(BaseModel):
    intent: Intent
    confidence: float = Field(ge=0.0, le=1.0)
    reasoning: str = Field(default="")


INTENT_PROMPT = ChatPromptTemplate.from_messages([
    ("system", """你是一个意图分类器。分析用户消息，判断对话意图。

意图类型：
- action：用户要求执行某个具体操作（查询、创建、修改、删除、发送）。这些操作需要调用工具才能完成。
  示例："帮我查订单 ORD-001"、"取消我的订阅"、"把名字改成张三"
  
- question：用户在询问知识、概念、原理、方法。不需要调用工具，用模型自身知识回答即可。
  示例："什么是 RESTful API？"、"Python 怎么处理并发？"、"你推荐什么编程语言？"
  
- chitchat：纯社交对话，不需要工具也不需要专业知识。
  示例："你好"、"谢谢"、"今天星期几"、"讲个笑话"
  
- clarification：用户消息太模糊，无法判断意图，需要追问。
  示例："那个东西怎么样了"、"帮我看一下"（没有指明看什么）

只输出 JSON。"""),
    ("user", "{message}"),
])


async def classify_intent(message: str) -> IntentResult:
    """对用户消息做意图分类"""
    prompt = INTENT_PROMPT.format_messages(message=message)
    
    response = await call_llm_with_retry(
        messages=prompt,
        model="gpt-5-mini",          # 意图分类用小模型即可
        response_format={"type": "json_object"},
    )
    
    return IntentResult(**json.loads(response))
```

路由层根据意图分派：

```python
# routes/chat.py
from core.intent_classifier import classify_intent, Intent


@router.post("/completions")
async def chat_completions(request: ChatRequest):
    # 第一步：意图分类
    intent_result = await classify_intent(request.message)
    logger.info("意图分类 | session_id=%s | intent=%s | confidence=%.2f",
                request.session_id, intent_result.intent, intent_result.confidence)

    # 第二步：按意图路由
    if intent_result.intent == Intent.ACTION and intent_result.confidence > 0.7:
        # 绑定工具，走 Agent 工具调用流程
        return await _handle_with_tools(request)
    
    elif intent_result.intent == Intent.CLARIFICATION:
        # 追问用户，不走工具
        return await _handle_clarification(request, intent_result.reasoning)
    
    else:
        # 纯对话，不绑定工具
        return await _handle_chat_only(request)
```

### 3.5.4 方案三：关键词匹配做"短路"，不做定级

关键词只适合一种用法：**只对不可能有歧义的强信号直接短路**，其余一律交给 LLM。反过来做（任意位置命中"查一下"就判 action 并给 0.9 置信度）非常危险——`r"(查一下|搜一下|看一下).*"` 这种无锚点模式在句中出现即命中，"我不确定该不该查一下我的订单""别帮我查一下了"都会被强行推到工具路径，直接越过 LLM 的判断。

把关键词分成两级：

```python
# core/intent_quick_check.py
import re

# 强信号：句首祈使 + 明确写操作动词。命中即可直接短路——这类句子几乎不可能是询问或闲聊
STRONG_ACTION_PATTERNS = [
    r"^\s*(取消|删除|改掉|修改|创建|新建|发送|下单|订购|购买|设置|切换)",
    r"^\s*(帮我|给我|替我)\s*(取消|删除|创建|发送|下单|订购|购买)",
]

# 弱信号：只是"看起来像要查东西"，只能作为候选信号，不能单独定级
WEAK_ACTION_PATTERNS = [
    r"(帮我|给我|替我).{0,8}(查|搜|找)",
    r"(查一下|搜一下|找一下|看一下)",
]

# 纯闲聊：同样要锚定句首，英文词再加词边界，避免 "hi" 命中 "history" 这类句子
CHITCHAT_PATTERNS = [
    r"^\s*(你好|嗨|在吗|谢谢|多谢|再见|晚安|早安)",
    r"^\s*(hi|hello|bye)\b",
    r"^\s*(讲个|来个|说个)(笑话|故事|段子)",
]


def quick_intent_check(message: str) -> str | None:
    """
    只返回"强信号"结论：能直接定级的返回 "action" / "chitchat"；
    其余（含所有弱信号）返回 None，交给 LLM 分类。
    """
    message = message.strip()

    for pattern in STRONG_ACTION_PATTERNS:
        if re.search(pattern, message):
            return "action"

    for pattern in CHITCHAT_PATTERNS:
        if re.search(pattern, message):
            return "chitchat"

    return None


def has_weak_action_signal(message: str) -> bool:
    """弱信号：只用来给分类模型加一句提示，不能代替模型判断。"""
    return any(re.search(p, message) for p in WEAK_ACTION_PATTERNS)


# 使用
quick = quick_intent_check(request.message)
if quick == "action":
    # 只有强信号才允许短路，且这里的置信度是"规则置信度"，与 LLM 输出的置信度不是一回事
    intent_result = IntentResult(intent=Intent.ACTION, confidence=0.9, reasoning="命中强信号祈使句")
elif quick == "chitchat":
    intent_result = IntentResult(intent=Intent.CHITCHAT, confidence=0.9, reasoning="命中强信号闲聊词")
else:
    # 弱信号一律复核："我不确定该不该查一下我的订单"这类句子必须由 LLM 判断
    if has_weak_action_signal(request.message):
        logger.info("命中弱信号，仍需 LLM 复核 | message=%s", request.message[:50])
    intent_result = await classify_intent(request.message)
```

注意这里的置信度语义：`0.9` 是"规则模式的置信度"，用来通过下游的 `confidence > 0.7` 阈值；它**不代表**模型认为这是 action。所以弱信号绝不能带这个值——否则就是绕过 LLM 做判断。

### 3.5.5 三个方案的对比与组合

```
用户消息到达
     │
     ▼
┌──────────────┐
│ 关键词快速判断 │  ← 方案三：几乎零延迟；只覆盖"句首祈使 + 写操作"的强信号，命中即短路
└──┬───────┬───┘
   │       │
  强信号  其他（含所有弱信号）
   │       │
   ▼       ▼
  直接    ┌──────────────┐
  路由    │ LLM 意图分类  │  ← 方案二：1~2 秒，兜住其余全部情况（弱信号只是提示）
          └──┬───────┬───┘
             │       │
          action   其他
             │       │
             ▼       ▼
         ┌──────┐ ┌──────┐
         │Agent │ │纯对话 │  ← 方案一：Agent 内部 LLM 再次判断具体调哪个工具
         │+工具  │ │模式   │
         └──────┘ └──────┘
```

**推荐组合：方案三（只做强信号短路）+ 方案二（LLM 分类）。** 方案一（纯靠 LLM）作为 Agent 内部的基础能力。三层叠加的关键是"关键词层宁可漏、不可错"：漏掉的句子由 LLM 兜住，只有正确率极高。

### 3.6.3 按场景限缩工具集

不是所有场景都需要全量工具。把工具分组，不同 Agent 节点只绑定所需的子集——这也是"全量绑 15 个"最直接的解法：

```python
# core/agent.py
from langgraph.graph import StateGraph, MessagesState
from langchain_openai import ChatOpenAI
from tools import ORDER_TOOLS, INVENTORY_TOOLS, GENERAL_TOOLS

# 工具节点复用 3.3.2 里那一个（守卫 + 超时 + handle_tool_errors 都在里面）
from core.tool_node import tool_node

llm = ChatOpenAI(model="gpt-5.1")


def build_agent():
    graph = StateGraph(MessagesState)

    # 意图路由节点：只绑通用工具
    llm_general = llm.bind_tools(GENERAL_TOOLS)

    # 订单处理节点：只绑订单工具；执行统一走同一个 ToolNode（它持有全量工具，能执行子集）
    llm_order = llm.bind_tools(ORDER_TOOLS)

    # 库存处理节点：只绑库存工具
    llm_inventory = llm.bind_tools(INVENTORY_TOOLS)

    graph.add_node("llm_general", llm_general)
    graph.add_node("llm_order", llm_order)
    graph.add_node("llm_inventory", llm_inventory)
    graph.add_node("tools", tool_node)        # 全项目唯一执行入口，不要每个节点各建一个
    # ... 定义节点和边 ...
```

这和 3.5 的意图识别是一条流水线：**意图识别决定"走哪条路"，工具分组决定"这条路上能看见哪些工具"**，两者配合才能既省 token 又少选错（经验观察：候选少、描述互斥时更稳）。注意工具节点不要每个场景各建一个 `ToolNode`——守卫、超时、错误处理只需在一处维护。

### 3.6.4 工具再多：对工具描述做检索（tool RAG）

3.4.2 的 `action` 枚举、3.6.3 的分组，解决的都是"候选太多"。但必须承认：真正的根因往往不是数量，而是**工具描述太宽泛、彼此语义重叠**——描述写好之后，20 个工具里选错的情况会大幅减少。所以先修描述，再考虑下面这些"数量级"方案：

| 方案 | 粒度 | 适用规模 | 代价 |
|------|------|---------|------|
| 全量 `bind_tools` | 不做限制 | < 10 个工具 | token 开销随工具数线性增长 |
| 任务/场景分组（3.6.3） | 按业务流程划分 | 10~30 个 | 需要先把路由做对 |
| **tool RAG：检索 top-k 再 bind** | 按当前问题动态选择 | 30+ 个，且描述区分度好 | 多一次检索延迟，可能召回错/漏 |
| 子 Agent / 命名空间拆分 | 按能力域拆分 Agent | 100+ 个，多团队维护 | 架构复杂度上升 |

tool RAG 的思路很直接：**工具描述本身就是检索语料**。把 `name + description` 离线做成向量索引，在线只 embed 用户问题，召回 top-k 个工具再 `bind_tools`：

```python
# core/tool_retriever.py —— 工具多到 bind 不完时：先检索再绑定（tool RAG）
import json

from langchain_core.tools import BaseTool

from core.cache import get_redis
from core.embedder import embed_text
from core.logger import get_logger

logger = get_logger(__name__)

TOOL_INDEX_KEY = "tool_index"     # Redis hash：工具名 → 描述向量
TOOL_INDEX_TTL = 86400


def _cosine(a: list[float], b: list[float]) -> float:
    dot = sum(x * y for x, y in zip(a, b))
    norm_a = sum(x * x for x in a) ** 0.5
    norm_b = sum(y * y for y in b) ** 0.5
    return dot / (norm_a * norm_b) if norm_a and norm_b else 0.0


async def build_tool_index(all_tools: list[BaseTool]) -> None:
    """离线建索引：进程启动时跑一次，工具增删时重跑。"""
    redis = get_redis()
    for t in all_tools:
        vector = await embed_text(f"{t.name}：{t.description}")
        await redis.hset(TOOL_INDEX_KEY, t.name, json.dumps(vector))
    await redis.expire(TOOL_INDEX_KEY, TOOL_INDEX_TTL)
    logger.info("工具索引已构建 | count=%d", len(all_tools))


async def select_tools(query: str, all_tools: list[BaseTool], top_k: int = 8) -> list[BaseTool]:
    """在线召回：只 embed 用户问题，按余弦相似度取 top-k。"""
    index = await get_redis().hgetall(TOOL_INDEX_KEY)
    by_name = {t.name: t for t in all_tools}
    query_vec = await embed_text(query)

    ranked = sorted(
        ((_cosine(query_vec, json.loads(vec)), name.decode()) for name, vec in index.items()),
        reverse=True,
    )
    selected = [by_name[name] for _, name in ranked[:top_k] if name in by_name]

    logger.info("tool RAG 召回 | top_k=%d | query=%s | tools=%s",
                top_k, query[:30], [t.name for t in selected])
    return selected


# 节点里：只把召回到的工具绑给模型
async def node_llm(state: dict) -> dict:
    tools_this_turn = await select_tools(state["user_query"], ALL_TOOLS, top_k=8)
    llm_with_tools = llm.bind_tools(tools_this_turn)
    ...
```

四个必须处理的细节：

- **召回为空要有兜底**：返回"当前没有合适工具"，或退回全量/默认子集，不能让模型"无工具可用"却以为有
- **top-k 不能太小**：召回漏掉的工具等于功能缺失，宁可 k 大一点（8~12）配合场景分组收窄
- **索引要跟着工具变更重建**：否则新增工具永远召回不到
- **命名空间/子 Agent 是同一思路的粗粒度版本**：按能力域（订单 Agent、知识库 Agent、运维 Agent）拆分，每个 Agent 只持有自己那 10~20 个工具，也是多团队并行开发时唯一可维护的形态

**一句话：工具选择的准确率，一半靠描述写清楚，一半靠候选收敛——能分组就分组，分不动就检索。**

## 3.8 常见踩坑清单

| 坑 | 现象 | 原因 | 解法 |
|----|------|------|------|
| 工具反复重试失败 | LLM 连续 5 次调同一个工具，每次报同样的错 | 失败被压成普通文本，模型分不清"失败"与"正常返回" | 工具抛 `ToolException`，由 `handle_tool_error` / `ToolNode(handle_tool_errors=...)` 转成 `status="error"` 的消息；再叠加失败计数守卫与 `recursion_limit` |
| 写操作被重复执行 | 用户被扣两次款、收到两张券 | "请求已送达但响应超时"是不可判定失败，重试与不重试都可能错 | 写操作一律带幂等键（服务端派生，见 3.3.5），让重试变安全 |
| 工具挂死不返回 | 日志不动、CPU 不高、QPS 归零，worker 被占满 | 下游假死且工具没有超时 | `asyncio.timeout` 包住工具执行，超时转 `status="error"`（见 3.3.4） |
| 工具被误调 | 用户聊天说"帮我推荐一本书"，Agent 跑去调 search_order | 工具描述太宽泛，LLM 产生幻觉性匹配 | 工具描述写"仅在用户明确提到订单号时调用" |
| 工具参数填错 | LLM 传了 `"明天"` 给要 `YYYY-MM-DD` 的参数 | LLM 不严格按格式填参数 | OpenAI 侧开 `bind_tools(..., strict=True)`；schema 拦不住的再做工具内容错（`"明天"` → `date+1`） |
| 工具太多导致选错 | 20 个工具里 LLM 选了错误的一个 | 主要不是数量，而是描述宽泛、语义重叠 | 先修描述，再合并为通用工具 + action 枚举、按场景分组（3.6.3）、必要时上 tool RAG（3.6.4） |
| 工具返回值太长 | Agent 拿到 5000 字结果后回复跑题 | 大段文本淹没了 LLM 的注意力 | 工具做截断（经验值 ≤1500 字符），或返回引用 key |
| 该调工具却没调 | LLM 用自己的知识编了一个答案，但实际需要查数据库 | `tool_choice="auto"` 时 LLM 过于自信 | 加意图分类步骤，对 action 类意图强制绑工具 |
| 慢模型判断意图太慢 | 每次请求要多等 1~2 秒做意图分类 | 意图分类走了大模型 | 用 5-mini 做分类，或关键词命中强信号时短路（弱信号不要短路） |

## 3.9 本章小结

| 要点 | 核心做法 | 一句话 |
|------|---------|--------|
| 工具定义 | `@tool` + `parse_docstring=True`（或 Pydantic `args_schema`） | 工具描述回答"要不要用"，`Args:` 里的参数说明回答"怎么填" |
| 工具绑定 | `llm.bind_tools(tools, tool_choice="auto")`；OpenAI 可加 `strict=True` | `tool_choice` 的取值跨厂商不通用，Claude 侧只有 `auto`/`any` |
| 失败语义 | `ToolException` + `handle_tool_error` + `ToolMessage.status="error"` | 失败要显式失败，别把异常压成一段中文 |
| 防止重复调用 | 只统计失败的守卫（Redis）+ 短路返回错误消息 + `recursion_limit` | 三层防线：失败说明白 > 反复失败降温 > 步数上限 |
| 超时与取消 | `httpx` 客户端超时 + `asyncio.timeout` + 超时转 `status="error"` | 没有超时的工具等于把 worker 借给下游；`CancelledError` 不要吞 |
| 写操作幂等 | 服务端派生幂等键，下游按 key 去重 | 不可判定的失败只有幂等键能解，别让模型猜"要不要重试" |
| 工具粒度 | 具名参数 > `action` 枚举 > `params: dict` 透传 | 3.4.2 的 `action` 方案能把 15 个工具压成 3 个；弱 schema 是最后手段 |
| 工具选择 | 修描述 → 场景分组 → tool RAG 检索 top-k → 子 Agent/命名空间 | 一半靠描述写清楚，一半靠候选收敛 |
| 意图识别 | 关键词只短路强信号 → LLM 分类 → 路由分派 | 关键词命中只能当候选信号，不能越过 LLM 定级 |
| 工具容错 | `strict`/schema 校验 + 异常转错误消息 + 返回值截断 | 工具不该崩，但"不崩"不等于"把失败说成普通文本" |
| 工具执行入口 | 统一走 `ToolNode`（`awrap_tool_call` 里做守卫与超时） | 自建执行器会丢并行、`tool_call_id` 配对与参数注入 |

**工具集的设计原则：工具是 LLM 的眼睛和手——眼睛要看得准（意图识别 + 候选收敛），手要稳（超时、幂等、失败语义），而且不能用一把锤子去拧螺丝（工具分组，场景限缩）。**
