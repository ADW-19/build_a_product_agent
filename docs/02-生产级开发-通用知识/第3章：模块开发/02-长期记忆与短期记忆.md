# 第二章：长期记忆与短期记忆

> **核心论点**：短期记忆让模型能"记住刚才说了什么"，长期记忆让模型能"记住你是一个什么样的人"。本章不讨论心理学概念，只讲工程实现——怎么让 Agent 在每一次对话中准确判断"什么该存入 Milvus 长期记住"、"什么只是本次对话的上下文"、以及当记忆太多时如何防止上下文爆炸。

---

## 2.1 概念澄清：工程意义上的长短期记忆

### 2.1.1 类比：人类怎么记东西

你和一个同事聊天：

- **短期记忆**：刚才 5 分钟你们聊了什么——"他说下周三要出差"、"我答应帮他查一下数据"。这些信息只在这次对话中需要，对话结束就可以忘掉。
- **长期记忆**：你认识这个同事三年了——"他叫张三，是后端工程师，擅长 Python，有两个孩子，对芒果过敏，上次一起吃饭是三个月前"。这些信息跨越多场对话，应该持久记住。

**对 Agent 来说，工程上的定义非常朴素：**

| 维度 | 短期记忆 | 长期记忆 |
|------|---------|---------|
| 生命周期 | 当前会话内有效，会话结束可丢弃 | 跨会话持久保留 |
| 存储位置 | Redis（快，可过期） | Milvus / 向量数据库（持久化，语义检索） |
| 数据形式 | 消息列表 `[{role, content}, ...]` | 结构化记忆条目 + 向量 embedding |
| 检索方式 | 直接按 session_id 全量取出 | 按语义相似度检索最相关的 N 条 |
| 典型内容 | "帮我查一下今天的天气" → "好的，今天晴天" | "用户叫张三，住在北京，喜欢简洁的回答" |
| 容量 | 受限（几十轮对话后裁剪） | 几乎无限（向量库可存百万条） |

### 2.1.2 为什么不是"给模型一个大 context 就行了"

有人问：模型上下文窗口已经到 128K token 了，为什么还要分长短期？直接把所有历史记录全塞进 prompt 不就行了？

三个原因：

1. **成本**：每轮对话都塞入 10K token 的历史，一天 1000 次对话 = 1000 万 token 的上下文处理。按输入 $1.25/1M token 算（GPT-5 档示例价，取价日 2026-09；单价随时点与模型变化，请按自己实际使用的模型核对），每天多花 $12.5，一年约 $4,600——全花在重复处理旧信息上。
2. **注意力衰减**：模型在长上下文中对中间位置的信息注意力显著下降（Lost in the Middle 现象）。塞了 50 条旧记忆，真正关键的那条可能被淹没。
3. **响应变慢**：上下文越长，首 token 延迟越高。prefill 的计算量与 prompt token 数近似成正比，128K 的 prompt 首 token 延迟通常是 1K 的十几到几十倍（具体倍率取决于模型、硬件与服务商的批处理策略，别用一个固定倍数去估容量）。

**结论：长短期记忆分离不是为了省事，是为了省钱、省时间、提准确率。**

## 2.2 短期记忆：会话内上下文管理

### 2.2.1 短期记忆的本质

短期记忆就是当前 session 的对话历史。上一章 1.2 节已经在 Redis 中按 `session_id` 隔离实现了。这里重点补充两个工程问题：**消息裁剪策略**和**多轮对话的 token 计算**。

### 2.2.2 消息裁剪：不能简单地"保留最近 N 条"

```python
# ❌ 粗暴裁剪——可能裁掉关键信息
MAX_HISTORY_LENGTH = 50
messages = messages[-MAX_HISTORY_LENGTH:]  # 保留最近 50 条
```

问题：用户在对话开头说了一句关键信息（如"用中文回复"），50 轮后被裁掉了，Agent 突然开始说英文。

**改进：分层裁剪——系统消息永不裁剪，其余按 token 预算从最旧端整轮裁掉（摘要替换见 2.4.3 的 compress_conversation）。**

```python
# core/short_memory.py
from langchain_core.messages import BaseMessage, trim_messages
from core.token_counter import count_message_tokens
from core.logger import get_logger

logger = get_logger(__name__)

# 本函数的默认值。生产代码应由 ContextBudget.short_term_memory_limit 传入（见 2.4.5）
MAX_TOTAL_TOKENS = 8000


def trim_history(
    messages: list[BaseMessage],
    max_tokens: int = MAX_TOTAL_TOKENS,
) -> list[BaseMessage]:
    """
    在 token 预算内裁剪对话历史。

    规则全部交给 langchain_core 的 trim_messages，不要自己写删除循环：
    1. strategy="last"     —— 从最新一条往回保留，砍掉最旧的一段
    2. start_on="human"    —— 裁剪后第一条必须是人类消息，历史不会以
                              assistant(tool_calls) 或 tool 结果开头
    3. include_system=True —— SystemMessage 计入预算，且永不被裁掉
    4. allow_partial=False —— 不切半条消息（切半条同样会破坏 tool 配对）

    为什么不能"按 role 二分 + 从最旧端 pop(0)"：
    assistant(tool_calls) 与紧随其后的 tool 消息是**同一轮的两个半句**，
    删掉前半句留下后半句，OpenAI 会报 tool_call_id 找不到、
    Anthropic 会报 tool_use id 没有对应的 tool_result，接口直接 400。
    带工具的 Agent 必然踩到——不是"偶尔出错"，是"必然出错"。

    旧的自己写循环的版本还有两个附带缺陷：
    - 末尾 keep_tail（最后 4 条）被整个排除在裁剪之外，尾部自身超预算时
      函数会把超预算的历史原样返回，且一声不响；
    - 只删不加、无告警，`removed` 变量取了却没人用。
    trim_messages 把尾部一并纳入预算（allow_partial=False 保证不切半条消息）。
    """
    if not messages:
        return messages

    trimmed = trim_messages(
        messages,
        max_tokens=max_tokens,
        token_counter=count_message_tokens,
        strategy="last",
        start_on="human",
        include_system=True,
        allow_partial=False,
    )

    # 连 trim_messages 也裁不动时（例如最后一条消息本身就超预算），
    # 它会把这部分原样留下。必须显式告警，不能静默把超预算历史交给下游。
    used = count_message_tokens(trimmed)
    if used > max_tokens:
        logger.warning(
            "裁剪后仍超预算：尾部单条消息过大 | used=%d | budget=%d | kept=%d",
            used, max_tokens, len(trimmed),
        )

    if len(trimmed) < len(messages):
        logger.info("历史裁剪 | %d 条 → %d 条", len(messages), len(trimmed))

    return trimmed
```

**两个 token 口径不要混用**

| 常量 | 来源 | 管的是什么 | 谁该用它 |
|------|------|-----------|---------|
| `MAX_TOTAL_TOKENS = 8000` | 本章演示用的占位默认值 | 仅"会话历史"这一项 | 单独演示裁剪函数时 |
| `ContextBudget.short_term_memory_limit`（见 2.4.5） | (128000 − 4096) × 0.75 ≈ 92928 | 会话历史在整条请求预算中的份额 | 生产代码 |

两个数差了一个数量级，同章并列就必须说明关系，否则你在一个文件里看到 8000、在另一个文件里看到 92928，不知道该信谁。**正确姿势是 `trim_history(history, max_tokens=budget.short_term_memory_limit)`，函数里的默认值只在单元测试里用。**

**消息表示必须全局统一**

`trim_history` 收的是 `BaseMessage`，2.2.1 的 `messages[-N:]` 示例里是 `dict`——同一个项目里两种表示混用，是最容易埋雷的地方。**一句话：进程内一律 `BaseMessage`（LangChain / LangGraph 的公共接口都是它），`dict` 只允许出现在存储与传输边界（Redis 里的 JSON、HTTP 请求体），且转换只做一次（见 2.2.4）。**

### 2.2.3 Token 计数：口径必须与被调模型一致

**错误做法：用"字符数 // 2"当 token 数。**

```python
# ❌ 三个问题叠在一起：算不准、与"精确计算"自相矛盾、content 为 None 时直接崩
def _count_tokens(messages: list[dict]) -> int:
    total_chars = sum(len(m.get("content", "")) for m in messages)
    return total_chars // 2  # 中英文混合，约 2 字符 ≈ 1 token
```

`get` 的默认值只在**键不存在**时生效：assistant 的 tool_calls 消息 `content` 字段存在但值是 `null`，于是 `len(None)` 抛 TypeError；多模态消息的 `content` 是数组，`len()` 得到的是"块数"而不是字符数。而且这跟本节标题里的"精确计算"是两套口径——同一个文件里既估又算，预算判断必然失真。

**正确做法：用目标模型对应的 tokenizer。**

```python
# core/token_counter.py
import tiktoken
from langchain_core.messages import BaseMessage

# 编码表按模型选，不要用一条 get_encoding 打天下
_ENCODING_BY_MODEL = {
    "gpt-5.1": "o200k_base",
    "gpt-5-mini": "o200k_base",
    "o1": "o200k_base",
    "gpt-4-turbo": "cl100k_base",
    "gpt-4": "cl100k_base",
    "gpt-3.5-turbo": "cl100k_base",
    "text-embedding-3-small": "cl100k_base",
}


def encoding_for(model: str = "gpt-5.1"):
    """按模型返回 tiktoken 编码；未登记的模型回落到 o200k_base"""
    return tiktoken.get_encoding(_ENCODING_BY_MODEL.get(model, "o200k_base"))


def message_text(msg: BaseMessage) -> str:
    """
    取出消息里的纯文本。两种"不是普通字符串"的 content 都要处理：
    - assistant 的 tool_calls 消息：content 是 None
    - 多模态消息：content 是 list[dict]（text 块 + image_url 块）
    """
    content = msg.content
    if content is None:            # ← 不是空串，是 None
        return ""
    if isinstance(content, str):
        return content
    if isinstance(content, list):  # ← 多模态：只统计文本块
        return "".join(
            block.get("text", "")
            for block in content
            if isinstance(block, dict) and block.get("type") == "text"
        )
    return str(content)


def count_tokens(text: str, model: str = "gpt-5.1") -> int:
    """精确计算一段文本的 token 数"""
    return len(encoding_for(model).encode(text))


def count_message_tokens(messages: list[BaseMessage], model: str = "gpt-5.1") -> int:
    """
    计算消息列表的 token 数，可直接作为 trim_messages 的 token_counter 传入。
    +4/条 是 OpenAI 文档给出的消息格式开销近似值（role + 分隔符），不是精确值。
    """
    total = 0
    for msg in messages:
        total += count_tokens(message_text(msg), model)
        total += 4  # 消息格式开销，OpenAI 近似值
    return total


def clip_to_tokens(text: str, max_tokens: int, model: str = "gpt-5.1") -> str:
    """把文本硬裁到 token 上限——LLM 不保证遵守"不超过 N 字"这类要求"""
    encoding = encoding_for(model)
    ids = encoding.encode(text)
    return text if len(ids) <= max_tokens else encoding.decode(ids[:max_tokens])
```

**取文本的正确写法，按表示二选一**

| 表示 | 正确写法 | 允许出现的地方 |
|------|---------|---------------|
| `dict`（`{"role", "content"}`） | `content = msg.get("content") or ""`，再对 `isinstance(content, list)` 做分支 | 只允许在存储/传输边界 |
| `BaseMessage`（`HumanMessage` 等） | `message_text(msg)`（即 `msg.content or ""` + list 分支） | 进程内的全部逻辑 |

注意 `msg.get("content", "")` 这个写法在 `BaseMessage` 上根本不存在——`.get` 是 dict 的接口。如果同一个函数的两条调用路径分别传入 dict 和 `BaseMessage`，它一定会在某条路径上崩。**这就是 2.2.2 反复强调"表示必须全局统一"的原因：混用不是风格问题，是崩溃问题。**

**计数口径必须与被调模型同源**

tiktoken 只覆盖 OpenAI 系模型。本章的对话接口支持 `claude-sonnet-4-6`（见 1.1.3 的 `model` 枚举），Claude 不走 tiktoken，官方计数接口在 Messages API 上：

```python
# Claude 系：tiktoken 算出来的数只能当参考，预算判断必须用官方接口
from anthropic import AsyncAnthropic

resp = await AsyncAnthropic().messages.count_tokens(
    model="claude-sonnet-4-6",
    messages=[{"role": "user", "content": "..."}],
)
tokens = resp.input_tokens
```

**一句话：token 计数必须与被调模型同源——OpenAI 系用 tiktoken 的模型对应编码，Claude 系用 `client.messages.count_tokens`；把 OpenAI 的 `+4/条` 近似值包装成"精确计算"，误差会随消息条数线性放大，而预算判断恰恰建在这个误差上。**

### 2.2.4 短期记忆的完整读取流程

```python
# services/chat_service.py
from langchain_core.messages import (
    BaseMessage, HumanMessage, SystemMessage, convert_to_messages,
)
from core.session import get_history
from core.short_memory import trim_history
from core.context_budget import budget


async def prepare_context(session_id: str, user_id: str, user_message: str) -> list[BaseMessage]:
    """
    为 Agent 准备上下文消息。

    组装顺序：系统提示词 → 长期记忆（检索） → 短期记忆（会话历史） → 当前用户消息
    """
    messages: list[BaseMessage] = []

    # 1. 系统提示词（角色设定）
    messages.append(SystemMessage(
        content="你是用户的 AI 助手。回答简洁、准确。用中文回复。",
    ))

    # 2. 长期记忆（从 Milvus 检索，见 2.3 节）
    long_term_memories = await retrieve_and_filter_memories(
        user_id,
        user_message,
        max_tokens=budget.long_term_memory_limit,
    )
    if long_term_memories:
        memory_text = "\n".join(f"- {m['content']}" for m in long_term_memories)
        messages.append(SystemMessage(content=f"以下是关于此用户的已知信息：\n{memory_text}"))

    # 3. 短期记忆（本次会话的历史）
    #    Redis 里存的是 JSON（dict），只在"出存储"这一处转成 BaseMessage；
    #    之后再写 m.get("role") / m["content"] 就是 bug
    raw_history = await get_history(session_id)
    history: list[BaseMessage] = convert_to_messages(raw_history)
    history = trim_history(history, max_tokens=budget.short_term_memory_limit)

    messages.extend(history)

    # 4. 当前用户消息
    messages.append(HumanMessage(content=user_message))

    return messages
```

**补充说明一：本文的 Redis 消息列表与第 1 章的 checkpointer 是两套真相**

第 1 章 1.2.5 已经用 `RedisSaver`（`thread_id = session_id`）把 LangGraph 的**真实消息流**（含 `tool_calls`、`tool` 结果、中断状态）持久化了；本文又用 `get_history` / `append_message_with_limit` 维护了一份 `[{role, content}]` JSON 列表。两套并存的问题：

| 问题 | 后果 |
|------|------|
| 谁是对话真源 | 出问题时两套数据不一致，排查只能靠猜 |
| 裁剪规则不一致 | 第 1 章按条数硬裁 50 条，本文按 token 裁——同一份历史在两处被两套规则改写 |
| 配对保护 | 两套都不保护 `tool_calls` / `tool` 配对（第 1 章的 `messages[-50:]` 会从中间截断） |

正确做法：

```python
# ✅ 推荐：对话状态只留 checkpointer 一份，读用 get_state，不额外手写 Redis 列表
from langgraph.checkpoint.redis import RedisSaver

config = {"configurable": {"thread_id": session_id}}   # thread_id 就是 session_id
state = await agent.aget_state(config)                 # 读回的就是真实消息流（BaseMessage 列表）

# ✅ 如果确实需要 Redis 列表（非 LangGraph 的旁路链路），裁剪也必须走 trim_messages，
#    不要用 messages[-MAX_HISTORY_LENGTH:] 这种按条数的硬裁
```

**跨会话长期记忆的一等公民是 LangGraph 的 `BaseStore`**：`InMemoryStore` / `PostgresStore` 提供带命名空间的精确 KV 读写与检索（`store.put(("user_1", "profile"), "city", {...})` / `store.search(("user_1", "profile"))`），LangGraph 1.x 里由 `store=` 注入图。本文用"自建 Milvus collection + LLM 抽取"实现语义记忆是可行的，但 profile 这类**确定值**不该由它承担（见 2.3.3 的"记忆分层"）。

**补充说明二：`append_message_with_limit` 的注释与实现不符**

第 1 章 1.2.6 里这个函数的注释写着"避免全量读取再写入的竞争问题"，但函数体正是**无锁的读改写**：

```python
# 它实际做的事情（伪代码）：
#   ① raw = await redis.get(key)        ← 读整个 JSON blob
#   ② messages.append(...)              ← 在内存里改
#   ③ await redis.setex(key, TTL, json) ← 整体写回
#
# 同 session 的两个请求并发时，后写的那个用自己那份旧快照覆盖先写的消息 ——
# "避免竞争"这个保证并不存在，丢消息是必然而非偶然。
```

```python
# ✅ 原子追加：Redis List + RPUSH（原子操作），LTRIM 控制长度上限
import json
import time
from core.cache import redis


async def append_message_atomic(session_id: str, role: str, content: str) -> None:
    """追加一条消息（原子），只保留最近 50 条"""
    key = f"session:{session_id}"
    payload = json.dumps({"role": role, "content": content, "ts": time.time()}, ensure_ascii=False)
    async with redis.pipeline(transaction=True) as pipe:
        pipe.rpush(key, payload)
        pipe.ltrim(key, -50, -1)          # 只保留最近 50 条
        pipe.expire(key, 3600 * 24)
        await pipe.execute()
```

对应的读取改成 `LRANGE key 0 -1` 逐条 `json.loads`。若需要"事件流 + 消费位点"，用 Redis Stream（`XADD` / `XREADGROUP`）比 List 更合适。**一句话：并发安全靠的是"单条原子命令"，不是把整个数据结构读出来再写回去——读改写必须加锁或换成原子结构，注释写得再对也没用。**

## 2.3 长期记忆：跨会话持久化到 Milvus

### 2.3.1 什么是"长期记忆"——Agent 视角的工程定义

长期记忆不是简单的"把对话记录存下来以后搜"。它的核心是**从对话中提取出关于用户的事实、偏好、知识，以结构化的形式持久存储，并在未来的对话中按语义相关性检索回来**。

举个例子：

```
对话 1（周一）：
  用户：我最近在学 Rust，太折磨了
  Agent：Rust 的学习曲线确实陡峭，需要帮忙吗？
  → 提取长期记忆：{"fact": "用户正在学习 Rust 语言", "category": "学习", "confidence": 0.9}

对话 2（周三）：
  用户：有没有什么推荐的编程书？
  Agent：（检索到长期记忆"用户正在学习 Rust"）
        → 推荐《The Rust Programming Language》而不是通用的《代码大全》
```

如果没有从对话 1 中提取并存储"用户正在学 Rust"这个事实，对话 2 中的 Agent 只会泛泛推荐。有了长期记忆，Agent 的回答从"通用"变成了"个性化"。

### 2.3.2 存储架构：Redis 做短期，Milvus 做长期

```
                ┌─────────────────────────────────┐
                │         用户消息到达              │
                └───────────────┬─────────────────┘
                                │
        ┌───────────────────────┼───────────────────────┐
        │                       │                       │
        ▼                       ▼                       ▼
┌───────────────┐    ┌──────────────────┐    ┌──────────────────┐
│  Redis        │    │  Milvus          │    │  LLM 调用        │
│  短期记忆      │    │  长期记忆向量库   │    │  生成回复         │
│               │    │                  │    │                  │
```

### 2.3.3 Milvus Collection 设计

```python
# core/long_memory_store.py
from pymilvus import DataType, MilvusClient

COLLECTION_NAME = "long_term_memories"
EMBED_DIM = 1536  # text-embedding-3-small 的输出维度（见 2.3.8）

# MilvusClient 是显式实例：地址、超时、鉴权都在构造参数里，
# 不再有进程级全局单例（写法对照见本节末尾）
client = MilvusClient(uri="http://localhost:19530")

# 定义 Collection Schema
# auto_id=False：主键由业务侧给出，这样才能用 upsert 做"同键覆盖"（见 2.6.2）
schema = MilvusClient.create_schema(auto_id=False, enable_dynamic_field=False)
schema.add_field(field_name="memory_key", datatype=DataType.VARCHAR, is_primary=True, max_length=128)
schema.add_field(field_name="user_id", datatype=DataType.VARCHAR, max_length=64)
schema.add_field(field_name="session_id", datatype=DataType.VARCHAR, max_length=64)
schema.add_field(field_name="content", datatype=DataType.VARCHAR, max_length=2000)
schema.add_field(field_name="subject", datatype=DataType.VARCHAR, max_length=64)
schema.add_field(field_name="category", datatype=DataType.VARCHAR, max_length=32)
schema.add_field(field_name="importance", datatype=DataType.INT64)  # 1~10，重要程度
schema.add_field(field_name="confidence", datatype=DataType.FLOAT)  # 0~1，LLM 判断的可信度
schema.add_field(field_name="vector", datatype=DataType.FLOAT_VECTOR, dim=EMBED_DIM)
schema.add_field(field_name="created_at", datatype=DataType.INT64)
schema.add_field(field_name="updated_at", datatype=DataType.INT64)
# 下面两个字段必须给 default_value：Milvus 只允许 nullable=True 或设了 default_value
# 的标量字段在插入时省略，否则报 The field "xxx" is not provided
schema.add_field(field_name="last_accessed_at", datatype=DataType.INT64, default_value=0)
schema.add_field(field_name="access_count", datatype=DataType.INT64, default_value=0)

index_params = client.prepare_index_params()
index_params.add_index(
    field_name="vector",
    index_type="IVF_FLAT",
    metric_type="IP",  # 内积；向量已归一化时等价于余弦相似度
    params={"nlist": 128},
)

if not client.has_collection(COLLECTION_NAME):
    client.create_collection(
        collection_name=COLLECTION_NAME,
        schema=schema,
        index_params=index_params,
    )

# ⚠️ load 必须放在 if 之外。
# Milvus 必须先 load 才能 search，而 load 是**有状态**的：Milvus 重启、querynode
# 被驱逐、显式 release 之后，已存在的 collection 也会回到未加载状态，search 直接报
# "collection not loaded"。如果 load 只写在"集合不存在"分支里，这段代码只有首次
# 创建时会执行 —— 上线后能跑，某天凌晨 Milvus 重启后整条长期记忆链路失效且没有恢复路径。
client.load_collection(COLLECTION_NAME)

# 检索前仍要再确认一次（load 幂等，成本可忽略），见下面的 ensure_loaded()
```

```python
# core/long_memory_store.py（续）—— 写入与删除
import asyncio


def ensure_loaded() -> None:
    """
    确保 collection 处于已加载状态。
    load 是幂等的：已加载时是空操作，未加载时才触发布段加载。
    所以最省心的写法是"每次检索前调一次"；若要显式判断，用
    client.get_load_state(collection_name=...) 读状态再按需补 load。
    """
    client.load_collection(COLLECTION_NAME)


async def upsert_memories(rows: list[dict]) -> None:
    """
    批量写入记忆：同 memory_key 覆盖，否则新增（last-write-wins）。
    注意 Milvus 的 upsert 是**整体替换**：data 里必须带齐所有非空字段，
    否则未给的字段会被写成默认值；schema 里没设 default_value 的字段漏传则直接报错。
    """
    if not rows:
        return
    await asyncio.to_thread(client.upsert, collection_name=COLLECTION_NAME, data=rows)


async def delete_memories_by_key(memory_keys: list[str]) -> None:
    """按主键删除。主键是唯一稳定的定位方式，内容字符串不是（见 2.6.2）"""
    if not memory_keys:
        return
    await asyncio.to_thread(client.delete, collection_name=COLLECTION_NAME, ids=memory_keys)
```

关键字段说明：

| 字段 | 作用 | 为什么需要 |
|------|------|-----------|
| `memory_key` | 主键，`hash(user_id + category + subject)` | 更新/删除/回写计数的**唯一定位依据**；同键 upsert 天然去重 |
| `content` | 记忆内容文本 | 检索回来后直接塞进 prompt |
| `subject` | 事实键（"居住城市"、"主力编程语言"） | 决定 `memory_key`，同一事实换措辞也不会存成两条 |
| `category` | 分类标签 | 支持按类别过滤（个人资料 / 偏好 / 知识 / 待办） |
| `importance` | 重要程度 1~10 | 检索时加权，重要记忆优先返回 |
| `confidence` | LLM 判断的可信度 0~1 | 低置信度的记忆可以忽略或降权 |
| `last_accessed_at` | 最后一次被召回的时间 | 判定"僵尸记忆"的唯一依据（见 2.6.3）；初始化为写入时间 |
| `access_count` | 被召回的总次数 | 识别"存了但从没用过"的记忆；schema 里给了 `default_value=0` |
| `updated_at` | 最后更新时间 | 同一条记忆被多次提及，更新该字段但保留最早创建时间 |

**补充说明一：pymilvus 的 ORM 写法已弃用，新代码统一用 `MilvusClient`**

旧写法（`connections.connect` / `utility.has_collection` / `Collection`）目前还能跑，但会发 `PyMilvusDeprecationWarning`，官方要求新代码统一用 `MilvusClient`：

| 旧 ORM 写法 | `MilvusClient` 写法 |
|-------------|---------------------|
| `connections.connect(host="localhost", port="19530")` | `MilvusClient(uri="http://localhost:19530")` |
| `utility.has_collection(name)` | `client.has_collection(name)` |
| `Collection(name, schema=...)` | `client.create_collection(collection_name=..., schema=..., index_params=...)` |
| `collection.create_index(field_name=..., index_params=...)` | `client.prepare_index_params()` + `add_index(...)`，随 `create_collection` 一起传 |
| `collection.load()` | `client.load_collection(name)` |
| `collection.search(data=..., anns_field=..., param=..., output_fields=...)` | `client.search(collection_name=..., data=..., anns_field=..., search_params=..., output_fields=...)` |
| `collection.insert([...])` | `client.insert(collection_name=..., data=[...])` |
| 命中结果 `hit.score` / `hit.entity.content` | 命中结果是 `dict`：`hit["distance"]` / `hit["entity"]["content"]` |
| 无对应方法 | `client.upsert(...)` / `client.query(filter=...)` / `client.delete(ids=[...])` |

**一句话：`load` 属于"查询路径"的前置条件，不属于"初始化路径"的一次性动作——把它写在创建分支里，等于赌 Milvus 永不重启。**

**补充说明二：确定性画像（profile）与语义记忆应该分成两层**

把姓名、城市、职业、偏好、事件、待办全塞进同一个向量 collection、只靠 `category` 区分，是最常见也最容易翻车的做法：

| 类型 | 典型问题 | 正确的读写方式 | 该放哪 |
|------|---------|---------------|--------|
| 画像 profile（"我叫什么""我住哪""我的职业"） | 用户说"我搬到上海了"，必须**精确覆盖**上一次的值 | 精确读 + 覆盖写（last-write-wins），按主键定位 | Redis Hash / Postgres / LangGraph `BaseStore` |
| 语义记忆（"喜欢简洁的回答""在学 Rust"） | 内容相关即可召回，允许模糊 | 向量相似度检索 | Milvus（本文这一套） |
| 情景记忆（"上周三讨论过部署方案"） | 会随时间衰减，命中率随时间下降 | 向量检索 + 时间衰减权重 | Milvus（`last_accessed_at` 参与排序） |

"用户住哪""我叫什么"这类问题要的是**确定的 KV**：查询它不该走相似度，更新它也不该走"按内容删旧插新"。用向量相似度 + 字符串匹配去维护这些值，必然出错——2.6.2 里"北京→上海"就是这个问题。工业界通行做法是**双写**：抽取到 profile 类事实时写 KV（覆盖），抽取到语义/情景类事实时写向量库（追加）；读取时 profile 直接拼进 system prompt，语义记忆走检索。

**一句话：确定性的值走 KV（精确读写覆盖），模糊的知识走向量（相似度检索）——把两者塞进同一个 collection 用 `category` 区分，等于用模糊工具干精确的活。**

### 2.3.4 核心难题：怎么让模型准确判断"什么该存入长期记忆"

这是整个系统的关键。你不能把每一句对话都存进 Milvus，否则库里 90% 是噪音——"好的""谢谢""知道了"这些毫无长期价值的对话会把真正的记忆淹没。

**方案：在每次对话结束后，让 LLM 做一次"记忆提取审查"。**

```python
# core/memory_extractor.py
import asyncio
import hashlib
import json
import time
from pydantic import BaseModel, Field
from langchain_core.messages import BaseMessage
from langchain_core.prompts import ChatPromptTemplate
from core.llm import call_llm_with_retry
from core.embedding import embed_texts
from core.long_memory_store import (
    COLLECTION_NAME, client, delete_memories_by_key, upsert_memories,
)
from core.memory_dedup import DEDUP_SIMILARITY, check_duplicates_batch
from core.token_counter import message_text
from core.logger import get_logger

logger = get_logger(__name__)


# ============ 第一步：定义记忆提取的输出结构 ============

class MemoryItem(BaseModel):
    """单条长期记忆的结构化定义"""
    content: str = Field(..., description="记忆内容。用完整句子表述，必须包含主语。例如'用户正在学习 Rust'而不是'学 Rust'")
    subject: str = Field(..., description="事实键：这条记忆描述的那个槽位，如「居住城市」「主力编程语言」「是否对芒果过敏」。同一 (user_id, category, subject) 视为同一事实，后写覆盖先写；一句话里有两个不同事实就拆成两条")
    category: str = Field(..., description="分类：personal(个人资料) / preference(偏好习惯) / knowledge(知识技能) / event(事件经历) / todo(待办事项) / other")
    importance: int = Field(..., ge=1, le=10, description="重要程度。10=核心身份信息，1=可能有用但不确定")
    confidence: float = Field(..., ge=0.0, le=1.0, description="可信度。1.0=用户明确说出的事实，0.5=从上下文推断的")


class MemoryExtractionResult(BaseModel):
    """记忆提取的完整结果"""
    # 新增或覆盖：后端按 (user_id, category, subject) 算出 memory_key 后 upsert，
    # 同一槽位的旧值被这条覆盖 —— 不需要 LLM 再复述一遍旧内容（见 2.6.2）
    new_memories: list[MemoryItem] = Field(default_factory=list)
    # 删除只认主键：LLM 复述的旧内容不可能与库里原文逐字一致，
    # 按内容匹配的删除会静默失败；memory_key 从检索结果里带给 LLM（见 2.3.7）
    delete_ids: list[str] = Field(
        default_factory=list,
        description="要删除的记忆 memory_key（必须取自'已有的长期记忆'列表里给出的键）",
    )
    notes: str = Field(default="", description="提取推理说明")


# ============ 第二步：构造记忆提取的 prompt ============

MEMORY_EXTRACTION_PROMPT = ChatPromptTemplate.from_messages([
    ("system", """你是一个记忆提取系统。你的任务是从对话中提取关于用户的长期记忆。

## 什么是值得存入长期记忆的信息：
1. **个人资料**：姓名、年龄、职业、所在地、家庭成员、联系方式
2. **偏好习惯**：喜欢/讨厌什么、沟通风格偏好（简洁/详细）、常用语言
3. **知识技能**：掌握的技术、学习进度、专业领域
4. **事件经历**：做过的事、去过的地方、重要日期
5. **待办事项**：用户提到的计划、承诺、截止日期

## 什么不应该存入长期记忆：
- 一次性的简单问答（"今天天气怎么样"——这是每次都要查的，不是记忆）
- 闲聊寒暄（"你好""谢谢""再见"）
- 纯粹的知识性内容（"Python 是什么"——这是知识库的事，不是用户记忆）
- 临时的会话状态（"刚才我说了A"——短期记忆就够了）
- 模糊不确定的推断（不确定就不要存）

## 记忆更新规则：
- 用户**补充**了新事实（不与已有记忆矛盾）：作为 new_memories 输出，subject 用新槽位
- 用户**改口/覆盖**了已有事实（"我搬到上海了"）：同样作为 new_memories 输出，
  **subject 必须与那条旧记忆一致**，系统会按同一个 memory_key 覆盖旧值
- 用户**明确否认**之前的信息（"不对，我不是..."）：把对应记忆的 memory_key 放进 delete_ids
- 不要复述旧内容来做"匹配"——下面的 memory_key 才是唯一可靠的定位方式

## 已有的长期记忆（每条都带 memory_key；要删除时直接引用这个键）：
{existing_memories}

## 重要程度评分标准：
- 10：核心身份信息（姓名、职业、重要关系）
- 7-9：重要偏好和习惯、正在学习的关键技能
- 4-6：有价值的参考信息、一般事件
- 1-3：边缘信息、可能有用但不重要

## 输出要求：
只输出 JSON，不要任何解释文字。严格遵循以下格式：

{{
  "new_memories": [
    {{"content": "用户正在学习 Rust", "subject": "正在学习的语言",
      "category": "knowledge", "importance": 7, "confidence": 0.9}}
  ],
  "delete_ids": [],
  "notes": ""
}}

字段约束：
- subject：必填。写"这条记忆描述的那个槽位"（如「居住城市」「主力编程语言」），
  只写槽位名，不要写值；同一槽位的旧值会被自动覆盖
- delete_ids：只能填上面"已有的长期记忆"里出现过的 memory_key，不要自己编造
- 没有任何值得记录的信息时，返回 {{"new_memories": [], "delete_ids": [], "notes": ""}}
"""),
    ("user", """请分析以下对话，提取值得存入长期记忆的信息。

对话内容：
{dialogue}
"""),
])


# ============ 第三步：执行记忆提取 ============

async def extract_long_term_memories(
    session_id: str,
    dialogue: list[BaseMessage],
    existing_memories: list[dict],  # [{"memory_key": "...", "content": "..."}]，来自 2.3.7 的检索
) -> MemoryExtractionResult:
    """
    从对话中提取长期记忆。

    每次对话结束后调用此函数，让 LLM 判断对话中是否有值得长期记住的信息。
    """
    dialogue_text = "\n".join(
        f"{m.type}: {message_text(m)}" for m in dialogue[-10:]  # 只要最近 10 条
    )

    # 主键必须交给 LLM，否则它只能靠"内容"描述要删哪条，而它复述不准
    existing_text = "\n".join(
        f"- [{m['memory_key']}] {m['content']}" for m in existing_memories
    ) or "（暂无已有记忆）"

    prompt = MEMORY_EXTRACTION_PROMPT.format_messages(
        existing_memories=existing_text,
        dialogue=dialogue_text,
    )

    try:
        # 用一个小模型做记忆提取，省成本
        response = await call_llm_with_retry(
            messages=prompt,
            model="gpt-5-mini",  # 记忆提取不需要大模型，5-mini 足够
            response_format={"type": "json_object"},  # 强制 JSON 输出
        )

        result = MemoryExtractionResult(**json.loads(response))

        if result.new_memories or result.delete_ids:
            logger.info(
                "记忆提取完成 | session_id=%s | upsert=%d | delete=%d",
                session_id,
                len(result.new_memories),
                len(result.delete_ids),
            )
        else:
            logger.debug("本轮对话无新的长期记忆 | session_id=%s", session_id)

        return result

    except Exception as e:
        logger.warning("记忆提取失败 | session_id=%s | error=%s", session_id, str(e))
        return MemoryExtractionResult()  # 提取失败不阻塞对话，返回空


# ============ 第四步：将提取的记忆批量写入 Milvus ============

def memory_key_of(user_id: str, category: str, subject: str) -> str:
    """
    稳定业务键：同一 user 的同一 category + 同一 subject 视为同一事实。
    用它做 Milvus 主键，写入就是 upsert（同键覆盖），
    不再需要"按内容查出旧记录 → 删掉 → 插入新的"这条必然出错的链路。
    """
    raw = f"{user_id}|{category}|{subject.strip().lower()}"
    return hashlib.sha256(raw.encode("utf-8")).hexdigest()[:32]


async def _preserve_existing_stats(rows: list[dict]) -> list[dict]:
    """
    upsert 是整体替换：先把旧行的 created_at / access_count / last_accessed_at 取回来合并，
    否则用户改口一次，这条记忆的创建时间被刷新、访问统计归零，"僵尸记忆"判定就废了。
    """
    keys = [row["memory_key"] for row in rows]
    if not keys:
        return rows
    old_rows = await asyncio.to_thread(
        client.query,
        collection_name=COLLECTION_NAME,
        filter=f"memory_key in {json.dumps(keys, ensure_ascii=False)}",
        output_fields=["memory_key", "created_at", "access_count", "last_accessed_at"],
    )
    old_by_key = {row["memory_key"]: row for row in old_rows}
    for row in rows:
        old = old_by_key.get(row["memory_key"])
        if old:
            row["created_at"] = old["created_at"]
            row["access_count"] = old["access_count"]
            row["last_accessed_at"] = old["last_accessed_at"]
    return rows


async def persist_memories(
    session_id: str,
    user_id: str,
    extraction_result: MemoryExtractionResult,
) -> None:
    """
    将 LLM 提取的记忆批量写入 Milvus。

    写放大是记忆系统最容易踩的坑：一次提取 8 条记忆，如果每条单独请求 embedding、
    单独 insert，就是 8 次 HTTP 往返 + 8 次写。
    正确做法：一次 embed（OpenAI 的 input 支持字符串数组）+ 一次 upsert。
    """
    now = int(time.time())
    items = extraction_result.new_memories

    # 1. 一次请求拿到全部向量（返回顺序与输入顺序一致）
    embeddings = await embed_texts([m.content for m in items])

    # 2. 组装行：字段名与 schema 一一对应，非空标量字段一个都不能漏
    rows = [
        {
            "memory_key": memory_key_of(user_id, memory.category, memory.subject),
            "user_id": user_id,
            "session_id": session_id,
            "content": memory.content,
            "subject": memory.subject,
            "category": memory.category,
            "importance": memory.importance,
            "confidence": memory.confidence,
            "vector": embedding,
            "created_at": now,
            "updated_at": now,
            "access_count": 0,        # 显式给值（schema 里也设了 default_value=0）
            "last_accessed_at": now,  # 初始化为写入时间，"90 天未访问"才有的算（见 2.6.3）
        }
        for memory, embedding in zip(items, embeddings)
    ]

    # 3. 语义去重的第二道网（见 2.6.1）：业务键覆盖不到"同一事实换了 subject 措辞"
    if rows:
        duplicates = await check_duplicates_batch(
            user_id,
            [row["content"] for row in rows],
            threshold=DEDUP_SIMILARITY,
        )
        rows = [row for row, dup in zip(rows, duplicates) if not dup]

    # 4. 落库：同 memory_key 覆盖（用户改口 → 旧值被替换），不同键则是新增
    if rows:
        await _preserve_existing_stats(rows)
        await upsert_memories(rows)
        logger.info("记忆写入 | session_id=%s | upsert=%d", session_id, len(rows))

    # 5. 删除只按主键，不做内容匹配
    if extraction_result.delete_ids:
        await delete_memories_by_key(extraction_result.delete_ids)
        logger.info("记忆删除 | session_id=%s | ids=%s", session_id, extraction_result.delete_ids)
```

```python
from pydantic import ValidationError

try:
    raw = json.loads(response)

except (json.JSONDecodeError, ValidationError) as e:
```

### 2.3.6 调用时机：什么时候触发记忆提取

**不要在同步的请求-响应链路中做记忆提取。** 因为：
- LLM 调用需要 1~3 秒，会拖慢用户感知的回复速度
- 记忆提取失败了也不应该影响正常对话

**正确做法：对话返回给用户后，异步后台执行；并且先用轻量门控筛掉不值得提取的轮次。**

```python
import asyncio
import re
from langchain_core.messages import AIMessage, HumanMessage
from core.memory_extractor import extract_long_term_memories, persist_memories
from core.long_memory_store import search_similar_memories

# 后台任务集合：保存 create_task 的引用，防止任务被 GC 回收（完成后自动清理）
_background_tasks: set[asyncio.Task] = set()

# 轻量门控：每轮对话都跑一次 LLM 提取，等于每轮把 token 成本翻一倍。
# 先用规则（寒暄/纯查询/太短）筛掉大部分轮次，再用小模型做二次判断。
_TRIVIAL = re.compile(r"^(好的|谢谢|嗯|收到|再见|ok|thanks?)[!。.~]*$", re.IGNORECASE)


def should_extract(user_message: str) -> bool:
    """规则门控：明显不携带长期信息的轮次直接跳过提取"""
    text = user_message.strip()
    if len(text) < 6 or _TRIVIAL.match(text):
        return False
    # 更省成本也更准的做法：再加一个小模型（gpt-5-mini + 二分类 prompt）做二次判断
    return True


# routes/chat.py 中的调用方式
@router.post("/completions")
async def chat_completions(request: ChatRequest):
    # 1. 正常处理对话（快速返回给用户）
    reply = await process_chat(request)

    # 2. 异步后台提取记忆（不阻塞返回）
    task = asyncio.create_task(_extract_memories_background(request.session_id, request.user_id, request.message, reply))
    _background_tasks.add(task)                        # 保存引用，防止被 GC 回收
    task.add_done_callback(_background_tasks.discard)  # 完成后自动清理

    return reply


async def _extract_memories_background(
    session_id: str,
    user_id: str,
    user_message: str,
    assistant_reply: str,
) -> None:
    """后台任务：从本轮对话中提取长期记忆"""
    try:
        if not should_extract(user_message):
            logger.debug("门控跳过记忆提取 | session_id=%s", session_id)
            return

        # 查询已有记忆：返回值里带 memory_key，交给 LLM 做"改口覆盖 / 否认删除"的定位
        existing = await search_similar_memories(
            user_id=user_id,
            query_text=user_message,
            top_k=10,
        )

        # 提取新记忆（进程内一律 BaseMessage）
        dialogue = [
            HumanMessage(content=user_message),
            AIMessage(content=assistant_reply),
        ]
        result = await extract_long_term_memories(session_id, dialogue, existing)

        # 持久化
        if result.new_memories or result.delete_ids:
            await persist_memories(session_id, user_id, result)

    except Exception as e:
        logger.exception("后台记忆提取失败 | session_id=%s | error=%s", session_id, str(e))
```

### 2.3.7 长期记忆的检索：语义相似度查询

```python
# core/long_memory_store.py（续）—— 检索
import asyncio
from core.cache import redis  # core/cache.py 导出的全局 Redis 客户端（见 1.3.7）
from core.embedding import embed_text

# 访问计数先落在 Redis 计数器里，由 2.6.3 的定时任务批量回写 Milvus
ACCESS_COUNTER_KEY = "memory:access_counter"


async def search_similar_memories(
    user_id: str,
    query_text: str,
    top_k: int = 5,
    min_similarity: float | None = None,  # 不设默认值：阈值必须在目标语料上标定（见本节末尾）
) -> list[dict]:
    """
    根据当前对话内容，检索最相关的长期记忆。

    检索过程：
    1. 将当前用户消息转为 embedding 向量
    2. 在 Milvus 中搜索最相似的记忆
    3. 过滤掉相似度过低的结果
    4. 按 importance × similarity 加权排序
    """
    # Milvus 必须先 load 才能 search。load 幂等，每次检索前确认一次最省心——
    # 不要依赖"建 collection 时 load 过"这个假设（重启/驱逐就会失效）
    await asyncio.to_thread(ensure_loaded)

    # 1. 生成查询向量
    query_embedding = await embed_text(query_text)

    # 2. 向量相似度搜索
    #    同步 pymilvus 调用会阻塞事件循环，用 asyncio.to_thread 放到线程池执行
    results = await asyncio.to_thread(
        client.search,
        collection_name=COLLECTION_NAME,
        data=[query_embedding],
        anns_field="vector",
        search_params={"metric_type": "IP", "params": {"nprobe": 16}},
        limit=top_k * 2,  # 多取一些，后面再过滤
        filter=f'user_id == "{user_id}"',  # 只搜当前用户
        # 主键必须返回：上层要把它交给 LLM 做覆盖/删除的定位（见 2.3.4、2.6.2）
        output_fields=["memory_key", "content", "subject", "category", "importance", "confidence"],
    )

    # 3. 过滤 + 加权
    scored_memories = []
    for hit in results[0]:
        similarity = hit["distance"]  # MilvusClient 返回 dict；旧 ORM 写法是 hit.score
        if min_similarity is not None and similarity < min_similarity:
            continue

        entity = hit["entity"]
        # 加权 = 相似度(0.7) + 重要程度(0.2) + 可信度(0.1)
        weighted_score = (
            similarity * 0.7 +
            (entity["importance"] / 10) * 0.2 +
            entity["confidence"] * 0.1
        )

        scored_memories.append({
            "memory_key": entity["memory_key"],  # ← 主键：更新/删除/回写计数的定位依据
            "content": entity["content"],
            "subject": entity["subject"],
            "category": entity["category"],
            "importance": entity["importance"],
            "confidence": entity["confidence"],
            "similarity": similarity,
            "weighted_score": weighted_score,
        })

    # 按加权分数降序
    scored_memories.sort(key=lambda x: x["weighted_score"], reverse=True)
    selected = scored_memories[:top_k]

    # 4. 访问计数不在检索链路上打 Milvus：
    #    每次召回都 update 一次是纯写放大（召回频率远高于写入频率），
    #    先在 Redis 里累加，由定时任务批量回写 access_count / last_accessed_at（见 2.6.3）
    if selected:
        async with redis.pipeline(transaction=False) as pipe:
            for mem in selected:
                pipe.hincrby(ACCESS_COUNTER_KEY, mem["memory_key"], 1)
            pipe.expire(ACCESS_COUNTER_KEY, 3600 * 24 * 7)
            await pipe.execute()

    logger.debug("长期记忆检索 | query=%s | found=%d", query_text[:50], len(selected))
    return selected
```

**阈值不是常数——`min_similarity` 必须自己在语料上标定**

| 阈值口径 | 出现在 | 判的是什么 | 能否互相套用 |
|---------|-------|-----------|-------------|
| 原始相似度 `min_similarity` | 2.3.7 | Milvus 直接返回的 `hit["distance"]`（IP 内积） | ❌ |
| 加权分 `MIN_WEIGHTED_SCORE` | 2.4.2 | `sim*0.7 + imp*0.2 + conf*0.1` | ❌ |
| 去重相似度 `DEDUP_SIMILARITY` | 2.6.1 | 原始相似度，但判的是"是否同一事实" | ❌ |

三个数写着差不多的数值，量纲和语义却完全不同。更关键的是：**`text-embedding-3-small` 上"语义相关但用词不同"的句对，相似度常落在 0.4~0.7，把 0.7 当默认阈值会大量误滤掉本应召回的长期记忆**，而误滤是静默的（日志里只看到 found 变少）。

标定方法（上线前必须做一次）：

1. 从真实语料里抽 200~500 条 (query, 记忆) 对，人工标注"是否应该召回"；
2. 跑全量打分，画相似度 → 召回率/精确率曲线；
3. 按业务取舍取工作点（记忆召回宁可多带几条，通常取召回率 ≥ 0.9 对应的最低阈值）；
4. 把标定结果写成配置项，**不要写死在函数签名里**；
5. 换 embedding 模型（small → large、换 bge-m3 等）后相似度分布整体平移，必须重标。

**一句话：任何写死在代码里的相似度阈值都只是占位符——它必须来自标注集上的标定，且换模型后重标。**

### 2.3.8 embedding 模型的选择

```python
# core/embedding.py
from openai import AsyncOpenAI
from core.config import OPENAI_API_KEY, OPENAI_BASE_URL

client = AsyncOpenAI(api_key=OPENAI_API_KEY, base_url=OPENAI_BASE_URL)


async def embed_text(text: str, model: str = "text-embedding-3-small") -> list[float]:
    """
    将文本转为 embedding 向量。

    text-embedding-3-small：
    - 维度：1536
    - 价格：$0.02/1M token（极便宜）
    - 性能：中英文语义检索效果良好
    - 推荐使用场景：长期记忆、文档切片等大量文本的向量化

    text-embedding-3-large（备选）：
    - 维度：3072（或降到 1024 用）
    - 价格：$0.13/1M token
    - 检索精度更高，适合对精度要求极高的场景
    - 注意：small 与 large 均支持多语言；跨语言检索效果差应从 query 改写/术语统一入手，而非换 embedding 模型
    """
    response = await client.embeddings.create(
        model=model,
        input=text,
    )
    return response.data[0].embedding


async def embed_texts(texts: list[str], model: str = "text-embedding-3-small") -> list[list[float]]:
    """
    批量 embedding：input 传数组，一次 HTTP 往返拿回 N 个向量，
    返回顺序与输入顺序一致。写入路径必须用这个版本（见 2.3.4）——
    N 条记忆逐个 embed 就是把一次网络往返拆成 N 次。
    """
    if not texts:
        return []
    response = await client.embeddings.create(
        model=model,
        input=texts,   # ← 数组，不是循环
    )
    return [item.embedding for item in response.data]
```

## 2.4 上下文爆炸问题

### 2.4.1 "上下文爆炸"是什么意思

Agent 每次对话需要把以下内容塞进 prompt：

```
┌──────────────────────────────────────────┐
│ 系统提示词                                │  ~200 token
│ 长期记忆（检索到的）                       │  ~500 token（正常）
│ 短期记忆（会话历史）                       │  ~2000 token（正常）
│ 工具定义                                  │  ~300 token
│ 当前用户消息                              │  ~100 token
│                                          │
│ 合计                                      │  ~3100 token ✅ 很健康
└──────────────────────────────────────────┘
```

但如果：
- 长期记忆检索了 20 条（4000 token）
- 用户连续聊了 100 轮（10000 token）
- 工具定义复杂（1000 token）

```
┌──────────────────────────────────────────┐
│ 系统提示词                                │  ~200 token
│ 长期记忆（20条，未过滤）                   │  ~4000 token
│ 短期记忆（100轮历史）                      │  ~10000 token
│ 工具定义                                  │  ~1000 token
│ 当前用户消息                              │  ~100 token
│                                          │
│ 合计                                      │  ~15300 token ⚠️ 逼近上限
└──────────────────────────────────────────┘
```

这就是上下文爆炸——太多信息塞进 prompt，导致：
1. **超出模型上下文窗口** → API 直接报错
2. **注意力稀释** → 模型忽略关键信息
3. **成本飙升** → 每轮对话都在为无用的历史 token 付费
4. **延迟增加** → prompt 越长，首 token 越慢

### 2.4.2 爆炸源一：长期记忆检索过多

**解法：严格控制检索数量 + 相似度阈值**

```python
# ❌ 检索 20 条全塞进去
memories = await search_similar_memories(user_id, query, top_k=20)

# ✅ 分层过滤，只保留高价值的
from core.token_counter import count_tokens

MAX_LTM_TOKENS = 800       # 长期记忆最多占 800 token（预算份额，生产由 ContextBudget 下发）
MIN_SIMILARITY = 0.65      # 原始相似度阈值：占位值，必须按语料标定（见 2.3.7 末尾）
MIN_WEIGHTED_SCORE = 0.65  # 加权分阈值：与上面口径不同，不能互相套用
KEEP_HIGH_IMPORTANCE = 3   # 高重要度记忆的兜底补位条数


async def retrieve_and_filter_memories(
    user_id: str,
    query_text: str,
    max_tokens: int = MAX_LTM_TOKENS,
) -> list[dict]:
    """检索长期记忆并做严格过滤"""
    # 第一步：候选检索
    candidates = await search_similar_memories(
        user_id=user_id,
        query_text=query_text,
        top_k=15,
        min_similarity=MIN_SIMILARITY,
    )

    # 第二步：按加权分排序，逐个加入，直到接近 token 上限
    selected = []
    token_count = 0
    for mem in candidates:
        if mem["weighted_score"] < MIN_WEIGHTED_SCORE:
            continue

        mem_tokens = count_tokens(mem["content"])   # 与裁剪、预算共用同一个 tokenizer
        if token_count + mem_tokens > max_tokens:
            break

        selected.append(mem)
        token_count += mem_tokens

    # 第三步：如果高重要度记忆被遗漏，提升它们（仍受 token 预算约束）
    high_importance = [m for m in candidates if m["importance"] >= 8 and m not in selected]
    for mem in high_importance[:KEEP_HIGH_IMPORTANCE]:
        mem_tokens = count_tokens(mem["content"])
        if token_count + mem_tokens > max_tokens:
            break  # 超出预算则不再追加，避免突破 token 上限
        selected.append(mem)
        token_count += mem_tokens

    return selected
```

注意 `MIN_WEIGHTED_SCORE` 判的是加权分，不是原始相似度：**`MIN_SIMILARITY = 0.65` 与 `MIN_WEIGHTED_SCORE = 0.65` 写着同一个数字，量纲却不同**。加权分里有 30% 来自 `importance` 和 `confidence`——一条 `importance=10`、`confidence=1.0` 的记忆，即使相似度只有 0.5，加权分也有 `0.5*0.7 + 1.0*0.2 + 1.0*0.1 = 0.65` 刚好过线。两个阈值必须各自标定（方法见 2.3.7 末尾），不能因为数字一样就以为其中一个可以省掉。

### 2.4.3 爆炸源二：短期历史过长

**解法：滚动摘要——把旧对话压缩为摘要，保留最近对话的完整内容。**

```python
# core/context_compressor.py
import json
from langchain_core.messages import BaseMessage, SystemMessage
from core.cache import redis
from core.llm import call_llm_with_retry
from core.token_counter import clip_to_tokens, count_tokens, message_text
from core.logger import get_logger

logger = get_logger(__name__)

SUMMARY_PREFIX = "[历史对话摘要]"


def _summary_key(session_id: str) -> str:
    """摘要与游标的持久化位置（按 session 隔离）"""
    return f"session_summary:{session_id}"


async def compress_conversation(
    session_id: str,             # 摘要 + 游标按 session 持久化，必须传进来
    messages: list[BaseMessage],
    keep_recent: int = 6,        # 保留最近 N 条完整消息
    max_summary_tokens: int = 500,   # 摘要自身的 token 上限，会真的生效
) -> list[BaseMessage]:
    """
    滚动摘要压缩：旧消息 → 摘要 + 最近消息保持完整。

    结果：
    [
        SystemMessage("[历史对话摘要] 用户询问了天气..."),
        HumanMessage("最近的第 3 轮消息"),      ← 完整保留
        AIMessage("最近的第 2 轮消息"),          ← 完整保留
        HumanMessage("最新消息"),                ← 完整保留
    ]

    四个必须做对的地方（做错任意一个，压缩就会变成"每轮重复烧钱"）：
    1. 摘要是**增量**的：Redis 里存 {summary, summarized_count} 游标，
       只摘要"游标之后、keep_recent 之前"的新增旧消息，已摘要过的部分送一次就够；
    2. 摘要是**持久化**的：结果写回 Redis —— 不写回，同一批旧消息每来一个请求
       就被重新摘要一次（O(n) 次 LLM 调用，且永远收敛不了）；
    3. 摘要**可再压缩**：旧摘要与新对话一起送给 LLM 合并成一份新摘要，
       不要每轮追加一条新的 system 摘要 —— 那样摘要是只增不减的；
    4. 送进 LLM 的原文**不预截断**：先 `content[:200]` 再摘要，等于压缩前就把
       关键信息丢了，摘要再准也补不回来。
    """
    if len(messages) <= keep_recent:
        return messages

    recent = messages[-keep_recent:]
    old = messages[:-keep_recent]

    # 读回上一轮的状态：已有摘要 + 已摘要到第几条（游标）
    state = json.loads(await redis.get(_summary_key(session_id)) or "{}")
    prev_summary: str = state.get("summary", "")
    summarized_count: int = int(state.get("summarized_count", 0))

    fresh = old[summarized_count:]   # 只有这部分是"还没进过摘要"的旧消息
    if not fresh:
        if prev_summary:
            return [SystemMessage(content=f"{SUMMARY_PREFIX} {prev_summary}")] + recent
        return messages

    # 生成/合并摘要（不预截断）
    dialogue_text = "\n".join(f"{m.type}: {message_text(m)}" for m in fresh)

    summary_prompt = [
        {"role": "system", "content": (
            f"用不超过 {max_summary_tokens} token 总结下面这段对话的关键信息。"
            "只记录事实和决定，不记录寒暄。"
            "保留用户提到的所有人名、数字、日期、承诺和偏好。"
            "如果给出了已有摘要，请把它与新对话合并成一份完整的新摘要，不要丢掉旧摘要里的信息。"
        )},
        {"role": "user", "content": (
            f"已有摘要：\n{prev_summary or '（无）'}\n\n新增对话：\n{dialogue_text}"
        )},
    ]

    try:
        summary = await call_llm_with_retry(
            messages=summary_prompt,
            model="gpt-5-mini",
        )
    except Exception:
        logger.warning("对话压缩失败 | session_id=%s", session_id)
        if prev_summary:
            # 已有摘要仍然有效：用它 + 最近完整消息，不丢上一轮已经压好的信息
            return [SystemMessage(content=f"{SUMMARY_PREFIX} {prev_summary}")] + recent
        return messages  # 连摘要都没有：原样返回，交给上游的预算/裁剪逻辑处理

    # 参数要真的生效：LLM 不保证遵守"不超过 N token"，超了就硬裁
    summary = clip_to_tokens(summary, max_summary_tokens)
    logger.info(
        "对话压缩完成 | session_id=%s | 本次摘要 %d 条 → %d token",
        session_id, len(fresh), count_tokens(summary),
    )

    # 持久化：摘要 + 游标一起写回，下一轮才知道"已经摘要到哪"
    await redis.setex(
        _summary_key(session_id),
        3600 * 24,
        json.dumps({"summary": summary, "summarized_count": len(old)}, ensure_ascii=False),
    )

    # 组装结果：摘要固定在前，再是最近完整消息
    return [SystemMessage(content=f"{SUMMARY_PREFIX} {summary}")] + recent
```

**对比：四个缺陷各自会造成什么**

| 缺陷 | 表现 | 后果 |
|------|------|------|
| `max_summary_tokens` 从未被使用（prompt 里写死"不超过 200 字"） | 调用方传 500、传 46000 都没区别 | 参数是假的，无法按预算调节摘要长度 |
| 摘要前先 `content[:200]` 截断 | 长消息的关键数字/承诺在压缩前就丢了 | 摘要系统性丢失长消息信息 |
| 摘要以 system 消息追加、下一轮只处理非 system 消息 | 每轮新增一条摘要，旧摘要再也不进压缩 | 摘要只增不减，最后自己变成"上下文爆炸"源 |
| 压缩结果不写回 Redis | 同一批旧消息每次请求都被重新摘要 | 每轮多一次恒定 LLM 调用，token 花费随 QPS 放大 |

**一句话：滚动摘要不是"每次请求压缩一次历史"，而是"把历史压成一份可增量更新的状态"——状态必须持久化、必须带游标、必须能自我合并，否则它比不压缩更贵。**

### 2.4.4 爆炸源三：工具定义的描述过长

工具定义的描述（docstring）会被转成 function calling 的 schema 发给 LLM。如果每个工具的 docstring 都是一个小作文，10 个工具就能吃掉 2000 token。

**解法：工具描述只写"做什么"和"参数含义"，不写"怎么做"。**

```python
from langchain_core.tools import tool

# ❌ 工具描述过于冗长

    （此处省略 200 字背景介绍）

    1. 当用户询问公司政策时
    2. 当用户询问技术文档时
    ...（此处省略 150 字使用场景）

    - 查询字符串不要超过 500 字符
    ...（此处省略 100 字注意事项）
    """

    """搜索公司内部文档。query: 搜索关键词；top_k: 返回结果数。"""
    ...
```

**经验值：每个工具的描述控制在 80 个中文字以内。** LLM 不需要知道工具的内部实现，只需要知道"什么时候用这个工具"和"传什么参数"。

### 2.4.5 终极方案：上下文预算管理系统

把上述各种策略整合为一个统一的上下文预算管理器：

```python
# core/context_budget.py
from dataclasses import dataclass, field
from langchain_core.messages import (
    BaseMessage, HumanMessage, SystemMessage, convert_to_messages,
)
from core.session import get_history
from core.context_compressor import compress_conversation
from core.token_counter import count_message_tokens
from core.logger import get_logger

logger = get_logger(__name__)


@dataclass
class ContextBudget:
    """
    上下文预算管理器。

    每条请求的总 token 预算 = 模型上下文窗口 - 回复预留空间。
    各组件按优先级分配 token 份额。
    """
    model_max_tokens: int = 128000       # 模型最大上下文
    response_reserve: int = 4096          # 留给模型回复的 token
    total_budget: int = field(init=False)

    # 各组件份额分配（总预算 = total_budget）
    system_prompt_share: float = 0.05     # 系统提示词：5%
    long_term_memory_share: float = 0.10  # 长期记忆：10%
    short_term_memory_share: float = 0.75 # 短期记忆：75%（大头）
    tool_def_share: float = 0.05          # 工具定义：5%
    current_message_share: float = 0.05   # 当前消息：5%

    def __post_init__(self):
        self.total_budget = self.model_max_tokens - self.response_reserve

    @property
    def long_term_memory_limit(self) -> int:
        return int(self.total_budget * self.long_term_memory_share)

    @property
    def short_term_memory_limit(self) -> int:
        return int(self.total_budget * self.short_term_memory_share)


# 使用示例
budget = ContextBudget(model_max_tokens=128000)

# 摘要自身的上限：摘要的价值就在于"够短才值得留下"。
# 传 short_term_memory_limit // 2（≈46000）等于没有上限——压完还是超预算，
# 下一轮继续压，LLM 调用费白花。
SUMMARY_MAX_TOKENS = 800
KEEP_RECENT = 6


async def build_context(request, budget: ContextBudget) -> list[BaseMessage]:
    """在预算约束下组装上下文（进程内一律 BaseMessage）"""
    messages: list[BaseMessage] = []

    # 1. 系统提示词（固定，通常不超预算）
    messages.append(SystemMessage(content=SYSTEM_PROMPT))

    # 2. 长期记忆（预算：10%）
    memories = await retrieve_and_filter_memories(
        request.user_id,
        request.message,
        max_tokens=budget.long_term_memory_limit,
    )
    if memories:
        memory_text = "\n".join(f"- {m['content']}" for m in memories)
        messages.append(SystemMessage(content=f"以下是关于此用户的已知信息：\n{memory_text}"))

    # 3. 短期记忆（预算：75%，但需要压缩）
    history = convert_to_messages(await get_history(request.session_id))

    # 如果历史 token 超预算，触发压缩
    history_tokens = count_message_tokens(history)
    if history_tokens > budget.short_term_memory_limit:
        logger.info("历史过长触发压缩 | before=%d tokens", history_tokens)
        history = await compress_conversation(
            request.session_id,                      # 摘要与游标按 session 持久化（见 2.4.3）
            history,
            keep_recent=KEEP_RECENT,
            max_summary_tokens=SUMMARY_MAX_TOKENS,   # ← 参数真的会被用上
        )
        logger.info("压缩后 | after=%d tokens", count_message_tokens(history))

    messages.extend(history)

    # 4. 当前消息
    messages.append(HumanMessage(content=request.message))

    total = count_message_tokens(messages)
    logger.info("上下文组装完成 | total_tokens=%d / budget=%d", total, budget.total_budget)

    return messages
```

**这份预算与 2.2.2 的 `MAX_TOTAL_TOKENS = 8000` 是什么关系**：8000 只是 `trim_history` 的默认参数（一个宽松的占位值），本节的 `budget.short_term_memory_limit = (128000 − 4096) × 0.75 ≈ 92928` 才是生产口径。二者不该同时生效——生产代码统一写成 `trim_history(history, max_tokens=budget.short_term_memory_limit)`，`MAX_TOTAL_TOKENS` 只在单元测试里当默认值用。**一句话：预算只有一个来源（模型窗口 − 回复预留），任何"函数体内写死的上限"都必须是它的下游，而不是与它并列的第二个真相。**

## 2.6 长期记忆的维护：去重、更新、遗忘

### 2.6.1 去重：避免"用户喜欢 Python"存了 20 条

"同一条记忆存了 20 遍"有两个来源，用两道防线分别处理：

| 来源 | 表现 | 防线 |
|------|------|------|
| 同一事实被反复提及 | "用户喜欢 Python" 每轮都提取一次 | 业务键 upsert（`user_id + category + subject` 同键覆盖，见 2.3.4） |
| 同一事实换了措辞 | "用户喜欢 Python" / "用户偏好 Python 而不是 Java" | 语义去重（下面的批量查重） |

```python
# core/memory_dedup.py
import asyncio
from core.embedding import embed_texts
from core.long_memory_store import COLLECTION_NAME, client, ensure_loaded
from core.logger import get_logger

logger = get_logger(__name__)

# ⚠️ 占位值，不是可直接使用的经验值：必须按语料标定（方法见 2.3.7 末尾）
DEDUP_SIMILARITY = 0.92


async def check_duplicates_batch(
    user_id: str,
    contents: list[str],
    threshold: float = DEDUP_SIMILARITY,
) -> list[bool]:
    """
    批量查重：一次 embed（input 传数组）+ 一次 search（data 传数组），
    返回与 contents 等长的布尔列表，True 表示库里已有高度相似的记忆。
    这个函数被 2.3.4 的 persist_memories 调用；写成批量的原因是：
    单条一个 AnnSearch 会把"写 N 条记忆"变成 N 次查询（写放大）。
    """
    if not contents:
        return []

    vectors = await embed_texts(contents)
    await asyncio.to_thread(ensure_loaded)
    results = await asyncio.to_thread(
        client.search,
        collection_name=COLLECTION_NAME,
        data=vectors,
        anns_field="vector",
        search_params={"metric_type": "IP", "params": {"nprobe": 16}},
        limit=1,
        filter=f'user_id == "{user_id}"',
        output_fields=["memory_key", "content"],
    )

    flags: list[bool] = []
    for hits in results:
        duplicate = bool(hits) and hits[0]["distance"] >= threshold
        flags.append(duplicate)
        if duplicate:
            logger.info(
                "命中重复记忆，跳过写入 | user_id=%s | existing=%s",
                user_id, hits[0]["entity"]["content"][:40],
            )
    return flags
```

### 2.6.2 更新：用户改口了，旧记忆要覆盖

用户说"我住在北京"→ 存了 → 三个月后说"我搬到上海了"→ 需要覆盖而非新增。

LLM 在记忆提取阶段就会判断是否矛盾（见 prompt 中的"记忆更新规则"），但**它输出的不是"旧内容字符串"，而是新事实**；覆盖由服务端的业务键完成：

```python
# ✅ 覆盖写：subject 相同 → memory_key 相同 → upsert 直接替换旧行
#    "用户住北京" → memory_key_of(user, personal, "居住城市") = a1b2...
#    "用户住上海" → memory_key_of(user, personal, "居住城市") = a1b2...   ← 同一个键
#    写入逻辑就是 2.3.4 的 persist_memories，不需要额外写一个 update 分支
```

| 做法 | 依赖什么定位 | 失败场景 |
|------|-------------|---------|
| 按 `old_content` 精确匹配后删除 | LLM 复述的字符串与库中原文**逐字一致** | 标点、主语、语序任意一处不同就匹配不到 → 删不掉（静默失败），库里同时存在"住北京"和"住上海" |
| 按检索结果里的主键删除 / 覆盖 | `output_fields` 里必须带主键 | 旧实现只返回 `content/category/...`，上层拿不到任何 id，连删都没法删 |
| 按业务键 upsert（本方案） | `user_id + category + subject`，与措辞无关 | 只有 subject 抽错才会失效（靠 prompt 约束 + 定期巡检兜底） |

**一句话：更新走"稳定业务键 + upsert"，删除走"主键 + delete"——两者都不依赖 LLM 复述的内容字符串。内容字符串是给人看的，不是给系统做定位用的。**

### 2.6.3 遗忘：不是所有记忆都值得永久保存

三种情况触发遗忘：

**1. 用户主动要求删除：**

```
用户："忘了之前我说的关于 Python 的事吧"
```

走 2.3.4 的提取流程：召回相关记忆时带回 `memory_key`（见 2.3.7 的 `output_fields`），LLM 把要删的键放进 `delete_ids`，后端调 `delete_memories_by_key(ids)`。**不要让 LLM 输出"要删的内容原文"再让后端做字符串匹配——它复述不出来**（见 2.6.2）。

**2. 长期未被检索的记忆（僵尸记忆）：**

```python
# core/memory_maintenance.py
import asyncio
import json
import time
from core.cache import redis
from core.long_memory_store import (
    COLLECTION_NAME, client, delete_memories_by_key, ensure_loaded, upsert_memories,
)
from core.logger import get_logger

logger = get_logger(__name__)

ACCESS_COUNTER_KEY = "memory:access_counter"  # 与 2.3.7 召回时 HINCRBY 的是同一个 key
STALE_DAYS = 90
STALE_MAX_IMPORTANCE = 3


async def flush_access_counters() -> int:
    """
    定时任务（每 5 分钟）：把 Redis 里累加的访问计数批量回写 Milvus。
    召回时一次 HINCRBY，比"每条记忆一次 update_entity"的写放大低一到两个数量级。
    """
    counters = {
        # core/cache.py 的连接池没有开 decode_responses，HGETALL 拿到的 key/value 是 bytes
        (k.decode() if isinstance(k, bytes) else k): int(v)
        for k, v in (await redis.hgetall(ACCESS_COUNTER_KEY)).items()
    }
    if not counters:
        return 0

    keys = list(counters.keys())
    # upsert 是整体替换：必须先把旧行完整取回来合并，否则 content / vector 会被清空
    old_rows = await asyncio.to_thread(
        client.query,
        collection_name=COLLECTION_NAME,
        filter=f"memory_key in {json.dumps(keys, ensure_ascii=False)}",
        output_fields=[
            "memory_key", "user_id", "session_id", "content", "subject",
            "category", "importance", "confidence", "vector", "created_at",
            "access_count", "last_accessed_at",
        ],
    )
    now = int(time.time())
    rows = [
        {
            **row,
            # Redis 里的是"两次回写之间的增量"，要累加到旧值上才是总次数
            "access_count": int(row["access_count"]) + counters[row["memory_key"]],
            "last_accessed_at": now,
            "updated_at": now,
        }
        for row in old_rows
    ]
    if rows:
        await upsert_memories(rows)
    await redis.hdel(ACCESS_COUNTER_KEY, *keys)
    logger.info("访问计数回写 | %d 条", len(rows))
    return len(rows)


async def cleanup_stale_memories(days: int = STALE_DAYS) -> int:
    """
    清理僵尸记忆：超过 N 天没被召回、且重要度低的记忆。

    判定依据必须是"最后一次被召回的时间"，不能是创建时间。这里曾经写错过，
    是本章最典型的一个"条件写反 + 字段根本不存在"的 bug：

    ❌ 旧实现注释写的是"清理 90 天未被访问的记忆"，条件里用的却是 created_at，
       而且比较方向写反——选出来的是"最近 90 天**新建**的记忆"，与"未被访问"正好相反。
       叠加两个附带问题：
         ① schema 里当时没有 last_accessed_at，"有多久没被访问"根本算不出来；
         ② 写入路径从不写 access_count（恒为 0），"access_count < 1"恒为真；
       三者合起来，条件退化成"删掉所有 importance < 3 的新记忆"——
       用户越活跃、说得越多，被误删的越多，而且不带任何报错。

    ✅ 现在：schema 有 last_accessed_at（由召回计数 + 上面的定时任务维护），条件按它写。
    """
    cutoff = int(time.time()) - days * 86400
    await asyncio.to_thread(ensure_loaded)

    stale = await asyncio.to_thread(
        client.query,
        collection_name=COLLECTION_NAME,
        filter=f"last_accessed_at < {cutoff} and importance < {STALE_MAX_IMPORTANCE}",
        output_fields=["memory_key"],
        limit=1000,  # 分批清理，避免一次删太多把查询节点拖住
    )
    keys = [row["memory_key"] for row in stale]
    if not keys:
        return 0

    await delete_memories_by_key(keys)
    logger.info("清理僵尸记忆 | removed=%d | cutoff=%d", len(keys), cutoff)
    return len(keys)
```

**为什么不能用 `access_count == 0` 代替时间条件**：刚写入的记忆访问次数也是 0，会立刻被清掉；而"多久没被召回"必须靠时间戳表达，这也正是 schema 里必须有 `last_accessed_at` 的原因。

**3. 用户用满了记忆配额：**

```python
MAX_MEMORIES_PER_USER = 500  # 每用户最多 500 条长期记忆

async def enforce_memory_quota(user_id: str):
    """超出配额时，删除最不重要 + 最久未访问的记忆（同样按 memory_key 删）"""
    ...
```

**一句话：遗忘的条件必须建立在"真的被记录下来的字段"上——写路径不写的字段、schema 里不存在的字段，都不能出现在清理条件里，否则条件会静默退化成"随机删数据"。**

| 概念 | 存储 | 生命周期 | 检索方式 | 容量管理 |
|------|------|---------|---------|---------|
| 短期记忆 | Redis | 当前会话 | 按 session_id 全量取出 | token 裁剪 + 滚动摘要压缩 |
| 长期记忆 | Milvus | 跨会话持久 | 语义相似度检索（embedding） | 去重 + 更新 + 遗忘 + 配额限制 |

| 关键设计决策 | 做法 | 原因 |
|-------------|------|------|
| LLM 判断存什么 | 每轮对话后 LLM 做记忆提取审查（先过轻量门控） | 规则判断太僵硬，LLM 理解语义才能区分"值得记"和"噪音"；但每轮都跑一次提取会把 token 成本翻倍 |
| 不阻塞对话 | `asyncio.create_task` 后台执行 | 记忆提取耗时 1~3 秒，不能拖慢用户看到的回复 |
| 记忆分层 | profile 走 KV（精确读写覆盖）+ 语义/情景走向量（相似度检索、可衰减） | "用户住哪"是确定值，不该用模糊检索去查、也不该用字符串匹配去更新 |
| 定位方式 | 更新 = 业务键 upsert，删除 = 主键 delete | LLM 复述的内容字符串不可靠，只有主键/业务键是稳定的 |
| 上下文预算 | 各组件按比例分配 token 份额 | 防止任一组件膨胀挤占全部空间 |
| 对话压缩 | 旧消息摘要（持久化 + 游标增量）+ 最近消息完整 | 既保留对话连贯性，又控制 token 数，且不会每轮重复摘要 |
| embedding 选型 | text-embedding-3-small | 性价比最高，$0.02/1M token，1536 维检索效果好；但换模型必须重标相似度阈值 |

**一句话总结：短期记忆是"记住刚才说了什么"，长期记忆是"记住你是一个什么样的人"。前者靠 Redis + 裁剪压缩，后者靠 LLM 提取 + Milvus 语义存储。两者协同，Agent 才能既有连贯对话能力，又有跨会话的个性化记忆。上下文预算系统是防止两者合在一起撑爆 prompt 的最终防线。**
