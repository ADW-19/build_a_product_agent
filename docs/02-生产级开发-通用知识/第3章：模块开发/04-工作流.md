# 第四章：工作流

> **核心论点**：单次 LLM 调用能解决的问题有限。真正的 Agent 能力来自于把多个 LLM 调用、工具执行、条件判断串联成一条可控的执行链——这就是工作流。工作流的"可控"体现在**谁在什么时候执行、下一步去哪，全部由代码预先决定**；"下一跳由模型临时决定"的那种形态叫自主 Agent，不是工作流（边界见 4.7.4）。本章聚焦 LangGraph 工作流的搭建方法，以及工作流中最棘手的问题：如何保证上游 LLM 节点的输出是稳定的，下游节点能可靠解析。

---

## 4.1 工作流是什么——从"一问一答"到"多步协作"

### 4.1.1 没有工作流的样子

```python
# 没有工作流：一个巨大的 prompt，一次 LLM 调用，一次返回
@app.post("/analyze")
async def analyze(text: str):
    prompt = f"""
    请分析以下文本：
    1. 提取关键信息
    2. 判断情感倾向
    3. 生成摘要
    4. 翻译成英文
    
    文本：{text}
    """
    response = await llm.ainvoke(prompt)
    return {"result": response.content}
```

问题：
- 每一步的质量无法单独控制
- 某一步失败，全部重来
- 无法在中间步骤插入工具调用
- LLM 的输出格式不稳定（有时 Markdown，有时纯文本，有时 JSON），难以解析
- Prompt 越长，LLM 的注意力越分散，质量越差

### 4.1.2 有工作流的样子

```
用户文本
   │
   ▼
┌──────────┐    结构化信息
│ 信息提取  │──────────────┐
│ (Node 1) │              │
└──────────┘              ▼
                    ┌──────────┐    情感标签
                    │ 情感分析  │──────────────┐
                    │ (Node 2) │              │
                    └──────────┘              ▼
                                        ┌──────────┐    摘要文本
                                        │ 摘要生成  │──────────────┐
                                        │ (Node 3) │              │
                                        └──────────┘              ▼
                                                            ┌──────────┐
                                                            │ 翻译     │
                                                            │ (Node 4) │
                                                            └────┬─────┘
                                                                 │
                                                                 ▼
                                                            最终结果
```

每个节点只做一件事，输入和输出都有明确的 Schema。节点之间通过**共享状态（State）**传递数据。这就是 LangGraph 的核心理念。

---

## 4.2 LangGraph 工作流基础：StateGraph 三要素

### 4.2.1 要素一：State（状态）——节点间的数据总线

State 是一个共享字典，每个节点读写它。LangGraph 会自动管理 State 在节点间的传递。

```python
from typing import TypedDict, Annotated
from operator import add
from langgraph.graph import StateGraph


# 定义 State 的结构
class AnalysisState(TypedDict):
    text: str                         # 输入文本
    entities: dict                    # 提取的结构化信息（Node 1 输出）
    sentiment: str                    # 情感标签（Node 2 输出）
    summary: str                      # 摘要（Node 3 输出）
    translation: str                  # 英文翻译（Node 4 输出）
    # 使用 Annotated + add 实现列表的追加（而非覆盖）
    messages: Annotated[list, add]    # 对话消息列表


# 初始 State
initial_state = AnalysisState(
    text="今天天气真好，适合出去走走。",
    entities={},
    sentiment="",
    summary="",
    translation="",
    messages=[],
)
```

关键设计：State 中的字段默认是**覆盖**语义（新值替换旧值）。如果需要**追加**语义（如消息列表），用 `Annotated[list, add]`。

### 4.2.2 要素二：Node（节点）——执行单元

每个节点是一个普通的 Python 函数，接收 State，返回 State 的部分更新：

```python
# 本节片段依赖：4.2.1 的 AnalysisState、core/ 骨架的 llm 单例
import json


def parse_entities(raw: str) -> dict:
    """
    把 LLM 返回的文本解析成 entities 字典（这里给的是最小实现）。

    注意：手写解析是下策——优先用 4.4.2 的 with_structured_output，
    让模型直接返回结构化对象，省掉这一层。
    """
    try:
        return json.loads(raw)
    except json.JSONDecodeError:
        logger.warning("实体解析失败，返回空结构")
        return {}


async def extract_entities(state: AnalysisState) -> dict:
    """
    节点 1：信息提取。
    输入 → State，输出 → State 的部分更新（只返回变更的字段）。
    """
    result = await llm.ainvoke(f"提取以下文本的关键实体...{state['text']}")
    entities = parse_entities(result.content)
    
    # 只返回这个节点负责更新的字段
    return {"entities": entities}


async def analyze_sentiment(state: AnalysisState) -> dict:
    """节点 2：情感分析。可以从 state 中读取上游节点的输出。"""
    # 用 entities 辅助情感判断
    context = f"文本：{state['text']}\n关键实体：{state['entities']}"
    result = await llm.ainvoke(f"判断情感...{context}")
    
    return {"sentiment": result.content.strip()}


async def generate_summary(state: AnalysisState) -> dict:
    """节点 3：生成摘要。读 state['text']，写 state['summary']。"""
    result = await llm.ainvoke(f"用一句话总结以下文本：\n{state['text']}")
    return {"summary": result.content.strip()}


async def translate_to_en(state: AnalysisState) -> dict:
    """节点 4：翻译。读 state['summary']，写 state['translation']。"""
    result = await llm.ainvoke(f"把以下内容翻译成英文：\n{state['summary']}")
    return {"translation": result.content.strip()}
```

节点的返回值是 `dict`，LangGraph 会自动将其合并回 State。只返回变更的字段即可，不需要返回整个 State。

### 4.2.3 要素三：Edge（边）——控制流的连接

```python
# 构建工作流
from langgraph.graph import StateGraph, START, END

graph = StateGraph(AnalysisState)

# 添加节点
graph.add_node("extract", extract_entities)
graph.add_node("sentiment", analyze_sentiment)
graph.add_node("summarize", generate_summary)
graph.add_node("translate", translate_to_en)

# 添加边（定义执行顺序）
graph.add_edge("extract", "sentiment")       # extract → sentiment
graph.add_edge("sentiment", "summarize")     # sentiment → summarize
graph.add_edge("summarize", "translate")     # summarize → translate

# 设置入口和出口：START / END 是 LangGraph 的两个虚拟节点
graph.add_edge(START, "extract")             # 入口
graph.add_edge("translate", END)             # 出口

# 编译
app = graph.compile()
```

边有三种类型：

| 类型 | 用法 | 含义 |
|------|------|------|
| 普通边 | `graph.add_edge("A", "B")` | A 执行完后无条件执行 B |
| 条件边 | `graph.add_conditional_edges("A", router, {"x": "B", "y": "C"})` | A 执行完后，根据 router 函数的返回值选择下一个节点 |
| 入口/出口 | `graph.add_edge(START, "A")` / `graph.add_edge("A", END)` | 工作流的起点和终点（`START`/`END` 从 `langgraph.graph` 导入） |

`graph.set_entry_point(...)` / `graph.set_finish_point(...)` 是旧写法，现已弃用——语义上它们就是给 `START`/`END` 加边，新代码统一用 `add_edge`。

## 4.3 条件边与路由：让工作流有"判断力"

### 4.3.1 最经典的条件路由：根据用户意图分流

```python
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class RouterState(TypedDict):
    message: str
    intent: str
    response: str


async def classify_intent_node(state: RouterState) -> dict:
    """分类节点：判断意图，写入 state"""
    intent_result = await classify_intent(state["message"])
    return {"intent": intent_result.intent}


async def handle_order(state: RouterState) -> dict:
    """订单分支：处理下单/查单类消息"""
    response = await llm.ainvoke(f"按订单流程处理用户消息：{state['message']}")
    return {"response": response.content.strip()}


async def handle_qa(state: RouterState) -> dict:
    """问答分支：基于知识库回答"""
    response = await llm.ainvoke(f"回答用户的问题：{state['message']}")
    return {"response": response.content.strip()}


async def handle_chat(state: RouterState) -> dict:
    """闲聊分支：直接回应"""
    response = await llm.ainvoke(f"友好地回应用户的闲聊：{state['message']}")
    return {"response": response.content.strip()}


def route_by_intent(state: RouterState) -> str:
    """
    路由函数：根据 intent 字段的值，返回下一个节点的名称。
    
    关键：判断依据已经在 State 里（由 classify 节点写入），
    这里只做纯逻辑判断，不调 LLM。
    返回的字符串必须是 add_conditional_edges 中映射的 key。
    """
    if state["intent"] == "order":
        return "order_handler"
    elif state["intent"] == "question":
        return "qa_handler"
    else:
        return "chat_handler"


# 构建
graph = StateGraph(RouterState)
graph.add_node("classify", classify_intent_node)
graph.add_node("order_handler", handle_order)
graph.add_node("qa_handler", handle_qa)
graph.add_node("chat_handler", handle_chat)

graph.add_edge(START, "classify")
graph.add_conditional_edges(
    "classify",          # 从哪个节点出发
    route_by_intent,     # 路由函数，返回下一个节点名
    {
        "order_handler": "order_handler",
        "qa_handler": "qa_handler",
        "chat_handler": "chat_handler",
    },
)
graph.add_edge("order_handler", END)
graph.add_edge("qa_handler", END)
graph.add_edge("chat_handler", END)
```

### 4.3.2 条件路由的关键原则

**路由函数不要调 LLM——不是因为框架不允许，而是因为路径会变得不可复现。** LangGraph 的 `add_conditional_edges` 明确支持 `async` 路由函数，下面第二个例子在语法和框架层面都能跑；真正的问题是：路由函数里的这次 LLM 调用**不会进入 State、不会被 checkpointer 记录**，于是路径无法回放、无法解释——线上排查时你只能看到"这次走了 escalate 分支"，看不到"为什么走了"。正确做法是**把 LLM 判断放进节点、把结论写进 State，条件边只读 State 做 `if/elif/else`**。

```python
# ✅ 路由函数：只读 State 做判断，判断依据由上游节点写入
def route_by_sentiment(state: AnalysisState) -> str:
    if state["sentiment"] == "negative":
        return "escalate"
    return "continue"

# ❌ 路由函数里调 LLM：语法与框架都合法，但路径不进 State、不可回放，排障时无法解释为什么走了这条路
async def route_by_llm(state: AnalysisState) -> str:
    result = await llm.ainvoke(f"这个要不要升级？{state['sentiment']}")
    return "escalate" if "升级" in result.content else "continue"
```

## 4.4 工作流的核心难题：保证 LLM 输出稳定可解析

### 4.4.1 问题场景

工作流中最常见的崩溃模式：

```
Node 1（LLM 提取）：
  输入：文本
  期望输出：{"name": "张三", "age": 30, "city": "北京"}
  实际输出："好的，我提取到以下信息：\n姓名：张三\n年龄：30\n城市：北京"
              ↑ LLM 用 Markdown 格式输出了，程序 JSON.parse 直接崩
              
Node 2（解析）：json.loads(state["entities"])  →  💥 JSONDecodeError
```

这就是工作流中最大的风险点——一个节点的输出是另一个节点的输入，如果上游输出的格式不稳定，下游就会崩溃。而 LLM 天生就是"格式不稳定"的。

### 4.4.2 方案一：`with_structured_output`（LangChain 原生方案，推荐）

```python
from pydantic import BaseModel, Field
from langchain_openai import ChatOpenAI


class ExtractedEntities(BaseModel):
    """Node 1 的期望输出结构

    注意字段写法：strict Structured Outputs 下所有字段都必须在 required 里，
    且不允许"非 null 的默认值"——所以"这个信息可能没有"要用 `X | None = None`
    表达，而不是 Field(default="") / Field(default_factory=list)。
    """
    name: str | None = Field(default=None, description="人物姓名，文本中没有则为 null")
    age: int | None = Field(default=None, description="年龄，文本中没有则为 null")
    city: str | None = Field(default=None, description="所在城市，文本中没有则为 null")
    keywords: list[str] | None = Field(default=None, description="关键词列表，没有则为 null")


# 使用 with_structured_output 绑定输出结构
llm = ChatOpenAI(model="gpt-5.1")
structured_llm = llm.with_structured_output(ExtractedEntities)


async def extract_entities_node(state: AnalysisState) -> dict:
    """节点：信息提取。输出保证是 ExtractedEntities 类型。"""
    result = await structured_llm.ainvoke(
        f"从以下文本中提取人物信息：\n{state['text']}"
    )
    # result 是 ExtractedEntities 实例，不是字符串
    # 不需要 json.loads，不需要 try-catch 解析
    return {"entities": result.model_dump()}
```

`with_structured_output` 做了什么：

1. **默认走 `method="json_schema"`**（`langchain-openai` 0.3.0 起，默认值已从 `function_calling` 改为 `json_schema`）：把 schema 交给 OpenAI 的 **Structured Outputs**，通过 `response_format` 传给模型。这是**服务端强约束**，不是"在 prompt 里请求模型配合"
2. 只有显式传 `method="function_calling"`，才会回到旧路径——把 schema 塞进 tool 定义、靠 `tool_calls` 拿结果（此时不使用 `response_format`）；`method="json_mode"` 只要求"是合法 JSON"，不校验 schema
3. LLM 返回后，自动用 Pydantic 校验
4. 注意：它**不会**自动重试非法 JSON——解析失败会抛 `OutputParserException`；需要重试时交给节点级 `retry_policy`（见 4.9.6），或自己用 `with_retry()` / fallback 链处理
5. 返回给你的就是 Pydantic 实例，类型安全

**strict 模式的两条硬约束（上面那段"字段写法"就是在绕开它们）：** 默认走 `json_schema` 就意味着走 strict Structured Outputs，OpenAI 会先校验你提交的 schema：

| 约束 | 说明 | 违规后果 |
|------|------|---------|
| 所有字段必须必填 | 每个 property 都要出现在 `required` 里 | 400：`Invalid schema for response_format ...: 'required' is required to be supplied and to be an array including every key in properties` |
| 不支持非 null 默认值与元数据约束 | `Field(default="")`、`Field(default_factory=list)`、`minimum`/`maximum`/`minLength` 等都不允许 | 同样是 400（schema 校验不过，请求根本发不出去） |

所以"这个字段可能没有"只有三种合法写法：**类型里带 null**（`name: str | None = Field(default=None)`，本节采用——类型里含 `null`、默认值也是 `null`，strict 接受这种写法）、**把字段改成真正必填**（让模型在没有信息时也必须给出一个值）、或者**显式退回 `method="function_calling"`**（tool_calls 路径对 schema 宽容得多）。反过来，如果模型或网关不支持 strict，不要硬撑默认值——显式指定 `function_calling`，或走 4.4.3 的 JSON Mode + Pydantic 二次校验。

**这是保证节点间数据传递稳定性的第一选择。** 能用 `with_structured_output` 的地方优先用它，不要手写 JSON 解析。

### 4.4.3 方案二：手动 JSON Mode + Pydantic 二次校验

如果用的模型不支持 `with_structured_output`，或者你需要更灵活的控制：

```python
import json
from pydantic import ValidationError
from core.llm import call_llm_with_retry


async def extract_entities_node(state: AnalysisState) -> dict:
    """手动 JSON 输出 + Pydantic 校验 + 重试"""
    
    prompt = f"""从以下文本中提取人物信息，以 JSON 格式返回。

文本：{state['text']}

输出格式：
{{
    "name": "姓名（没有则为空字符串）",
    "age": 年龄数字（没有则为0）,
    "city": "城市（没有则为空字符串）",
    "keywords": ["关键词1", "关键词2"]
}}

只输出 JSON，不要添加任何解释文字。"""

    for attempt in range(3):
        try:
            response = await call_llm_with_retry(
                messages=[{"role": "user", "content": prompt}],
                response_format={"type": "json_object"},  # 强制 JSON 输出
            )
            
            # 第一层：JSON 解析
            raw = json.loads(response)
            
            # 第二层：Pydantic 校验
            entities = ExtractedEntities(**raw)
            
            return {"entities": entities.model_dump()}
            
        except json.JSONDecodeError as e:
            logger.warning("Node1 JSON解析失败 (attempt=%d): %s", attempt + 1, str(e))
            if attempt == 2:
                # 三次都失败，返回空结构，不阻塞整个工作流
                return {"entities": ExtractedEntities().model_dump()}
            
        except ValidationError as e:
            logger.warning("Node1 Pydantic校验失败 (attempt=%d): %s", attempt + 1, str(e))
            if attempt == 2:
                return {"entities": ExtractedEntities().model_dump()}
```

**双重校验是保险机制：** JSON 解析保证是合法 JSON，Pydantic 校验保证字段类型正确。两关都通过，下游节点才能放心使用。

**但"降级"只对可选信息成立。** 上面三次都失败时返回空结构，是因为 `ExtractedEntities` 的字段都是"没有也可以"的可选信息；如果某个字段决定了下游走哪条分支（比如 4.6 里的 `severity`），就不能降级成默认值——那会把一次失败伪装成一次正常判定。这类字段的处理方式见 4.6 与 4.9.6。

### 4.4.4 方案三：在 prompt 里用 Few-shot 示例固化输出格式

对于不支持 JSON Mode 的模型，或者输出特别复杂的情况，Few-shot 是最可靠的手段：

```python
EXTRACTION_PROMPT = """从文本中提取人物信息。

## 输出格式（严格遵守）
<entity>
name: 姓名
age: 年龄
city: 城市
</entity>

## 示例
文本：我叫李四，今年25岁，住在上海。
<entity>
name: 李四
age: 25
city: 上海
</entity>

文本：小红是杭州人。
<entity>
name: 小红
age: 0
city: 杭州
</entity>

## 现在请提取
文本：{text}"""
```

然后解析时用正则或简单字符串匹配：

```python
import re

def parse_entity_output(raw: str) -> dict:
    """解析标记格式的输出，比 JSON 更宽松"""
    result = {"name": "", "age": 0, "city": ""}
    
    for line in raw.split("\n"):
        line = line.strip()
        if line.startswith("name:"):
            result["name"] = line.split(":", 1)[1].strip()
        elif line.startswith("age:"):
            try:
                result["age"] = int(line.split(":", 1)[1].strip())
            except ValueError:
                pass
        elif line.startswith("city:"):
            result["city"] = line.split(":", 1)[1].strip()
    
    return result
```

这种方式比 JSON 容错性好——LLM 多了一个空格、少了一个引号都不会崩。但只适合简单结构，复杂嵌套结构还是推荐 JSON。

### 4.4.5 三个方案的选型指南

| 方案 | 可靠性 | 复杂度 | 适用场景 |
|------|--------|--------|---------|
| `with_structured_output`（默认 `method="json_schema"` → Structured Outputs） | ★★★★★ | 最低 | GPT-5.1/Claude 等支持 strict 的强模型，**默认首选** |
| `with_structured_output(method="function_calling")` | ★★★★☆ | 低 | 模型/网关不支持 strict，或 schema 里有 strict 不允许的字段写法，退回 tool_calls 路径 |
| JSON Mode + Pydantic 双重校验 | ★★★★☆ | 中等 | 需要灵活控制 prompt，或模型不支持 structured output |
| Few-shot 标记格式 | ★★★☆☆ | 低（解析简单，但 LLM 输出可能偏离格式） | 简单结构、弱模型、需要最大容错 |

**原则：能用 `with_structured_output` 就优先用它。一个 API 调用就能解决的事，不要自己写解析和重试。**

## 4.5 节点间的数据契约：下游节点必须"防御性读取"

即使上游用了 `with_structured_output`，下游节点也不能假设数据一定完美：

```python
async def sentiment_analysis_node(state: AnalysisState) -> dict:
    """
    下游节点：防御性读取上游数据。
    
    即使上游合约是 ExtractedEntities，也要处理：
    - 实体为空
    - 字段缺失
    - 类型不对（上游出了 bug）
    """
    entities = state.get("entities", {})
    
    # 防御性读取：给默认值，做类型断言
    name = entities.get("name", "")
    age = entities.get("age", 0)
    city = entities.get("city", "")
    
    # 确保类型正确
    if not isinstance(age, int):
        age = 0
    
    # 构建分析上下文（无实体也能正常工作）
    context_parts = []
    if name:
        context_parts.append(f"人物：{name}")
    if city:
        context_parts.append(f"城市：{city}")
    
    context = "；".join(context_parts) if context_parts else "无额外上下文"
    
    result = await llm.ainvoke(
        f"文本：{state['text']}\n{context}\n判断上述文本的情感倾向..."
    )
    
    return {"sentiment": result.content.strip()}
```

**规则：上游节点的输出对下游节点来说是不可信的。** 即使类型系统保证了结构，也要做最低限度的防御——给默认值、校验类型、处理空值。这是工作流稳定性的最后一道防线。

## 4.6 实战：搭建一个完整的三节点工作流

### 4.6.1 场景

用户提交一段客服对话记录，Agent 需要：
1. 提取客户信息 + 问题描述
2. 判断问题严重程度
3. 严重问题 → 生成升级处理建议，普通问题 → 生成标准回复模板

### 4.6.2 完整代码

```python
# workflows/ticket_analysis.py
from typing import TypedDict, Literal
from pydantic import BaseModel, Field
from langgraph.graph import StateGraph, START, END
from langgraph.types import RetryPolicy
from langgraph.checkpoint.memory import InMemorySaver
from langchain_openai import ChatOpenAI
from core.logger import get_logger

logger = get_logger(__name__)
llm = ChatOpenAI(model="gpt-5.1")

# ==================== State 定义 ====================

class TicketState(TypedDict):
    transcript: str                   # 原始对话记录
    customer_name: str | None         # 客户姓名（可选信息，缺失可为 None）
    customer_level: str | None        # 客户等级（可选信息，缺失可为 None）
    problem: str                      # 问题描述（下游判定的依据，不能为空）
    severity: str                     # 严重程度：critical / normal / unknown（unknown = 判定失败，必须转人工）
    action: str                       # 最终输出


# ==================== 结构化输出模型 ====================

class ExtractionResult(BaseModel):
    """Node 1 的输出结构（strict Structured Outputs 兼容写法，见 4.4.2）"""
    customer_name: str | None = Field(default=None, description="客户姓名，没有则为 null")
    customer_level: Literal["VIP", "普通"] | None = Field(default=None, description="客户等级，没有则为 null")
    problem: str = Field(description="问题的简要描述（一句话），无法判断时返回空字符串")


class SeverityResult(BaseModel):
    """Node 2 的输出结构"""
    severity: Literal["critical", "normal"] = Field(description="严重程度")
    reason: str = Field(description="判断依据")


# ==================== Node 1：信息提取（可降级节点） ====================

extract_llm = llm.with_structured_output(ExtractionResult)

async def extract_info(state: TicketState) -> dict:
    """从对话记录中提取客户和问题信息。

    这是可降级节点：客户姓名/等级属于"没有也能继续"的可选信息，失败可降级；
    但降级必须诚实——绝不编造一个看起来合理的值。
    """
    try:
        result = await extract_llm.ainvoke(
            f"分析以下客服对话记录，提取客户信息和问题描述：\n\n{state['transcript']}"
        )
        logger.info("信息提取完成 | customer=%s | level=%s", result.customer_name, result.customer_level)
        return result.model_dump()
    except Exception:
        logger.exception("信息提取失败——降级：可选字段置空，problem 留空交由下游显式失败")
        # 不要写 problem="信息提取失败"：它会被下游当作一条真实的"普通问题"参与判定
        return {"customer_name": None, "customer_level": None, "problem": ""}


# ==================== Node 2：严重程度判断（不可降级节点） ====================

severity_llm = llm.with_structured_output(SeverityResult)

async def assess_severity(state: TicketState) -> dict:
    """根据客户等级和问题描述，判断严重程度。

    severity 决定业务路由，所以这里【没有 try-catch】：
    - 判定依据缺失 → 显式返回 "unknown"，由路由送给人工兜底节点；
    - LLM 调用异常 → 直接抛出，交给节点级 RetryPolicy 重试（见 4.9.6），
      重试耗尽后请求失败并保留现场，而不是猜一个 normal 继续往下走。
    """
    # 防御性读取
    level = state.get("customer_level") or "普通"
    problem = (state.get("problem") or "").strip()

    if not problem:
        logger.error("严重程度无法判定：problem 为空，转人工")
        return {"severity": "unknown"}

    result = await severity_llm.ainvoke(
        f"客户等级：{level}\n问题：{problem}\n\n判断该问题的严重程度。"
        f"判定标准：VIP客户 = critical；涉及退款/投诉 = critical；其他 = normal。"
    )
    logger.info("严重程度判定 | severity=%s | reason=%s", result.severity, result.reason)
    return {"severity": result.severity}


# ==================== Node 3A：严重问题处理 ====================

async def handle_critical(state: TicketState) -> dict:
    """生成升级处理建议"""
    response = await llm.ainvoke(
        f"生成客户投诉升级处理方案：\n"
        f"客户：{state.get('customer_name', '未知')}（{state.get('customer_level', '普通')}）\n"
        f"问题：{state.get('problem', '未知')}\n"
        f"要求：1. 升级到主管 2. 48小时内闭环 3. 提供补偿方案建议"
    )
    return {"action": response.content}


# ==================== Node 3B：普通问题处理 ====================

async def handle_normal(state: TicketState) -> dict:
    """生成标准回复模板"""
    response = await llm.ainvoke(
        f"生成客服标准回复模板：\n"
        f"客户：{state.get('customer_name', '用户')}\n"
        f"问题：{state.get('problem', '未知')}\n"
        f"要求：礼貌、专业、给出预计解决时间"
    )
    return {"action": response.content}


# ==================== Node 3C：人工兜底 ====================

async def human_review(state: TicketState) -> dict:
    """兜底节点：严重程度未知时，不自动回复，转人工工单"""
    logger.error(
        "工单转人工 | reason=severity 未知 | level=%s", state.get("customer_level")
    )
    return {"action": "【需人工介入】严重程度未能判定，已转人工工单，请人工核实后回复。"}


# ==================== 路由函数 ====================

def route_by_severity(state: TicketState) -> str:
    """纯逻辑路由：不调 LLM。未知/缺失一律走人工——绝不默认成 normal"""
    severity = state.get("severity")
    if severity == "critical":
        return "critical_handler"
    if severity == "normal":
        return "normal_handler"
    return "human_review"


# ==================== 构建工作流 ====================

def build_ticket_workflow(checkpointer=None):
    graph = StateGraph(TicketState)

    # 添加节点
    # assess 是不可降级节点：异常直接上抛，由 retry_policy 按指数退避重试，重试耗尽即整体失败并保留现场
    graph.add_node("assess", assess_severity, retry_policy=RetryPolicy(max_attempts=3))
    # extract 是可降级节点：异常在节点内被消化成"可选字段缺失"，不会上抛，所以配 retry_policy 也不会生效
    graph.add_node("extract", extract_info)
    graph.add_node("critical_handler", handle_critical)
    graph.add_node("normal_handler", handle_normal)
    graph.add_node("human_review", human_review)

    # 连线
    graph.add_edge(START, "extract")
    graph.add_edge("extract", "assess")
    graph.add_conditional_edges(
        "assess",
        route_by_severity,
        {
            "critical_handler": "critical_handler",
            "normal_handler": "normal_handler",
            "human_review": "human_review",
        },
    )
    graph.add_edge("critical_handler", END)
    graph.add_edge("normal_handler", END)
    graph.add_edge("human_review", END)

    return graph.compile(checkpointer=checkpointer)


# checkpointer 由启动时创建并注入（Redis/Postgres saver，见 4.9）；
# 不挂 checkpointer 只能"一次跑完"，无法多轮续跑、断点恢复与人工审批
ticket_workflow = build_ticket_workflow(checkpointer=InMemorySaver())  # 仅开发环境，生产替换
```

调用方式：

```python
# 每个会话一个 thread_id（通常直接复用 session_id）：
# State 与每一步的中间结果按线程隔离落盘，可续跑、可恢复、可回溯
config = {"configurable": {"thread_id": "ticket-session-001"}}

result = await ticket_workflow.ainvoke({
    "transcript": "客户张三（VIP）：我买的手机屏幕碎了，要求退款！客服：好的我记录一下...",
    "customer_name": None,
    "customer_level": None,
    "problem": "",
    "severity": "",
    "action": "",
}, config=config)
# → result["severity"] = "critical"
# → result["action"] = "升级处理方案：赔偿 + 主管跟进..."

# 若 severity 判定失败（problem 为空等），route_by_severity 会把流程送进 human_review：
# → result["severity"] = "unknown"
# → result["action"] = "【需人工介入】..."
```

### 4.6.3 这个工作流的"稳定合约"体现在哪

```
Node 1 (extract_info)  ← 可降级节点
  输出: ExtractionResult (Pydantic 校验保证)
  异常: 可选字段置空（None），problem 留空——不编造值
         │
         ▼
Node 2 (assess_severity)  ← 不可降级节点
  输入: state.customer_name / state.problem
  读取方式: state.get("problem") or ""  ← 防御性读取，但空值不会被"补"成合理值
  输出: SeverityResult (Pydantic 校验保证)
  依据缺失: 返回 severity="unknown"
  调用异常: 不吞——上抛给节点级 retry_policy，重试耗尽即整体失败并保留现场
         │
         ▼
路由函数 (route_by_severity)
  输入: state.severity
  逻辑: critical → 升级；normal → 标准回复；其余（含 unknown / 缺失）→ 人工兜底
         │
   ┌─────┼──────┐
   ▼     ▼      ▼
Node 3A Node 3B Node 3C
 升级    标准回复  转人工（判定失败的显式出口）
```

每一步都有两重保障：**Pydantic 校验保证输出结构** + **`.get()` 保证输入容错**。但要分清"容错"与"假装成功"：上游输出结构由 Pydantic 兜住，下游读取给默认值兜住缺失；而一旦失败影响到**走哪条路**（`severity`），就必须显式失败（`unknown` → 人工），不能靠默认值把流程"接"下去。

**一句话：可降级的是可选信息，不可降级的是业务判断——把失败伪装成 normal，等于把 VIP 客户的退款投诉静默降级成标准模板回复。**

## 4.7 工作流的两种模式（以及一个必须澄清的边界）

### 4.7.1 模式一：串行管道（Pipeline）

```
A → B → C → D → 结束
```

适用场景：数据需要逐步加工（提取 → 分析 → 总结 → 翻译）。前面已有完整示例。

### 4.7.2 模式二：并行扇出/聚合（Fan-out / Fan-in）

```
              ┌→ B1（查订单）─┐
A（意图识别）→ ┼→ B2（查库存）─┼→ C（汇总回复）
              └→ B3（查物流）─┘
```

LangGraph 原生支持并行：

```python
# B1, B2, B3 会同时执行
graph.add_edge("A", "B1")
graph.add_edge("A", "B2")
graph.add_edge("A", "B3")

# 都执行完后汇入 C
graph.add_edge("B1", "C")
graph.add_edge("B2", "C")
graph.add_edge("B3", "C")
```

从同一个节点出发的多条边，LangGraph 会自动并行执行目标节点。只有所有并行节点都完成后，才会进入汇聚节点 C。

### 4.7.3 边界：ReAct 循环不是"第三种工作流模式"

```
     ┌──────────────────────────┐
     │                          │
     ▼                          │
┌─────────┐   tool_call   ┌─────────┐
│  LLM    │──────────────→│ 工具执行 │
│  推理   │←──────────────│         │
└─────────┘   结果文本    └─────────┘
     │
     │ 无 tool_call
     ▼
   结束
```

前面两种模式都属于**确定性编排**：谁在什么时候执行、下一步去哪，全由代码里的边决定。而这张图不一样——**要不要调工具、调哪个工具、循环几轮，全部由模型在运行时决定**。按第 1 章《协议与架构模式选型》的定义，这是 **Agent 形态，不是工作流**：

| | 工作流（本章主体） | 自主 Agent（ReAct 等） |
|------|------------------|---------------------|
| 流程决定者 | 开发者（代码里的边） | LLM（运行时决定下一跳） |
| 确定性 | 输入 A 必定走同一条路径 | 同一输入可能走出不同路径 |
| 可回放性 | 每条路径都能被 State 记录、能断点恢复 | 只能靠 trace 事后分析 |
| 典型场景 | 表单处理、审批流、数据 ETL、客服分流 | 开放式排障、多工具探索、研究型任务 |

把它写在这里，是因为工程上两者经常**嵌套**——工作流里的某个节点内部跑一个 Agent 循环，外层依然由代码控制；但选型时要分清，不能拿"Agent 循环"去论证"工作流"的可控性。

自定义 ReAct 循环要落回 `StateGraph`。不过**先别急着写**：LangChain 1.x（对应 LangGraph v1）已经提供了官方实现，默认就用它——`langchain.agents.create_agent` 一行代码创建（`langgraph.prebuilt.create_react_agent` 是它的前身，现已弃用）：

```python
from langchain.agents import create_agent
from langgraph.checkpoint.memory import InMemorySaver
from tools.order import order_tool
from tools.inventory import inventory_tool
from tools.kb import search_kb

agent = create_agent(
    model=llm,
    tools=[order_tool, inventory_tool, search_kb],
    system_prompt="你是订单客服助手：先查订单，再基于查询结果回答。",   # 注意参数名是 system_prompt
    checkpointer=InMemorySaver(),      # 想传 thread_id 就必须挂 checkpointer（见 4.9）
)

result = await agent.ainvoke(
    {"messages": [{"role": "user", "content": "查一下订单 ORD-001"}]},
    config={"configurable": {"thread_id": "session-001"}},
)
```

`create_agent` 返回的就是一张编译好的图：ReAct 循环、工具节点、状态定义都已内置，人在环、上下文压缩、工具护栏都在 middleware 层配置。**只有当你需要自定义状态机（自定义 State 字段、自定义节点粒度、工作流里嵌循环）时，才落回本章的 `StateGraph`。**

需要完全自定义循环时，用条件边自己搭：

```python
from langgraph.graph import MessagesState, END

def should_continue(state: MessagesState) -> str:
    """检查最后一条消息是否有 tool_calls"""
    last_message = state["messages"][-1]
    if hasattr(last_message, "tool_calls") and last_message.tool_calls:
        return "tools"
    return "end"

graph.add_conditional_edges(
    "llm",
    should_continue,
    {"tools": "tools", "end": END},
)
graph.add_edge("tools", "llm")  # 工具执行完 → 回到 LLM 继续推理
```

### 4.7.4 选型判据：什么时候用工作流，什么时候上自主 Agent

Anthropic 在《Building Effective Agents》里给的次序是"**能用最简单方案就别上 agent**"：一次 prompt 能搞定就别上工作流，工作流能搞定就别上自主 Agent。判断该用哪一层，看四个问题：

| 判据 | 倾向工作流（确定性编排） | 倾向自主 Agent（模型决定下一跳） |
|------|------------------------|-------------------------------|
| 任务路径能否预先枚举 | 能：步骤固定、分支有限（审批、ETL、表单、客服分流） | 不能：步数取决于问题本身（开放式排障、研究型任务） |
| 错误代价 | 高：写库、退款、发消息必须可控、可审、可回滚 | 较低或可回滚，允许试错 |
| 可观测/可回放要求 | 高：每条路径要能复盘，还要断点续跑与人工审批 | 可接受"每次路径不同"，靠 trace 事后分析 |
| 成本与延迟 | 敏感：路径固定，LLM 调用次数与延迟可预估 | 宽松：多轮工具调用与重试不可避免 |

**一句话判据：路径能预先画出来的，用工作流；画不出来的，才用自主 Agent。** 而生产系统通常是组合的——外层用工作流保证可控（谁先谁后、哪里要人审、失败怎么兜底），把真正需要"自己决定下一步"的那一段封装成一个 Agent 节点。

## 4.8 工作流调试与可观测性

### 4.8.1 记录每个节点的输入输出

```python
from functools import wraps
from core.logger import get_logger

logger = get_logger("workflow")


def trace_node(node_name: str):
    """节点追踪装饰器：自动记录输入输出的关键信息"""
    def decorator(func):
        @wraps(func)
        async def wrapper(state: dict) -> dict:
            logger.info("[%s] 开始执行", node_name)
            
            try:
                result = await func(state)
                
                # 只记录输出字段名和长度，不记录完整内容（避免日志爆炸）
                output_summary = {
                    k: f"len={len(str(v))}" if isinstance(v, (str, list, dict)) else str(v)
                    for k, v in result.items()
                }
                logger.info("[%s] 执行完成 | output=%s", node_name, output_summary)
                
                return result
            except Exception:
                logger.exception("[%s] 执行异常", node_name)
                raise
        
        return wrapper
    return decorator


# 使用
@trace_node("extract_info")
async def extract_info(state: TicketState) -> dict:
    ...
```

### 4.8.2 用 `astream_events` 观测整个流程

`astream_events` 有两代调用约定，先分清版本——**照抄旧文的 v2 写法在今天属于 legacy**：

| 版本 | 调用形态 | 事件形态 | 状态 |
|------|---------|---------|------|
| `version="v1"` / `"v2"` | `async for event in workflow.astream_events(...)`（异步生成器） | 结构化字典：`event["event"]` / `event["name"]` / `event["data"]` / `event["metadata"]` | legacy：仍可用，但推荐迁移 |
| `version="v3"` | `run = await workflow.astream_events(..., version="v3")`，再 `async with run as stream:` | **typed 事件投影**：`stream.messages`（逐条模型输出）、`stream.values`（状态快照）、`stream.output`（最终结果）等 | LangChain 1.3 / LangGraph 1.2 起 GA 的类型化事件流，当前推荐 |

**v3（推荐）——不再自己解析字典，直接消费类型化投影：**

```python
async def run_with_trace(workflow, initial_state: dict, config: dict):
    """运行工作流并消费 v3 的类型化事件流"""
    run = await workflow.astream_events(initial_state, config=config, version="v3")

    async with run as stream:
        # ① 模型输出流：这才是能推给前端的"流式"
        async for message in stream.messages:
            if message.text:
                yield message.text          # 增量文本，直接推进 SSE
            # 工具调用也有独立投影（stream.tool_calls），用来给前端展示"正在查订单…"

        # ② 最终结果：等价于 ainvoke 的返回值
        output = await stream.output
        logger.info("流程结束 | output_keys=%s", sorted(output.keys()))
```

**v2（legacy）——必须按 `metadata.langgraph_node` 过滤，否则打印出来的不是节点：**

```python
async def stream_workflow(workflow, initial_state: dict, config: dict):
    """v2 legacy 事件流：只挑出"真正的节点事件"与"真正的 token 事件" """
    async for event in workflow.astream_events(initial_state, config=config, version="v2"):
        kind = event["event"]
        node = (event.get("metadata") or {}).get("langgraph_node")

        # ① 节点级追踪：只有真正的图节点才带 langgraph_node
        if node and kind == "on_chain_start":
            logger.info("▶ 节点开始: %s", node)
        elif node and kind == "on_chain_end":
            logger.info("■ 节点完成: %s", node)
        elif node and kind == "on_chain_error":
            logger.error("✖ 节点异常: %s | %s", node, event.get("data", {}).get("error", ""))

        # ② 真正的流式输出：模型逐 token 的增量（前端 SSE 用它）
        elif kind == "on_chat_model_stream":
            text = getattr(event.get("data", {}).get("chunk"), "content", "")
            if text:
                yield text
```

**为什么必须过滤：** v2 里的 `on_chain_start` / `on_chain_end` 不只由图节点发出——**图本身**（name 为 `LangGraph`）和节点内部的**嵌套 runnable**（比如 `extract_llm` 这种 `RunnableSequence`、结构化输出的解析器）同样会发。不过滤就会打出"节点开始: LangGraph""节点开始: extract_llm"，与 4.8.1 的节点追踪混在一条日志流里，根本分不清哪条才是真节点。`metadata.langgraph_node` 是 LangGraph 给"节点内部所有事件"打的统一标记，按它过滤才等于"节点事件"。

| 事件 | 出现在哪里 | 怎么处理 |
|------|-----------|---------|
| `on_chain_start` / `end` / `error` 且带 `metadata.langgraph_node` | 图节点开始/结束/异常 | 节点级追踪（4.8.1 的那套日志） |
| `on_chain_start`，name=`LangGraph`，无 `langgraph_node` | 整张图开始执行 | 忽略；要看"整轮耗时"时才用 |
| `on_chain_*`，name=`extract_llm` / 结构化输出解析器 | 节点内部的嵌套 runnable | 忽略（排查某个节点时才单独看） |
| `on_chat_model_stream` | 模型逐 token 输出 | 推给前端，这才是真正的流式 |
| `on_tool_start` / `on_tool_end` | 工具执行开始/结束 | 工具调用进度展示（见第一章：对话接口） |

**一句话：v2 的 `on_chain_*` 是"所有 chain 的事件"，`metadata.langgraph_node` 才是"节点"；要看流式内容就订阅 `on_chat_model_stream`（v3 则是 `stream.messages`）。** 注：v3 的投影对象字段仍在小版本内演进，升级时留意 release notes。

## 4.9 上生产必需：Checkpointer、恢复与并行扇出

本章前面的示例大多是 `graph.compile()` 直接编译——本地跑得通，但它"跑完即忘"。而生产环境有三件事都要求图记住自己走到哪了：**用户关掉页面再回来**（多轮续跑）、**进程重启或请求超时**（断点恢复）、**关键动作要人点头**（人工审批）。这一节把这一层补上。

### 4.9.1 没挂 checkpointer 的图，就是"不能恢复"的图

```python
# ❌ 典型写法：compile() 什么都不传，运行时却传了 thread_id
app = graph.compile()

await app.ainvoke(state, config={"configurable": {"thread_id": "s-1"}})
# ValueError: Checkpointer requires one or more of the following 'configurable' keys:
#   thread_id, checkpoint_ns, checkpoint_id
```

**本质原因：** `thread_id` 不是"传给图的普通参数"，而是"去 checkpointer 里取哪条执行线程"的 key。没有 checkpointer，就没有这东西可取——框架直接拒绝执行，而不是默默忽略。反过来讲：**只要你想传 `thread_id`（多轮会话、断点恢复、人工中断），就必须在 `compile()` 时挂上 checkpointer。**

```python
# ✅ 正确：编译时挂 checkpointer，运行时每个会话带自己的 thread_id
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver          # 开发环境
from langgraph.checkpoint.redis.aio import AsyncRedisSaver     # 生产环境

def build_ticket_workflow(checkpointer):
    graph = StateGraph(TicketState)
    ...                       # 节点与连线同 4.6
    return graph.compile(checkpointer=checkpointer)   # ← 唯一区别在这里

# 生产：应用启动时建好 saver 并全局复用（不要每个请求新建连接）
async with AsyncRedisSaver.from_conn_string("redis://localhost:6379/1") as saver:
    await saver.asetup()                              # 首次运行建索引，幂等，可重复执行
    ticket_workflow = build_ticket_workflow(saver)

    # 运行时：thread_id 直接复用 session_id（见第一章：对话接口）
    session_id = "s-2026-09-18-001"                   # 实际项目里来自请求体
    config = {"configurable": {"thread_id": session_id}}
    result = await ticket_workflow.ainvoke(state, config=config)
```

开发环境用 `InMemorySaver`（进程重启即丢），生产必须换 Redis/Postgres saver——选型见 4.9.7。

### 4.9.2 `thread_id`：一个会话 = 一条执行线程

| 维度 | 不传 `thread_id` | 传 `thread_id` |
|------|-----------------|---------------|
| State 落盘 | 不落盘，请求结束即消失 | 每步之后落盘，可续跑 |
| 多轮会话 | 每次调用都是孤立的一轮 | 同一 thread 上 State 累积（多轮上下文天然接上） |
| 隔离性 | 无隔离概念 | 不同 thread 完全隔离，互不污染 |
| 断点恢复 | 不可能 | `ainvoke(None, config=config)` 从上次落盘处继续 |
| 生产映射 | —— | `thread_id = session_id`（与对话接口的会话隔离共用一套 key） |

排查时这套 API 很有用（都不需要重跑图）：

```python
# 看当前线程的 State（值、下一步要执行哪个节点、是否停在中断点）
snapshot = await ticket_workflow.aget_state(config)
print(snapshot.values, snapshot.next, snapshot.tasks)

# 人工修正 State 后再继续（例如补上缺失的 problem）
await ticket_workflow.aupdate_state(config, {"problem": "客户要求退款，屏幕碎裂"})
result = await ticket_workflow.ainvoke(None, config=config)   # 传 None = 从断点继续
```

**一句话：`thread_id` 就是"执行现场"的编号——没有它，图只有这一次执行；有了它，图才有"上一次"。**

### 4.9.3 恢复会重放节点：有副作用的节点必须幂等

**这是最容易被忽略的一条。** 恢复（无论因为中断、超时还是进程重启）不是"从节点中间接着跑半个"，而是**从最后一个 checkpoint 重新执行那个节点**。也就是说：节点函数会被再执行一次。

```python
async def send_sms(phone: str, text: str, idempotency_key: str | None = None) -> None:
    """下游短信服务封装（真实项目里放 services/）：带幂等键时同 key 只发一次"""
    ...


# ❌ 不幂等：节点被重放一次，客户就多收一条短信
async def notify_customer(state: dict) -> dict:
    await send_sms(state["phone"], "您的工单已升级")
    return {"notified": True}


# ✅ 幂等：用业务键做幂等键，重复执行也只生效一次
async def notify_customer_idempotent(state: dict) -> dict:
    # 幂等键必须由业务信息构成：不能含随机数、时间戳、自增 ID
    idempotency_key = f"{state['transcript'][:32]}:escalated"
    await send_sms(state["phone"], "您的工单已升级", idempotency_key=idempotency_key)
    return {"notified": True}
```

三种常见做法，从强到弱：

| 做法 | 说明 | 适用 |
|------|------|------|
| 业务唯一键 | 数据库唯一索引 + upsert/`ON CONFLICT DO NOTHING` | 写库、建单、扣款 |
| 幂等键 | 下游接口支持 `Idempotency-Key`，同 key 只生效一次 | 调用外部 API、发消息 |
| 状态位检查 | 先读 State/DB，发现"已经做过"就跳过 | 事后统计、通知类操作（注意：并发/重放窗口下不是强保证） |

**同理，不要往 State 里塞不可序列化的东西**（数据库连接、LLM 客户端、文件句柄）——checkpointer 要序列化 State 落盘，塞进去的后果是每步序列化失败或体积失控。State 里只放数据，资源放单例（`core/` 骨架）。

**一句话：恢复 = 重放节点，所以节点的副作用必须能用幂等键压住。**

### 4.9.4 中断与恢复：`interrupt()` + `Command(resume=...)`

需要"人工拍板"时，用 `interrupt()` 把控制权交回外部，再用 `Command(resume=...)` 送答案回去：

```python
from langgraph.types import Command, interrupt

async def review_and_send(state: TicketState) -> dict:
    """节点内暂停：把待确认内容交给人工，等 resume 值返回"""
    # interrupt() 会落盘当前 State 并让本次执行停下。
    # 关键：从调用方视角它【不抛异常】——ainvoke 正常返回，结果里带 __interrupt__
    decision = interrupt({
        "type": "review_required",
        "action": state["action"],
    })
    # 恢复执行时，interrupt() 的返回值就是 Command(resume=...) 里传进来的东西
    if decision["approved"]:
        return {"action": state["action"]}
    return {"action": "【已驳回】" + decision["reason"]}
```

```python
# 第一次调用：执行到 interrupt 处停下，正常返回（注意：不抛异常）
result = await ticket_workflow.ainvoke(state, config=config)
if "__interrupt__" in result:
    payload = result["__interrupt__"][0].value     # 交给前端/审核终端展示
    logger.info("等待人工审批: %s", payload)

# 人工审批后：同一个 thread_id，传 Command(resume=...) 恢复
result = await ticket_workflow.ainvoke(
    Command(resume={"approved": True, "reason": ""}),
    config=config,                                  # ← 必须与上面是同一个 thread_id
)
```

三个必踩的点：

1. **`interrupt()` 需要 checkpointer**：没有 checkpointer 就没有"落盘 + 恢复"的载体，直接报错；
2. **恢复必须用同一个 `thread_id`**：换一个 thread 就是另一个会话，会从头开始跑；
3. **interrupt 之前的代码会被重放**：恢复时节点从头执行，所以 `interrupt()` 之前不要放有副作用的代码（同上，副作用要靠幂等键兜住）。

**一句话：中断 = 落盘并返回 `__interrupt__`，恢复 = 同 `thread_id` + `Command(resume=...)`。**

### 4.9.5 `Send`：运行时才知道分支数的扇出

4.7.2 的"多条固定边"适合分支数在编译期就确定的场景；如果分支数是**运行时才知道**的（例如"把检索到的 20 篇文档各摘要一次"），用 `Send` 做 map-reduce：

```python
from typing import TypedDict, Annotated
from operator import add
from langgraph.graph import StateGraph
from langgraph.types import Send


class MapReduceState(TypedDict):
    doc_ids: list[str]
    # 并行分支的返回值必须"追加"，不能"覆盖"——否则并发写同一个 key 会抛 InvalidUpdateError
    summaries: Annotated[list[str], add]
    summary: str                       # 聚合结果


def plan_docs(state: MapReduceState) -> dict:
    """上游节点（示例）：确定要并行处理哪些文档，写进 doc_ids"""
    ...


def fan_out(state: MapReduceState) -> list[Send]:
    """路由函数返回一组 Send：每个 Send 就是一次并行分支调用"""
    return [Send("summarize_one", {"doc_id": doc_id}) for doc_id in state["doc_ids"]]


async def summarize_one(state: dict) -> dict:
    """分支节点：只处理一个 doc_id，返回部分更新"""
    summary = await llm.ainvoke(f"用一句话总结文档 {state['doc_id']}")
    return {"summaries": [summary.content.strip()]}


async def reduce_summaries(state: MapReduceState) -> dict:
    """fan-in 聚合节点：所有分支完成后才执行一次"""
    return {"summary": "\n".join(f"- {s}" for s in state["summaries"])}


graph = StateGraph(MapReduceState)
graph.add_node("plan", plan_docs)
graph.add_node("summarize_one", summarize_one)
graph.add_node("reduce", reduce_summaries)
graph.add_conditional_edges("plan", fan_out, ["summarize_one"])    # 返回 list[Send] 时必须用 map 形式
graph.add_edge("summarize_one", "reduce")                          # 全部分支完成后才进 reduce
```

（`plan_docs` 用省略号占位，按 4.6 的写法实现即可。）

要点：

- **`Send` 的 payload 是该分支自己的输入**，不是全量 State——分支节点只能看到你显式传进去的字段（这也是它的优点：分支间不会互相干扰）；
- **fan-in 是自动的**：所有 `Send` 出来的分支都跑完，才进入下游节点（这里是 `reduce`）；
- **聚合字段必须带 reducer**（`Annotated[list, add]`），否则并发写同一个 key 会抛 `InvalidUpdateError`；
- **并行度要自己控**：分支数就是并发请求数，扇出 500 个分支等于同时打 500 次 LLM/数据库调用——要配合信号量、限流和连接池上限。

**一句话：`Send` 把"分支数在运行时才知道"的扇出交给框架调度，你只需要保证聚合字段有 reducer、扇出数量有上限。**

### 4.9.6 节点级 `retry_policy`：比手写 try-catch 更正确

4.6 里"不可降级"的 `assess` 没有自己吞异常，靠的就是这一层——**重试是框架级机制，不是节点里的 `for` 循环**：

```python
from langgraph.types import RetryPolicy

graph.add_node(
    "assess",
    assess_severity,
    # 节点抛异常时，框架按指数退避 + 抖动重试，最多 3 次
    retry_policy=RetryPolicy(max_attempts=3, initial_interval=0.5, backoff_factor=2.0, jitter=True),
)
```

| 维度 | 节点内手写 `try/except` + `sleep` | 节点级 `retry_policy` |
|------|----------------------------------|----------------------|
| 重试范围 | 只有你包住的那几行 | 整个节点（含 State 读取与后续处理） |
| 退避策略 | 自己写，容易写出 `time.sleep` 阻塞事件循环 | 框架统一：指数退避 + 抖动 |
| 用尽重试后 | 由你决定返回值——很容易"降级"成默认值，把失败伪装成成功 | 抛出去，checkpointer 保留现场，可人工干预、可恢复 |
| 可观测性 | 只在你自己的日志里 | 重试次数与失败进事件流/trace，能接告警 |

三个边界要记住：

1. `retry_policy` 只重试**异常**。"返回了一个不合理的值"不算异常——那要靠 schema 校验（4.4）和显式失败分支（4.6 的 `unknown` → 人工）来兜；
2. **节点内 `catch` 与节点级 `retry_policy` 是二选一**：异常被节点自己 catch 住，框架就看不到它，重试永远不会触发（4.6 里 `extract` 就是这么降级的，所以它不配 `retry_policy`）。想"先重试、再降级"，就在节点内用 `with_retry()` 重试，失败后再返回降级值；
3. 不要在重试里做**不可重入**的事：如果节点里已经发过消息、写过半条记录，重试会再来一遍——回到 4.9.3 的幂等键。

**一句话：让框架重试、让异常上抛、让失败可见，而不是在节点里把异常"消化"成默认值。**

### 4.9.7 Saver 选型：`AsyncPostgresSaver` vs Redis saver

| 维度 | `AsyncPostgresSaver` | Redis saver（`AsyncRedisSaver`） |
|------|---------------------|-------------------------------|
| 存储模型 | 事务型表：checkpoint 与 writes 可分事务原子写入 | 快照 + 索引，依赖 Redis 持久化（AOF/RDB）配置 |
| 可查询性 | 强：直接用 SQL 查历史、做审计与离线分析 | 弱：只能按 thread/key 读，不适合复杂查询 |
| 过期与清理 | 自己写清理任务（按时间删旧 checkpoint） | 原生 TTL，适合"会话结束即过期" |
| 多实例/多进程 | 天然支持，连接池生态成熟 | 支持，但要控 key 前缀与内存上限 |
| 适合 | 需要审计、需要长期留存、要做状态分析的业务 | 高频短会话、低延迟、可接受会话过期即丢 |

两者都要**定期清理**：checkpoint 是"每一步都存一份"，不清理就会无限增长（见 4.9.8）。子图各自挂 checkpointer 时要留意命名空间——同一份状态可能被存两遍。

**一句话：要审计与查询选 Postgres，要低延迟与自动过期选 Redis；无论选哪个，清理策略必须一起上。**

### 4.9.8 状态体积：checkpoint 是"每步一份快照"

**本质原因：** LangGraph 在一个 superstep（一批节点执行）之后就会落一次 checkpoint，保存的是**当前完整的 State**（外加待处理的 writes）。所以：State 越大，每一步的序列化与写盘成本越高；轮次越多，累计写入量按平方级增长（第 20 步要重写一遍前 19 步积累的内容）。同一轮对话里如果图跑了 5 个 superstep，那就是 5 份快照——这也是"每轮存一份"的直觉最容易错的地方。

```python
from typing import TypedDict, Annotated
from operator import add


# ❌ 把中间产物和大对象全塞进 State
class BadState(TypedDict):
    raw_documents: list[str]        # 几十万字全文，每步都被重写一遍
    all_llm_outputs: list[str]      # 每个节点的原始输出都留着
    messages: list                  # 永不裁剪，越长越贵


# ✅ 只放"下一步需要的东西"：大对象进对象存储/DB，State 里只留引用
class GoodState(TypedDict):
    doc_ids: list[str]                          # 存引用，不存全文
    summary: str
    messages: Annotated[list, add]              # 配合定期裁剪（见第二章：长期记忆与短期记忆）
```

落盘前的自查清单：

- State 里有没有**大文本、二进制、base64**（图片、PDF 原文）？→ 挪到对象存储，State 只留 key；
- `messages` 有没有**裁剪策略**？→ 只保留最近 N 轮或做摘要压缩，否则每轮都在重写全部历史；
- 并行累加类字段（`Annotated[list, add]`）是不是**只增不删**？→ 它是写放大最狠的一类；
- 是否**每一步都要落盘**？→ 中间步骤不必留痕的长流程可以用 `durability` 相关配置减少中间 checkpoint 写入（写入次数与恢复粒度之间的权衡）；
- 存储侧有没有 **TTL / 保留策略**？→ 没有 TTL，checkpoint 会随轮次无限增长。

**一句话：State 是"下一步需要的数据"，不是"过程日志"——checkpoint 的成本由 State 的体积和轮次共同决定。**

## 4.10 常见踩坑清单

| 坑 | 现象 | 原因 | 解法 |
|----|------|------|------|
| LLM 输出格式不对 | 下游节点 json.loads 报错 | LLM 在 JSON 前后加了 Markdown 标记或解释文字 | 用 `with_structured_output`，或在 prompt 中强调"只输出 JSON"，并做 Pydantic 二次校验 |
| strict schema 被拒 | 调用直接 400：`Invalid schema for response_format` | 默认走 `method="json_schema"`（Structured Outputs），而 schema 用了 `Field(default="")` / `default_factory` / `minimum` 这类 strict 不允许的写法 | 字段写成 `X \| None = Field(default=None)`，或改必填，或显式 `with_structured_output(..., method="function_calling")` |
| 并行节点数据竞争 | 并行执行的两个节点都在改 state 的同一个字段 | 两个节点同时写同一个 key：LangGraph 对无 reducer 的 channel 会抛 `InvalidUpdateError` 明确报错（不是静默覆盖） | 并行节点写不同的字段，或使用 `Annotated[list, add]` 追加语义 |
| 条件路由走错 | 该升级的工单没升级 | 路由依据来自 LLM 判断，而判断过程没进 State（放进路由函数里调 LLM 尤其严重） | LLM 判断放进节点并写入 State，路由函数只读 State 做 if/else；本文档不给条件边留"调 LLM"的口子 |
| 节点异常返回默认值 | 关键分支静默降级（VIP 投诉走了标准回复），日志之外无人知晓 | 无差别 try-catch 把异常"消化"成默认值，业务判断被伪装成正常结果 | 区分可降级/不可降级：可选信息可给默认值；决定路由的字段必须 raise（配节点级 `retry_policy`），或返回显式失败值走人工兜底 |
| 图无法恢复/HITL 报错 | 进程重启后无法续跑；传 `thread_id` 报 `ValueError: Checkpointer requires ...` | `compile()` 时没挂 checkpointer | `graph.compile(checkpointer=saver)`，运行时统一传 `config={"configurable": {"thread_id": session_id}}`（见 4.9） |
| 恢复后副作用重复 | 恢复一次，客户收到两条短信/库里多一条记录 | 恢复会重放节点，节点里的写库/发消息不幂等 | 用业务唯一键 / 幂等键 / 状态位检查（见 4.9.3） |
| State 字段拼写错误 | 下游节点读不到上游写的数据 | `return {"severity": "high"}` 但下游读 `state["severty"]` | 用 TypedDict 定义 State，IDE 自动补全 + mypy 静态检查 |
| 工作流无限循环 | ReAct 循环跑了 100 步不结束 | LLM 反复调同一个工具 | `recursion_limit` + `ToolFailureGuard`（见第三章） |

## 4.11 本章小结

| 要点 | 核心做法 | 一句话 |
|------|---------|--------|
| State 设计 | TypedDict 定义所有字段，明确每个字段由哪个节点写入 | State 是节点间的数据总线，结构清晰是第一要务 |
| 结构化输出 | `llm.with_structured_output(PydanticModel)`（默认走 strict Structured Outputs） | 让 LLM 直接输出 Pydantic 实例，省掉解析和校验代码；字段写 `X \| None = None` 而不是非 null 默认值 |
| 数据契约 | 上游 Pydantic 校验输出 + 下游 `.get()` 防御读取 | 上游保证输出正确，下游保证输入容错——双重保险 |
| 条件路由 | LLM 判断写进节点与 State，路由函数只做 if/else | 路由依据必须在 State 中已存在，路径才可回放 |
| 节点异常 | 可降级节点返回默认值；不可降级节点 raise（配 `retry_policy`）或返回显式失败值走人工 | 一个节点崩了不该拖垮整个流程，但更不能被静默降级 |
| 可恢复性 | `compile(checkpointer=...)` + 每个会话一个 `thread_id` | 没有 checkpointer 就没有恢复、没有 HITL、没有跨进程续跑 |
| 副作用与恢复 | 恢复会重放节点，写库/发消息用幂等键 | 幂等是能安全恢复的前提 |
| 并行执行 | 固定分支用多条边，运行时才知道分支数用 `Send` | 并行节点不能写 State 的同一个字段（要写就带 reducer） |

**工作流的本质是"把复杂任务拆成多个简单步骤，每一步只做一件事，但要保证上一步的输出能安全地成为下一步的输入"。** 拆得开是设计能力，接得稳是工程质量——能恢复、可回放、失败可见，才算真的接稳了。
