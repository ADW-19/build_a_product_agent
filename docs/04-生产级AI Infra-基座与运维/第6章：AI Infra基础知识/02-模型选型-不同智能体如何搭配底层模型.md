# 第二章：模型选型——不同智能体如何搭配底层模型

> **核心论点**：Agent 的模型选型不是"哪个模型 benchmark 最高就选哪个"。不同类型的智能体对模型的诉求完全不同——代码生成要的是逻辑严密和长上下文、客服问答要的是低延迟和高并发、安全审查要的是快和准而不是聪明。模型选型 = 先拆解你的 Agent 有哪些子任务 → 每个子任务对参数/生态/性能的权重不同 → 按权重匹配合适的模型 → 再设计流量调度和降级策略。本章以编码智能体为例，走一遍从业务需求到完整模型架构的全流程。

---

## 2.1 不同智能体的模型需求差异

### 2.1.1 为什么不能用"一个大模型全干"

在 1.5 节中我们讨论了舰队模式的架构优势。本节从模型选型角度回答一个更具体的问题：**面对市场上几十个模型，每个智能体角色应该选哪个？**

不同类型的智能体对模型的诉求差异极大：

```
智能体类型        核心诉求              关键指标              不适合的模型
─────────────────────────────────────────────────────────────────────
编码 Agent       长代码逻辑一致         HumanEval/     SWE-bench  延迟差但逻辑强的模型
                 长上下文理解           上下文窗口 ≥ 128K
                
客服 Agent       低延迟、高并发         首 token < 300ms         大参数慢模型
                 意图识别准确           并发 > 100 QPS

翻译 Agent       多语言能力             BLEU / COMET             单语言优化的模型
                 领域术语准确           垂直领域 fine-tune 支持

安全审查 Agent   极低延迟、高精度        首 token < 100ms         通用大模型
                 规则确定性高            输出格式严格可控          （过于"聪明"反而容易绕过规则）

写作 Agent       创意性、文风多样        语言流畅度                死板的数学优化模型
                 长文本连贯性            长文本连贯性 ≥ 8K

RAG 知识问答     检索与生成的配合        忠实度 (Faithfulness)     容易幻觉的模型
                 引用能力                上下文利用率
```

**结论：不存在"最好的模型"，只存在"最适合你这个 Agent 子任务的模型"。**

### 2.1.2 智能体拆解——从任务到模型需求

以一个典型的编码智能体为例，它内部至少有 6 个不同的模型调用点：

```
用户："帮我在这个项目里加一个用户登录模块"
         │
         ▼
┌──────────────────────────────────────────────────────────┐
│ ① 意图识别 ─────────────────────→ 小模型 (0.5B~1.5B)     │
│    "这是代码生成请求"                快、准、不需要聪明     │
├──────────────────────────────────────────────────────────┤
│ ② 代码上下文理解 ────────────────→ 专用代码模型 (27B~230B)│
│    "理解项目结构、找到插入点"         长上下文、代码逻辑    │
├──────────────────────────────────────────────────────────┤
│ ③ 代码生成 ──────────────────────→ 专用代码模型 (主模型)  │
│    "写出符合规范的代码"               逻辑严密、多文件协调  │
├──────────────────────────────────────────────────────────┤
│ ④ 代码审查 ──────────────────────→ 小模型 (0.5B~7B)      │
│    "检查安全问题、命名规范"            规则性强、不需要创造  │
├──────────────────────────────────────────────────────────┤
│ ⑤ 文档/注释生成 ─────────────────→ 通用模型 (备用/征用)   │
│    "给生成的代码写注释和文档"         语言流畅、结构化输出   │
├──────────────────────────────────────────────────────────┤
│ ⑥ 用户交互/解释 ─────────────────→ 通用模型 (备用/征用)   │
│    "用通俗语言解释代码做了什么"        表达清晰、用户友好    │
└──────────────────────────────────────────────────────────┘
```

**6 个调用点，至少 3 种不同的模型。** 没有任何一个模型能在所有调用点上都表现最优。

## 2.2 模型选型三维框架：参数 · 生态 · 性能

### 2.2.1 三维框架全景

```
                   参数 (Parameters)
                  模型有多大？
                  智力天花板在哪？
                       │
                       │
         ┌─────────────┼─────────────┐
         │             │             │
         │    选型决策三角的平衡点    │
         │             │             │
         │             │             │
    ─────┼─────────────┼─────────────┼─────
         │             │             │
         │             │             │
  生态 (Ecosystem)              性能 (Performance)
  文档/社区/工具链？              延迟/吞吐/成本？
  出问题了谁来救？                 ROI 划算吗？
```

**一个好的模型选型决策，必须同时回答这三个问题。缺一个维度，决策就有盲区。**

### 2.2.2 各维度的具体评估项

| 维度 | 评估项 | 为什么重要 |
|------|--------|-----------|
| **参数** | 参数量 (B) | 智力天花板。大参数 = 更强推理，但也 = 更贵 |
| | 上下文窗口 | 代码 Agent 需要 ≥ 128K，客服可能 32K 就够 |
| | 训练数据质量 | 同样参数量的模型，"用什么数据训练"差异巨大 |
| | 领域适配度 | HumanEval 高分 ≠ 你的业务场景高分 |
| **生态** | 开源/闭源 | 开源可私有化部署，闭源依赖厂商 SLA |
| | 社区活跃度 | GitHub Star / Issue 响应 / 更新频率 |
| | 文档质量 | 中文文档？部署文档？Fine-tune 教程？ |
| | 与现有技术栈的兼容性 | 是否兼容 VLLM/SGlang？是否有 OpenAI 兼容 API？ |
| | 厂商稳定性 | 闭源模型的厂商会不会突然调价/下线/改协议？ |
| **性能** | 首 token 延迟 (TTFT) | 用户体感——看到第一个字要等多久 |
| | 生成吞吐 (token/s) | 瓶颈在哪——GPU 还是显存带宽？ |
| | 并发能力 (QPS) | 你的 Agent 要扛多少用户同时在线？ |
| | 推理成本 (￥/1M token) | 你的日请求量 × 单次 token 消耗 × 单价 = 日成本 |
| | 硬件需求 | 需要几张什么卡？你的机房有没有？ |

## 2.3 参数维度——大模型还是小模型？

### 2.3.1 参数量的真实意义

```
参数量级      智力能力                    典型角色              成本量级
──────────────────────────────────────────────────────────────────
0.5B~3B      模式匹配、规则判断           意图分类、安全审查、    极低
             简单的分类/提取              实体识别、格式校验      (CPU 可跑)

7B~14B       基础推理、简单代码            翻译、摘要、RAG 生成、  低
             结构化输出                   客服基础问答            (1 张消费级 GPU)

27B~70B      复杂推理、多步代码            代码理解、复杂问答、    中
             逻辑严密性开始涌现            多工具编排              (1~4 张 A100)

70B~230B     深度推理、长代码生成          核心编码、数学推理、    高
             跨文件协调、架构设计          架构设计                (4~8 张 A100)

230B+ (MoE)  专家级推理                    超大项目编码、         很高
             多领域知识融合                科研级推理              (8+ 张 A100)
```

**关键认知：参数量不是线性的。** 从 7B 到 70B，参数量 ×10，但编码能力（HumanEval）可能从 60% 涨到 85%——涨了 25 个百分点，而不是 10 倍。你要为这 25 个百分点的提升付出 10 倍的算力成本。这不是"越大越好"，而是"花多少钱买多少能力"的 ROI 决策。

### 2.3.2 什么任务必须大模型，什么任务小模型就够了

```
必须大模型（< 70B 做不好）：              小模型（< 7B）就够：
─────────────────────────────────────────────────────────────
✅ 多文件代码生成（需全局架构理解）         ✅ 意图分类（40 个类，0.5B 就能做到 93%）
✅ 复杂逻辑推理（多步推导）                 ✅ 安全内容审查（规则匹配 > 推理）
✅ 需要领域深度知识的问答                   ✅ 实体提取（日期/金额/订单号）
✅ 需要理解用户模糊意图并追问               ✅ 格式校验（是不是合法 JSON）
✅ 跨语言翻译（中英之外的语言对）            ✅ 情感分析
✅ 创意写作（文笔、风格）                   ✅ 代码规范检查（命名/缩进/注释）
```

**一个实用的判断标准：如果这个任务你可以用一套明确的规则做到 85% 的准确率，那就不需要大模型。小模型（甚至正则表达式）就够。**

## 2.4 生态维度——开源的自由 vs 闭源的省心

### 2.4.1 开源 vs 闭源的选择逻辑

```
选开源模型时你在选什么：
  ✅ 数据隐私（敏感代码不出公司）
  ✅ 可定制（fine-tune、量化、改推理逻辑）
  ✅ 无供应商锁定（不会被突然涨价或下线）
  ❌ 需要自己维护基础设施
  ❌ 出了问题自己排查

选闭源 API 时你在选什么：
  ✅ 零运维（厂商帮你管 GPU、管扩缩容）
  ✅ 始终用最新最强模型（厂商持续升级）
  ✅ SLA 保障（99.9% 可用性由厂商承担）
  ❌ 数据隐私风险（代码/用户数据离开你的服务器）
  ❌ 成本不可控（按 token 计费，量大了肉疼）
  ❌ 模型行为不可控（厂商更新模型，你的 prompt 可能失效）
```

### 2.4.2 生态健康度快速评估法

```python
# 开源模型生态健康度——10 分钟快速评估清单

评估项                             怎么看                       红线
──────────────────────────────────────────────────────────────────
GitHub 活跃度                     Star 数 + 近期 commit 频率     归档仓库、最后更新 > 6 个月
Issue 响应速度                    看 Issue 关闭率和响应时间      大量 Open Issue 无人回复
部署文档质量                      跟着文档走一遍，能跑起来吗？    文档只有 README 三行字

社区模型变体                      搜 HuggingFace，有多少        只有官方权重，没有社区贡献
                                  fine-tune/量化版本
许可证                            能不能商用？                  CC BY-NC 等非商用协议
中文社区讨论量                    知乎/公众号/微信群讨论频次     关键词搜不到任何中文内容
```

## 2.5 性能维度——延迟、吞吐、成本的三角权衡

### 2.5.1 同一个模型在不同推理引擎下的性能差异

> 这部分在 1.6~1.8 节已详细展开。本节聚焦于：**在候选模型之间做性能对比时，怎么看数据。**

```
关键指标             测什么                    怎么看
─────────────────────────────────────────────────────────────────
TTFT (Time to        从发送请求到收到第一个     Agent 对客场景：< 300ms（用户等不了）
First Token)         token 的时间              内部工具场景：< 2000ms

TPOT (Time per       每生成一个 token 的       影响"打字感"——TPOT > 100ms 用户觉得卡
Output Token)        平均时间

吞吐 (Throughput)    每秒能生成多少个 token    你的并发需求 × 平均输出长度 ÷ 吞吐 = 需要的实例数

每百万 token 成本    API 价格或 GPU 租赁 ÷    日请求量 × 单次平均 token 消耗 × 单价 = 日账单
                     吞吐能力换算
                     
显存占用            加载模型需要多少显存       你的 GPU 有没有这么多显存？
                                              没显存 → 量化 → 精度损失 → 能力下降
```

### 2.5.2 性能数据怎么看才不被忽悠

```
⚠️ 模型厂商公布的 benchmark 性能 ≠ 你业务场景的实际性能

常见的 benchmark 陷阱：

① 数据污染
  → 模型可能在训练集中见过 benchmark 测试集
  → HumanEval 94% ≠ 你的代码库里能写出 94% 正确的代码

② 评估方式不一致
  → 有的用 greedy decoding（确定性），有的用 sampling（多样性）
  → greedy 分数高 ≠ 实际对话体验好

③ 硬件环境不一致
  → 厂商用 8×H100 跑出来的吞吐 ≠ 你用 2×A100 的实际表现

④ 不在你的领域测
  → MMLU 总分高 ≠ 你的电商售后场景好
  → 必须用自己的业务测试集评估

✅ 唯一可靠的性能数据来源：用你的业务测试集，在你的硬件上，用你的推理参数，实际跑一遍。
```

## 2.6 实战案例——编码智能体从 0 到 1 的模型选型

### 2.6.1 案例背景：虚构场景设定

> **声明**：以下案例中出现的团队、业务场景、模型选型决策均为作者虚构，旨在提供一个贴近实际的模型选型决策演练。模型名称采用真实存在的开源/商业模型以增强可参考性，但具体的性能数据和决策过程为推演性质。

```
┌─────────────────────────────────────────────────────────────┐
│ 团队：某中型互联网公司的 AI 平台组                           │
│ 任务：构建一个内部编码智能体，帮助全公司 300+ 开发人员        │
│       进行日常编码辅助（代码生成、Review、重构、文档）         │
│                                                             │
│ 业务约束：                                                   │
│  - 代码数据绝对不能离开公司内网（排除所有闭源 API）            │
│  - 日活开发者：200~300 人，峰值并发约 80                     │
│  - 现有 GPU 资源：8×A100-80GB + 4×A10-24GB                 │
│  - 预算：已采购硬件，无额外 API 预算                         │
│                                                             │
│ 模型能力要求：                                               │
│  - 支持 Python / JavaScript / Go / Java / SQL               │
│  - 上下文窗口 ≥ 128K（一个中等项目模块 ~50K token）           │
│  - 代码生成准确率（pass@1）≥ 70%（内部验收标准）              │
│  - 首 token 延迟 ≤ 2s（开发者等不了太久）                    │
└─────────────────────────────────────────────────────────────┘
```

### 2.6.2 候选模型初筛

团队首先拉了一个候选清单，排除掉明显不符合的：

```
候选模型                  参数量    代码能力(Bench)   硬件需求         排除原因
────────────────────────────────────────────────────────────────────────────
DeepSeek-V4.1 (MoE)      685B(MoE)  SWE-bench 52%    16×H200       硬件不够
Claude Opus 4.7          闭源       SWE-bench 68%    闭源 API        数据不能出内网
Gemini 2.5 Pro           闭源       SWE-bench 58%    闭源 API        同上
Qwen3.6-27B              27B       LiveCodeBench 65% 2×A100        候选（备选）
MiniMax-M2.7             230B(MoE) LiveCodeBench 72% 4×A100        候选（主力）
DeepSeek-Coder-V3        262B(MoE) LiveCodeBench 69% 4×A100        候选
Mistral Large 3          123B      HumanEval 84%     4×A100        通用模型，代码不是强项
Qwen3-Coder-8B           8B        LiveCodeBench 48% 1×A10         参数太小，仅备用审查
```

**筛到 3 个：MiniMax-M2.7、DeepSeek-Coder-V3、Qwen3.6-27B。**

### 2.6.3 底座模型深度对比——为什么最终选了 MiniMax-M2.7

团队拿了 50 个内部真实的编码任务（包含单元测试生成、多文件重构、SQL 优化、代码审查），在 4×A100 上用 VLLM 部署，逐一跑分：

```
评测维度 (权重)        MiniMax-M2.7    DeepSeek-Coder-V3   Qwen3.6-27B
─────────────────────────────────────────────────────────────────────
HumanEval pass@1       91%             90%                 88%
LiveCodeBench          72%             68%                 65%
真实业务任务 pass@1    78%             74%                 63%
  - 多文件重构 (10题)  8/10            7/10                5/10
  - SQL 优化 (10题)     7/10            5/10                6/10
  - 单元测试生成 (10题)  9/10           9/10                7/10
  - 代码审查 (10题)     7/10            8/10                6/10
  - Bug 定位 (10题)     8/10            8/10                5/10

长上下文 (128K) 稳定性  ✅ 稳定          ⚠️ 偶发注意力衰减     ✅ 稳定
推理速度 (token/s)      85              62                  120
首 token 延迟 (TTFT)    1800ms          2200ms               800ms
显存占用 (4×A100)       72GB            78GB                 52GB

部署复杂度              标准 VLLM       标准 VLLM            标准 VLLM
社区支持                 中文社区活跃    中文社区活跃          中文社区活跃
许可证                   开源可商用      开源可商用            开源可商用
```

**关键决策分析：**

```
为什么 MiniMax-M2.7 胜出：

① 编码能力全面领先
   → 在真实业务任务（不是刷榜 benchmark）上，M2.7 的多文件重构和 SQL 优化
      明显优于其他候选。团队的核心需求恰恰是多文件协调。

② MoE 架构的性价比
   → 230B 总参数，但每次推理只激活约 40B → 推理成本和 40B 模型差不多
   → 4×A100 可以部署，8 张卡刚好够跑 2 个实例（一个主、一个备灾）

③ 长上下文稳定性
   → DeepSeek-Coder-V3 的 128K 上下文下注意力有衰减（具体表现：长文件中
      后半部分的代码风格与前半部分不一致）
   → M2.7 在 128K 上下文下保持稳定的代码风格一致性

④ 推理速度可以接受
   → TTFT 1800ms 虽然比 Qwen3.6-27B 的 800ms 慢了一倍多，
      但对于编码场景（开发者预期等待 1~3 秒），2s 以内是可接受的。
   → 如果做客服场景这就是硬伤，但编码场景可以接受。
```

### 2.6.4 备用模型选型——Qwen3.6-27B 的角色

```
为什么需要备用，以及为什么选 Qwen3.6-27B：

备用的两个作用：
  ① 主模型挂了时的降级承接
  ② 简单编码任务的分流（降低主模型负载）

Qwen3.6-27B 的关键优势：
  → 参数量 27B，仅需 2×A100（主模型占 4 张，备用正好用剩下的 2 张）
  → LiveCodeBench 65%，虽然不是最高，但足以应付简单到中等难度任务
  → TTFT 800ms，比主模型快一倍——简单任务走它反而体验更好
  → 部署简单，VLLM 原生支持，不需要额外适配

备用的限制（团队明确接受）：
  → 不支持 128K 长上下文（保守设 32K），复杂多文件任务在降级期间降级为"建议拆分任务"
  → 代码审查准确率下降约 15%，复杂逻辑审查在降级期间转人工
```

### 2.6.5 轻量任务的小模型方案——0.6B 也能上生产

```
  (命名/缩进/注释)                                                    不需要 AI

简单代码补全      Qwen3-Coder-1.7B GPU (1×A10)      首 token < 150ms  单行/单函数补全
  (行级/函数级)                                                      1.5B 就够，7B 是浪费
```

**关键决策：让 0.6B 的小模型去拦截 60% 的简单流量。**

```
流量分布（实测上线 2 周后的数据）：

  意图分类（0.6B）────── 100% 流量（所有请求都先走）────── 首 token 50ms
       │
       ├── "帮我写个登录接口" (代码生成请求, 35%)
       │       └──→ 主模型 (M2.7) ──── 首 token 1800ms
       │
       ├── "这个函数有什么安全问题" (安全审查, 15%)
       │       └──→ CodeBERT 小模型 ── 首 token 30ms
       │
       ├── "给这个类加注释" (文档生成, 20%)
       │       └──→ deepseek-v4-pro (公司统一部署) ── 首 token 400ms
       │
       ├── "这行语句能不能优化" (简单补全, 20%)
       │       └──→ Qwen3-Coder-1.7B ── 首 token 150ms
       │
       └── "帮我设计一个微服务架构" (复杂任务, 10%)
               └──→ 主模型 (M2.7) ── 首 token 2500ms
```

**0.6B 小模型拦截了 60% 的流量，意味着主模型只需要处理 40% 的核心请求——显存和算力被释放出来，可以专注于复杂任务。**

### 2.6.6 为什么没有选向量检索模型做 RAG

> 这是一个重要的架构取舍，值得单独展开。

团队评估过"用向量检索 + RAG 的方式做代码知识库问答"的方案，最终否决了。原因是向量检索在结构化代码场景下有四个硬伤：

```
硬伤一：代码是结构化数据，语义向量对它不敏感

  代码："def calculate_discount(price, coupon): return price - coupon"
  语义向量 → 相似的可能是 "def apply_discount(cart): ..."

  但开发者问 "calculate_discount 里用了几个参数" 时：
  → 向量检索返回的是语义相似的函数，不是结构信息
  → 结构信息（参数列表、返回值类型）是 AST 解析的活，不是 embedding 的活

硬伤二：代码知识库需要精确匹配，不需要语义近似

  用户问："ORD-88483 这个订单的状态"

  RAG 的 embedding 检索：
    搜索"订单状态" → 返回"订单状态查询 API"文档 → 没有 ORD-88483 的结果

  结构化查询（代码直接调 SQL/API）：
    SELECT status FROM orders WHERE order_id = 'ORD-88483' → "已发货"

  → 精确匹配场景下，embedding 检索是负优化：返回了看起来相关但实质无用的内容。

硬伤三：代码变更频繁，向量索引跟不上

  代码库每天有 200+ 次 commit。
  每次 commit 后需要：重新解析 → 重新切 chunk → 重新 embedding → 重新入库
  → 这个管线的延迟和成本远超直接用代码分析工具（AST/LSP）

硬伤四：RAG 检索不适合"找依赖关系"

  开发者问："谁调用了这个函数？" "这个类的继承链是什么？"
  → 这是静态分析工具的活（jedi/lsprotocol/pyre）
  → RAG 最多返回"这个函数的文档"，但它不知道谁调用了它
```

**团队的做法：在 Agent 工具层直接集成代码分析工具，绕过向量检索。**

```python
# Agent 的工具定义——不依赖向量检索，直接调代码分析工具

CODE_ANALYSIS_TOOLS = {
    "find_definition": {
        "tool": "jedi_definition_tool",
        "description": "精确查找函数/类的定义位置",
        "why_no_rag": "需要 AST 级别的精确匹配，不是语义近似"
    },
    "find_references": {
        "tool": "jedi_references_tool",
        "description": "查找所有调用该函数的位置",
        "why_no_rag": "调用链是图结构，embedding 无法表达"
    },
    "get_class_hierarchy": {
        "tool": "jedi_hierarchy_tool",
        "description": "获取类的完整继承链",
        "why_no_rag": "树形结构，不是文本片段"
    },
    "search_code_pattern": {
        "tool": "ripgrep_tool",  # 精确文本搜索
        "description": "按正则/关键词搜索代码",
        "why_no_rag": "代码搜索需要精确匹配，不是模糊语义"
    },
    "get_file_structure": {
        "tool": "ast_parser_tool",
        "description": "解析文件的 AST 结构（类、函数、导入）",
        "why_no_rag": "结构性信息需要 AST，embedding 给不了"
    },
}
```

**这个决策节省了维护向量数据库和 embedding 管线的成本，同时获得了更精准的代码分析能力。**

### 2.6.7 意图路由与流量调度

团队在 Agent 入口层做了一层智能路由，将不同类型的请求分发到不同的模型：

```python
# core/code_agent/router.py —— 编码智能体的模型路由

from enum import Enum


class TaskCategory(str, Enum):
    CODE_GENERATION = "code_generation"       # 代码生成 → 主模型 M2.7
    CODE_REVIEW = "code_review"               # 代码审查 → 小模型 0.5B~1.5B
    DOCUMENTATION = "documentation"           # 文档/注释/作图 → DeepSeek-V4-Pro
    EXPLANATION = "explanation"               # 解释代码 → DeepSeek-V4-Pro
    REFACTORING = "refactoring"               # 重构 → 主模型 M2.7
    SECURITY_SCAN = "security_scan"           # 安全扫描 → CodeBERT 小模型


# 路由规则（基于意图分类结果）
ROUTING_TABLE = {
    TaskCategory.CODE_GENERATION: {
        "primary_model": "minimax-m2.7",
        "backup_model": "qwen3.6-27b",
        "fallback_model": "deepseek-v4-pro",  # 紧急征用
        "max_latency_ms": 5000,
    },
    TaskCategory.CODE_REVIEW: {
        "primary_model": "qwen2.5-coder-1.5b",
        "backup_model": "qwen3.6-27b",
        "fallback_model": "minimax-m2.7",     # 复杂审查回退到主模型
        "max_latency_ms": 3000,
    },
    TaskCategory.DOCUMENTATION: {
        "primary_model": "deepseek-v4-pro",   # 公司统一部署
        "backup_model": "qwen3.6-27b",
        "fallback_model": "minimax-m2.7",
        "max_latency_ms": 8000,
    },
    TaskCategory.SECURITY_SCAN: {
        "primary_model": "codebert-security",
        "backup_model": None,                 # 安全扫描没有备用——错了宁可阻塞
        "fallback_model": None,
        "max_latency_ms": 500,
    },
}

# ⚠️ 关键设计：文档/注释/解释类任务不经过代码模型
# 原因：代码模型（M2.7）擅长生成代码，但写注释和解释时语言不够流畅。
# 公司统一部署的 DeepSeek-V4-Pro 是通用模型，在语言表达上更自然。
# 代价：需要走一次网络请求到公司的模型服务。
```

### 2.6.8 降级策略全景

```
正常状态：
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  意图识别 ──→ 路由 ──→ 代码生成 ──→ M2.7 (4×A100, TTFT 1.8s) │
│                     ├── 文档写作 ──→ DeepSeek-V4-Pro (公司)  │
│                     ├── 代码审查 ──→ Qwen3-Coder-1.7B (1×A10)  │
│                     └── 安全扫描 ──→ CodeBERT (CPU)         │
└─────────────────────────────────────────────────────────────┘

M2.7 故障（心跳连续 3 次失败）：
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  意图识别 ──→ 路由 ──→ 代码生成 ──→ Qwen3.6-27B (2×A100)    │
│                     │              ⚠️ 降级：32K 上下文限制    │
│                     │              ⚠️ 复杂任务提示"请拆分"    │
│                     ├── 文档写作 ──→ DeepSeek-V4-Pro (不变)  │
│                     ├── 代码审查 ──→ Qwen3-Coder-1.7B (不变)    │
│                     └── 安全扫描 ──→ CodeBERT (不变)         │
└─────────────────────────────────────────────────────────────┘

流量突发（QPS 超过 M2.7 承载能力的 1.5 倍）：
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  网关层限流 + 优先级排队：                                    │
│    代码生成请求（高优先级）→ 队列最大长度 100                  │
│    文档写作请求（中优先级）→ 队列最大长度 50                   │
│    代码审查请求（低优先级）→ 队列最大长度 30                   │
│    超出队列长度 → HTTP 503，前端展示"当前使用人数较多，        │
│                    预计等待 X 秒，或稍后重试"                 │
│                                                             │
│  代码生成 ──→ M2.7 (主) + DeepSeek-V4-Pro (临时征用)          │
│              征用的 V4-Pro 只接代码生成高优队列溢出的请求       │
│              "V4-Pro 虽为多业务公用，但可以保证输出质量"       │
│                                                             │
│  文档写作 ──→ DeepSeek-V4-Pro (中优队列，征用期间可能延迟)     │
│                                                             │
│  代码审查 ──→ Qwen3-Coder-1.7B (低优队列，可能被拒绝)         │
│                                                             │
│  安全扫描 ──→ 不排队，不受影响 (CodeBERT 在 CPU 上跑)          │
│                                                             │
│  流量恢复正常后：                                            │
│    网关关闭限流开关，队列清空                                  │
│    DeepSeek-V4-Pro 停止接收代码生成流量，回归只处理文档/解释  │
│    M2.7 恢复独占代码生成流量                                │
└─────────────────────────────────────────────────────────────┘

M2.7 故障 + DeepSeek-V4-Pro 也不可用（最坏情况）：
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  网关层限流：                                                │
│    只放行代码生成类请求（意图 = CODE_GENERATION / REFACTORING）│
│    文档写作、解释、代码审查全部拒绝——回复统一话术：           │
│    "系统繁忙，请稍后重试或联系人工协助"                       │
│                                                             │
│  放行的代码生成请求进入排队队列：                             │
│    最大排队长度：50                                          │
│    超过 50 → 直接拒绝（HTTP 503）                            │
│    排队超时 30s → 拒绝（避免用户无限等）                      │
│                                                             │
│  代码生成任务 → Qwen3.6-27B (仅剩的算力，只保核心)            │
│    上下文窗口限制 32K（复杂多文件任务提示"请拆分后重试"）      │
│                                                             │
│  "最坏情况下的取舍：写代码是核心价值，必须保。                │
│   写文档/解释代码是锦上添花，暂时牺牲。                       │
│   宁可让 30% 的人排队等待，也不能让 100% 的人收到错误结果。"   │
└─────────────────────────────────────────────────────────────┘
```

**降级策略的核心原则：不是"所有任务都降级跑"，而是"只保证核心任务存活，非核心任务直接砍掉，流量超出承载能力就排队和限流"。**

## 2.7 不同智能体类型的模型搭配模板

### 2.7.1 三种典型智能体的模型搭配参考

基于前面的分析框架和编码智能体的案例，以下是三种常见 Agent 类型的模型搭配模板：

```
【模板一：编码智能体】

  底座模型 (主)      MiniMax-M2.7 / DeepSeek-Coder-V3 / Qwen3.6-27B
  备用模型            比主模型参数小一个量级（如 230B → 27B）
  轻量任务模型        0.5B~1.7B (意图分类、安全扫描、格式检查)
  通用任务模型        公司统一部署的通用大模型 (文档、注释、解释)
  不推荐              RAG + 向量检索 (代码场景不如直接调代码分析工具)


【模板二：客服智能体】

  底座模型 (主)      Qwen3.6-32B / Llama 4 (低延迟 + 高并发)
  备用模型            Qwen3.6-8B (基础问答够用)
  意图识别模型        0.6B (40 类意图分类，准确率达到 93%)
  安全审查模型        0.6B~1.7B (敏感内容过滤)
  多语言翻译模型      Qwen3.6-14B 专用翻译模型 (如有海外用户)
  推荐                RAG + 向量检索 (客服场景确实是 RAG 的甜区)


【模板三：数据分析智能体】

  底座模型 (主)      DeepSeek-V4.1 / Claude Sonnet 4.6 (推理能力强)
  备用模型            Qwen3.6-27B
  SQL 生成模型        DeepSeek-V4.1 (SQL 生成需求逻辑严密)
  图表描述/解释        公司通用大模型 (DeepSeek-V4-Pro)
  数据校验模型        小模型 (0.6B, 检查 SQL 语法、数据范围)
  推荐                结合结构化查询 (SQL) + 语义检索 (RAG)
```

### 2.7.2 选型决策速查表

```
你要做的智能体是？
     │
     ├── 代码相关 (生成/审查/重构)
     │     → 选编码专用模型 (MiniMax-M2.7 / Qwen3-Coder / DeepSeek-Coder-V3)
     │     → 不用 RAG，用代码分析工具
     │     → 简单审查用 0.6B~1.7B 小模型
     │
     ├── 对话/客服/问答
     │     → 选低延迟模型 (Qwen3.6-32B / Llama 4)
     │     → 用 RAG + 语义检索
     │     → 意图分类用 0.6B 小模型
     │
     ├── 数据分析/SQL
     │     → 选推理强模型 (DeepSeek-V4.1 / Claude Sonnet 4.6)
     │     → 结合 SQL 精确查询 + RAG 语义检索
     │     → SQL 校验用确定性规则
     │
     ├── 写作/创作
     │     → 选通用大模型 (DeepSeek-V4-Pro / Claude Opus 4.7 / Gemini 2.5 Pro)
     │     → 不需要专用模型——通用模型的语言流畅度更高
     │
     └── 安全/审查
           → 选 0.6B~1.7B 小模型 (规则性强，不需要创造力)
           → 结合确定性规则 (正则 + 黑名单)
           → 大模型反而容易绕过规则
```

## 2.8 本章小结

| 要点 | 核心原则 | 一句话 |
|------|---------|--------|
| 不同 Agent 不同模型 | 先拆解子任务，再为每个子任务选模型 | **不存在最好的模型，只存在最适合你子任务的模型** |
| 三维选型框架 | 参数(智力) × 生态(维护成本) × 性能(ROI) | **缺任何一个维度，决策就有盲区** |
| 大 vs 小模型 | 大模型做推理，小模型做分类和审查 | **能用规则做到 85% 的，就不需要大模型** |
| 编码 Agent 选型 | 代码专用模型 + 代码分析工具代替 RAG | **代码是结构化的，embedding 检索对它不敏感** |
| 意图路由 | 0.6B 小模型拦截 60% 简单流量 | **让大模型只处理它必须处理的核心任务** |
| 降级策略 | 先牺牲质量，再牺牲可用性 | **啄序：备用模型 → 征用通用模型 → 大不了降级但服务不挂** |
| 性能数据 | 用你自己的业务测试集，在你的硬件上测 | **benchmark 分数只能帮你筛候选，不能帮你做决策** |
