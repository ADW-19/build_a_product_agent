# 第一章：模型底座运维基础知识与架构选型

> **核心论点**：模型部署不是"找个服务器把模型跑起来就行"。生产环境下的模型服务需要回答四个硬问题——进程挂了谁拉起？流量突增能不能扛住？节点坏了业务断不断？推理引擎选哪个能同时满足延迟和并发要求？这四个问题分别对应进程管控、主从降级、容器编排、推理引擎选型。本章逐一拆解从"能跑"到"生产可用"的完整部署架构。

---

## 1.1 生产级模型部署的三个层次

模型部署没有银弹。一个 3 人团队的内部工具和一个千万 DAU 的对外服务，架构完全不同。但有一条原则是通用的：

```
业务量级          部署方案                    核心组件
─────────────────────────────────────────────────────────
小规模            单机 + 进程守护              supervisorctl
（日请求 < 1万）   一个模型实例 + 自动重启       + Nginx 反向代理

中等规模           主从双节点 + 降级            supervisorctl × 2
（日请求 1~50万）  主节点大模型 + 备节点小模型   + Keepalived/HAProxy
                                               + 健康检查脚本

大规模             容器化 + K8s 编排            Docker + K8s
（日请求 > 50万）  多副本 + 自动扩缩容           + GPU Operator
                  多模型混合调度                + Prometheus + Grafana
```

**升级路径不是线性的——业务量上来之前，不要提前过度设计。** 日请求不到 1 万就上 K8s，维护 YAML 配置的时间比开发功能还多，得不偿失。

## 1.2 supervisorctl——小规模生产的进程守护

### 1.2.1 为什么需要进程管控组件

模型推理服务本质上是一个长时间运行的 Python 进程。在生产环境中，这个进程随时可能挂：

```
模型服务的典型故障模式：

① OOM Kill —— 并发上来，显存不够，内核直接杀进程
② Python 异常 —— 某个特殊输入触发了未被 catch 的异常，进程崩溃
③ GPU 掉线 —— NVIDIA 驱动偶发故障，CUDA 不可用
④ 僵尸进程 —— 推理卡住，进程还在但已经不响应请求了
⑤ 机器重启 —— 机房维护、内核更新导致整机重启
```

**没有进程管控的生产环境 = 裸奔。** 你以为服务在跑，实际上凌晨 3 点 OOM 挂了，到早上 9 点你才发现。

> supervisorctl：一个经典的 Python 进程管理工具，负责"启动你的服务、监控它是否活着、挂了自动拉起来、日志帮你管理好"。它不解决并发、不解决扩容——但它解决"服务挂了你不用半夜爬起来重启"。

### 1.2.2 supervisorctl vs systemd vs pm2

三方都做进程守护，但选型要看场景：

| 特性              |         supervisorctl         |         systemd         |          pm2          |
| ----------------- | :----------------------------: | :---------------------: | :--------------------: |
| 配置复杂度        |      低（一个 ini 文件）      | 中（需写 service 文件） |           低           |
| Python 进程友好度 |    极佳（Python 社区标配）    |          一般          | 一般（主要是 Node.js） |
| 自动重启          |     ✅ 支持，可配重试次数     |         ✅ 支持         |        ✅ 支持        |
| 日志轮转          | ✅ 内置 stdout/stderr 自动管理 |  ❌ 需额外配 logrotate  |        ✅ 内置        |
| 进程组管理        |    ✅ 一个 group 管多个进程    |   ❌ 需写多个 service   |        ✅ 支持        |
| 资源限制          |    ❌ 无（用 cgroups 补充）    |     ✅ 原生 cgroups     |         ❌ 无         |
| 维护状态          |   经典工具，功能稳定但更新慢   |  Linux 标配，持续维护  |   活跃，Node.js 生态   |

**结论：Python 模型服务首选 supervisorctl。** 配置最简单、Python 社区最熟悉、出问题的排查路径最短。如果你需要更细粒度的资源限制（CPU/内存限制），在 supervisorctl 之上叠加 cgroups，而不是换 systemd。

### 1.2.3 完整配置示例

一个典型的 Agent 后端模型服务，supervisorctl 配置如下：

```ini
; /etc/supervisor/conf.d/agent_model_service.conf
; 一个完整的模型推理服务 supervisor 配置

[program:vllm_main_model]
; ===== 主模型：通用大模型（生产主力） =====
command=/home/agent/vllm_env/bin/python -m vllm.entrypoints.openai.api_server \
    --model /data/models/qwen2.5-72b-instruct-awq \
    --served-model-name agent-main \
    --tensor-parallel-size 4 \
    --gpu-memory-utilization 0.90 \
    --max-model-len 32768 \
    --port 8000 \
    --host 0.0.0.0

; 工作目录
directory=/home/agent

; 自动启动（随 supervisor 启动）
autostart=true

; 自动重启（挂了就拉起来）
autorestart=true

; 启动后等 30 秒再判为"启动成功"（模型加载需要时间）
startsecs=30

; 10 秒内重启超过 3 次 → 不再重启（可能不是偶然故障，是模型文件坏了）
startretries=3

; 进程停止信号：先 SIGTERM 等 120 秒，还不死再 SIGKILL（大模型卸载要时间）
stopsignal=TERM
stopwaitsecs=120

; 用哪个用户运行（不要用 root）
user=agent

; 环境变量
environment=CUDA_VISIBLE_DEVICES="0,1,2,3",VLLM_LOGGING_LEVEL="INFO"

; stdout 日志（info 级别）
stdout_logfile=/var/log/agent/vllm_main_stdout.log
stdout_logfile_maxbytes=100MB
stdout_logfile_backups=5
redirect_stderr=false

; stderr 日志（单独存放，error 排查更快）
stderr_logfile=/var/log/agent/vllm_main_stderr.log
stderr_logfile_maxbytes=100MB
stderr_logfile_backups=5


[program:agent_api_server]
; ===== Agent API 服务（FastAPI 后端） =====
command=/home/agent/venv/bin/uvicorn main:app --host 0.0.0.0 --port 8080 --workers 4
directory=/home/agent
autostart=true
autorestart=true
startsecs=5
startretries=3
stopsignal=TERM
stopwaitsecs=30
user=agent
stdout_logfile=/var/log/agent/api_stdout.log
stdout_logfile_maxbytes=100MB
stdout_logfile_backups=5
stderr_logfile=/var/log/agent/api_stderr.log
stderr_logfile_maxbytes=100MB
stderr_logfile_backups=5
; API 服务依赖模型服务先启动
; 如果模型没起来，API 起来了也没用
depends_on=vllm_main_model


[group:agent_production]
; ===== 进程组：一条命令管理整个 Agent 服务栈 =====
programs=vllm_main_model,agent_api_server
```

```bash
# supervisorctl 日常操作命令

# 重载配置（修改 ini 后）
sudo supervisorctl reread
sudo supervisorctl update

# 启动 / 停止 / 重启
sudo supervisorctl start agent_production:*
sudo supervisorctl stop vllm_main_model
sudo supervisorctl restart agent_api_server

# 查看状态
sudo supervisorctl status
# 输出：
# vllm_main_model              RUNNING   pid 12834, uptime 3 days, 12:05:42
# agent_api_server             RUNNING   pid 12856, uptime 3 days, 12:05:38

# 看实时日志
sudo supervisorctl tail -f vllm_main_model stderr
```

### 1.2.4 supervisorctl 的边界——它不管什么

supervisorctl 只管"进程活着"，它不管：

- ❌ **负载均衡**——只有一个进程监听一个端口，没有分发能力
- ❌ **并发扩容**——不会根据 QPS 自动启动更多进程
- ❌ **健康检查**——进程活着 ≠ 服务正常（模型可能推理超时）
- ❌ **跨机器管理**——只管本机，多机器需要每台单独配
- ❌ **GPU 资源管理**——不知道显存是否够用

**这些不是 supervisorctl 的 bug，是它的设计范围。** 当你需要这些能力时，意味着你该升级到下一层架构了。

## 1.3 主从节点 + 降级策略

### 1.3.1 为什么需要降级

单节点部署有一个致命问题：**你只有一个模型实例，它崩了整个服务就挂了。**

但中小团队通常负担不起两个全量模型实例——72B 模型跑两份，需要 8 张 GPU，成本翻倍。降级策略的核心思想是：**主节点用大模型保证服务质量，备用节点用小模型保证服务不挂。**

```
                    用户请求
                       │
                       ▼
              ┌────────────────┐
              │   Nginx/HAProxy │
              │   (反向代理)     │
              └───────┬────────┘
                      │
               健康检查 ──────────┐
              (每 5 秒心跳)       │
                      │           │
          ┌───────────┴───────────┴──────────┐
          │                                   │
          ▼                                   ▼
   ┌──────────────┐                   ┌──────────────┐
   │  主节点 (A)   │                   │  备节点 (B)   │
   │              │                   │              │
   │ 72B 模型     │                   │ 7B 模型      │
   │ 4×GPU        │                   │ 1×GPU        │
   │              │                   │              │
   │ 承担 100%    │  ←── A 挂了 ──→   │ 承担 100%    │
   │ 正常流量     │     自动切换       │ 降级流量     │
   │              │                   │              │
   │ RPS: 200     │                   │ RPS: 80      │
   │ P95: 3s      │                   │ P95: 1.5s    │
   │ 回复质量: 高 │                   │ 回复质量: 中  │
   └──────────────┘                   └──────────────┘
```

### 1.3.2 降级切换的四个关键决策

**决策一：什么条件触发切换？**

```python
# /home/agent/health_check.py —— 健康检查脚本
"""
由 Nginx/HAProxy 或 cron 调用，判断主节点是否健康。
不健康的判断标准比"进程活着"更严格——必须能正常推理。
"""

import aiohttp
import asyncio
import json

MAIN_NODE_URL = "http://192.168.1.10:8000/v1/chat/completions"
BACKUP_NODE_URL = "http://192.168.1.11:8000/v1/chat/completions"

# 用于心跳检测的标准 query（简单、确定性高、耗时短）
HEARTBEAT_QUERY = "回复 OK，只要这两个字母。不要其他内容。"

HEARTBEAT_TIMEOUT = 10  # 心跳超时（秒）
HEARTBEAT_MAX_TOKENS = 5  # 心跳最多生成 5 个 token


async def check_node_health(url: str) -> dict:
    """
    健康检查：不仅是"端口通不通"，而是"模型能不能推理"。

    返回：
      {"healthy": True, "latency_ms": 345}
      {"healthy": False, "reason": "timeout / error / wrong_response"}
    """
    try:
        async with aiohttp.ClientSession() as session:
            start = asyncio.get_event_loop().time()
            async with session.post(
                url,
                json={
                    "model": "agent-main",
                    "messages": [{"role": "user", "content": HEARTBEAT_QUERY}],
                    "max_tokens": HEARTBEAT_MAX_TOKENS,
                },
                timeout=aiohttp.ClientTimeout(total=HEARTBEAT_TIMEOUT),
            ) as resp:
                latency = (asyncio.get_event_loop().time() - start) * 1000

                if resp.status != 200:
                    return {"healthy": False, "reason": f"HTTP {resp.status}", "latency_ms": latency}

                data = await resp.json()
                reply = data["choices"][0]["message"]["content"].strip()

                # 模型不仅要回复，还得回复正确（防止模型幻觉/崩溃时乱输出）
                if "OK" not in reply and "ok" not in reply.lower():
                    return {"healthy": False, "reason": f"wrong reply: {reply[:50]}", "latency_ms": latency}

                return {"healthy": True, "latency_ms": latency}

    except asyncio.TimeoutError:
        return {"healthy": False, "reason": "timeout", "latency_ms": HEARTBEAT_TIMEOUT * 1000}
    except Exception as e:
        return {"healthy": False, "reason": str(e)[:100], "latency_ms": 0}
```

**触发条件（推荐配置）：** 连续 3 次心跳失败 → 切换。单次失败可能是网络抖动，立即切换会导致频繁翻转。

```python

import json
import time
from datetime import datetime

FAILOVER_LOG = "/var/log/agent/failover.log"

# 状态文件（供监控读取）
STATE_FILE = "/var/run/agent/current_active_node"


def trigger_failover(reason: str):
    """
    执行降级切换：
    1. 更新 Nginx/HAProxy 配置 → 指向备用节点
    2. 发告警
    3. 记日志
    """
    timestamp = datetime.now().isoformat()

    # 1. 切换 Nginx upstream 到备用节点
    _switch_nginx_upstream("backup")

    # 2. 写状态文件
    with open(STATE_FILE, "w") as f:
        f.write("backup\n")

    # 3. 发告警（钉钉 / 飞书 / PagerDuty）
    _send_alert(
        title="⚠️ Agent 模型服务降级",
        body=f"主节点不可用，已切换到备用节点（7B 小模型）\n"
             f"切换时间：{timestamp}\n"
             f"原因：{reason}\n"
             f"⚠️ 注意：回复质量已下降，请尽快恢复主节点！",
    )

    # 4. 记日志
    with open(FAILOVER_LOG, "a") as f:
        f.write(f"{timestamp} | FAILOVER TO BACKUP | reason={reason}\n")


def _switch_nginx_upstream(target: str):

    upstream_conf = "/etc/nginx/conf.d/agent_upstream.conf"

    if target == "main":

    else:
        upstream = "server 192.168.1.11:8000 weight=100;"

    with open(upstream_conf, "w") as f:
        f.write(f"upstream agent_model {{\n    {upstream}\n}}\n")

    # 热重载 Nginx
    subprocess.run(["nginx", "-s", "reload"], check=True)
```

**决策二：备节点用小模型，哪些能力会受损？**

```
功能                    主节点 (72B)      备节点 (7B)        影响
─────────────────────────────────────────────────────────────
简单问答（FAQ 匹配）     ✅ 准确率 95%      ✅ 准确率 90%      可接受
工具调用（查订单）       ✅ 准确率 98%      ✅ 准确率 92%      可接受
多步推理（组合查询）     ✅ 准确率 90%      ⚠️ 准确率 70%      部分降级
复杂任务（报告生成）     ✅ 准确率 85%      ❌ 准确率 45%      不可用
长上下文（> 16K）        ✅ 支持            ❌ 窗口不够         不可用
多语言                   ✅ 支持            ⚠️ 仅中英文         部分降级
```

**降级期间的策略：** 备节点只保核心功能——简单问答和基础工具调用。复杂任务直接回复"系统繁忙，请稍后重试或联系人工客服"。这比让 7B 模型胡编乱造好得多。

**决策三：怎么自动切回主节点？**

```python
# 主节点恢复后的自动切回逻辑（需人工确认）

# ❌ 不要做全自动切回！
# 原因：主节点"看起来恢复了"可能是假恢复——
#       GPU 错误导致模型加载成功但推理时随机崩溃
#       → 切回去 → 又崩 → 又切 → 反复翻转（flapping）
#       → 用户体验比一直用降级模型还差

# ✅ 正确做法：自动检测恢复 + 人工确认切回
# 1. 健康检查脚本持续探测主节点
# 2. 主节点连续 10 次心跳正常 → 发通知"主节点已恢复，是否切回？"
# 3. 运维确认后，手动或脚本执行切回
# 4. 切回后观察 30 分钟，确认稳定
```

**决策四：Nginx 层面的流量分发**

```nginx
# /etc/nginx/conf.d/agent_upstream.conf
# 主节点配置（正常运行时）

upstream agent_model {
    # 主节点权重 100（承担全部流量）
    server 192.168.1.10:8000 weight=100 max_fails=3 fail_timeout=30s;
    # 备节点正常情况下不参与（health check 标记为 down 或 weight=0）
    # backup 指令：只有当主节点全部不可用时才启用
    server 192.168.1.11:8000 backup;
}

server {
    listen 80;
    server_name agent-api.internal;

    location /v1/chat/completions {
        proxy_pass http://agent_model;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_read_timeout 120s;    # 模型推理可能很慢
        proxy_buffering off;        # SSE 流式需要关闭缓冲
        proxy_set_header X-Accel-Buffering no;
    }
}
```

注意 `backup` 关键字：Nginx 原生的备用服务器机制。主节点正常时，备节点不接收任何流量。主节点挂了 → Nginx 自动切换到 backup server。不需要外部脚本干预 Nginx 层面的切换。

### 1.3.3 从 supervisorctl 到多节点的一步之遥

```
单节点（supervisorctl）：                   主从双节点：
┌──────────────┐                      ┌──────────────┐
│  一台机器     │                      │  机器 A (主)  │
│  跑所有进程   │        ──→           │  72B 模型     │
│  挂了全挂     │                      └──────┬───────┘
└──────────────┘                             │
                                      ┌──────┴───────┐
                                      │  机器 B (备)  │
                                      │  7B 模型      │
                                      │  + failover   │
                                      └──────────────┘
                                             │
                                      ┌──────┴───────┐
                                      │ Nginx/HAProxy │
                                      │ 反向代理      │
                                      └──────────────┘
```

两台机器、各配一套 supervisorctl、一个 Nginx 做反向代理和健康路由——这就是一个"有降级能力的最小生产部署"。

## 1.4 Docker + K8s——多节点规模化编排

### 1.4.1 什么时候该升级到 K8s

```
信号                                            说明
─────────────────────────────────────────────────────────
你开始需要 3+ 个模型实例来扛并发                 supervisorctl 管多实例很痛苦

你需要同时管理 70B 推理 Pod + 7B 推理 Pod      不同模型混部在同一 GPU 集群
  + Embedding Pod + Reranker Pod                 手动分配 GPU 不现实

你需要滚动更新（不停机升级模型）                K8s RollingUpdate 天然支持

你需要在同一批 GPU 上动态调度训练和推理任务      K8s + GPU Operator 的调度能力

你需要跨机器自动恢复                            某个节点挂了，Pod 自动迁移到其他节点
```

**如果你有一个 3 人团队，日请求不到 10 万——不要上 K8s。** 维护 K8s 集群本身需要运维投入，纯属过度设计。

### 1.4.2 模型服务的 Docker 化

```dockerfile
# Dockerfile.vllm —— 基于 VLLM 官方镜像的模型服务
FROM vllm/vllm-openai:latest

# 安装额外依赖（监控、日志等）

# 模型文件可以挂载 Volume（不打包进镜像——72B 模型 150GB）

    "--model", "/models/qwen2.5-72b-instruct-awq",
```

### 1.4.3 K8s 部署要点

```yaml
# k8s/vllm-deployment.yaml —— 核心要点
apiVersion: apps/v1
kind: Deployment
metadata:
  name: vllm-main-model
  labels:
    app: agent
    model-size: large
    model-type: general
spec:
  # 主模型就 1 个副本（72B 模型需要 4 张 GPU，多副本对 GPU 需求太大）
  # 如果需要多副本 → 用 7B/13B 模型 + HPA
  replicas: 1

  # 滚动更新：先起新的，再停旧的（需要 2× 显存！）
  # 如果 GPU 不够同时跑两个 72B → 用 Recreate 策略
  strategy:
    type: Recreate  # 先停旧 Pod，再启新 Pod（省 GPU，但有短暂服务中断）

  selector:
    matchLabels:
      app: agent
      model-size: large

  template:
    metadata:
      labels:
        app: agent
        model-size: large
    spec:
      # ===== GPU 调度——K8s 部署模型的核心 =====
      nodeSelector:
        # 标记：只调度到有 GPU 的节点
        accelerator: nvidia-a100
      # 或者用 topologySpreadConstraints 避免全挤在一台机器上

      containers:
      - name: vllm-server
        image: registry.internal/agent/vllm-server:v1.2.0
        ports:
        - containerPort: 8000
          name: http

        resources:
          limits:
            nvidia.com/gpu: 4  # 4 张 GPU（tensor-parallel-size=4）
          requests:
            nvidia.com/gpu: 4  # requests = limits，GPU 不能用 burst

        env:
        - name: CUDA_VISIBLE_DEVICES
          value: "0,1,2,3"

        # ===== 存活探针（Liveness）=====
        # 探测模型是否还能正常推理。失败了 → K8s 杀 Pod 重建。
        livenessProbe:
          httpGet:
            path: /health
            port: 8000
          initialDelaySeconds: 120  # 模型加载需要时间，别急着杀
          periodSeconds: 30
          timeoutSeconds: 10
          failureThreshold: 3        # 连续 3 次失败才杀

        # ===== 就绪探针（Readiness）=====
        # 探测模型是否准备好接收流量。失败了 → 从 Service 移除，不杀 Pod。
        readinessProbe:
          httpGet:
            path: /health
            port: 8000
          initialDelaySeconds: 120
          periodSeconds: 10
          timeoutSeconds: 5
          failureThreshold: 2

        # ===== 模型文件通过 Volume 挂载（不打包进镜像） =====
        volumeMounts:
        - name: model-storage
          mountPath: /models
          readOnly: true

      volumes:
      - name: model-storage
        persistentVolumeClaim:
          claimName: model-weights-pvc  # 模型权重用 PV/PVC 管理

---
# k8s/vllm-service.yaml
apiVersion: v1
kind: Service
metadata:
  name: vllm-main-service
spec:
  selector:
    app: agent
    model-size: large
  ports:
  - port: 8000
    targetPort: 8000
  type: ClusterIP  # 集群内部访问，不暴露公网
```

**K8s 部署的四个关键要点：**

1. **GPU 资源是稀缺的。** 72B 模型需要 4 张 GPU，如果用 RollingUpdate 策略，需要 8 张才能不停机更新——大多数团队没这个预算。妥协方案是用 `Recreate`（先停后启），接受 2 分钟的服务中断。
2. **模型文件不要放镜像里。** 72B 模型约 140GB，打包进镜像 → Docker registry 爆炸。用 PV/PVC 或 hostPath 挂载模型文件。
3. **Health check 要走真实推理。** 仅检查端口 8000 是否通是不够的——模型可能加载成功但推理时 CUDA 错误。Health check 应该调一次真实推理。
4. **不需要 HPA（水平自动扩缩容）的前提是想清楚。** GPU 模型不是无状态 Web 服务——扩缩容需要几十秒加载模型（GV 级别权重），远不如增加 replicas 有效。更好的做法是小模型多 replica + 大模型单 replica，而不是对大模型做 HPA。

## 1.5 1通用模型 + N个小模型——Agent 底座的"舰队模式"

### 1.5.1 为什么不是一个大模型全干

直观想法：选一个最强的模型（如 GPT-4o、Claude Opus、Qwen-72B），所有任务都丢给它。

```
"大模型全干" 的问题：

                    ┌─────────────────────────┐
                    │    72B 通用大模型         │
                    │                          │
  "你好" ──────────→│  简单问候                 │→ "你好！有什么可以帮您？"
                    │  耗时 800ms, 0.02元       │
                    │                          │
  "帮我查订单" ────→│  工具调用                 │→ 订单信息
                    │  耗时 2500ms, 0.08元      │
                    │                          │
  "这个用英文翻译"─→│  翻译任务                 │→ 翻译结果
                    │  耗时 1200ms, 0.04元      │
                    │                          │
  "总结这篇文章"───→│  长文本总结               │→ 等待 8 秒...
                    │  耗时 8000ms, 0.25元      │
                    │                          │
  100 并发同时来 ──→│  💥 OOM                   │
                    └─────────────────────────┘

问题一：成本。简单任务（问候、FAQ 匹配）不需要 72B 模型，但大模型全干了。
        用 GPT-4o 回复 "你好" 和用 GPT-4o-mini 回复 "你好"，
        成本差 20 倍，准确率没有实质差异。

问题二：延迟。所有请求排同一个队列，翻译任务在等前面的长文本总结完成。
        一个大模型同时只能处理有限并发。

问题三：单一故障点。这一个大模型挂了，所有功能全挂。
```

### 1.5.2 舰队模式的核心思想

```
                    ┌─────────────────────────────────────────────┐
                    │              Agent 路由层                    │
                    │   (意图识别 → 任务分类 → 模型分发)            │
                    └──────┬──────────┬──────────┬────────────────┘
                           │          │          │
              ┌────────────▼──┐ ┌─────▼─────┐ ┌─▼──────────┐
              │  通用模型      │ │ 翻译模型   │ │ 摘要模型    │
              │  72B (vLLM)   │ │ 13B (SG)  │ │ 7B (SG)    │
              │               │ │           │ │            │
              │  负责：        │ │ 负责：     │ │ 负责：      │
              │  复杂推理      │ │ 翻译任务   │ │ 长文本摘要  │
              │  工具调用      │ │ 多语言处理 │ │ 格式化输出  │
              │  多步决策      │ │           │ │            │
              │               │ │           │ │            │
              │  实例数: 1    │ │ 实例数: 2  │ │ 实例数: 3  │
              │  延迟: 2-8s   │ │ 延迟: 0.5s │ │ 延迟: 3-5s │
              └───────────────┘ └───────────┘ └────────────┘
```

**1 个通用大模型的职责：**

- 复杂多步推理（"帮我分析这个方案的三条路径"）
- 需要综合多个工具调用的任务
- 意图不明确、需要追问和澄清
- 输出质量要求最高的场景（如给用户看的正式回复）

**N 个小模型的职责：**

- 高频、低延迟任务（翻译、分类、实体提取、FAQ 匹配）
- 特定领域任务（代码生成、SQL 生成、数学计算）
- 预处理和后处理（query 改写、回复格式化、安全审查）
- 流量削峰——简单任务不走大模型，节省算力

### 1.5.3 三个维度量化对比

```
场景：日均 100 万次 Agent 请求，其中 40% 简单任务、35% 中等问题、25% 复杂任务

方案 A：全用 72B 模型
  GPU：12 × A100（3 台 4 卡机器）
  日均 GPU 成本：12 × 24h × ¥12/h ≈ ¥3,456
  平均延迟：3.2s
  最大并发：约 60 QPS（72B 模型单实例）

方案 B：1×72B + 3×7B（舰队模式）
  GPU：4 × A100（72B）+ 3 × A10（7B×3）= 4 卡 + 3 卡
  日均 GPU 成本：4×24×¥12 + 3×24×¥5 ≈ ¥1,512
  平均延迟：1.8s（简单任务走 7B，耗时 0.3s）
  最大并发：约 200 QPS（7B 可开多实例）
  
  成本降低 56%，延迟降低 44%，并发能力提升 3 倍。
```

### 1.5.4 为什么主流架构都在选这个

不是因为理论上更优美，而是因为**成本账算得很清楚**：

1. **GPU 利用率。** 一个大模型独占了 4 张 A100，但 40% 的请求是简单任务——相当于用 4 张 A100 在处理"你好""再见"。舰队模型让 GPU 物尽其用。
2. **独立扩缩容。** 双十一期间翻译请求暴涨（海外用户涌入）——只需要给翻译小模型加 2 个实例，不用动通用大模型。解耦 = 弹性。
3. **故障隔离。** 翻译小模型崩了，翻译功能降级（提示"暂时无法翻译"），但核心对话功能不受影响。大模型全干模式下，一个任务类型崩 = 全部崩。
4. **迭代速度。** 翻译小模型可以单独 fine-tune、单独部署、单独 A/B 测试。改一行 prompt 不需要重新部署 140GB 的 72B 模型。

## 1.6 VLLM——生产级推理引擎的首选

### 1.6.1 VLLM 是什么

VLLM 是一个**高性能大语言模型推理引擎**，由 UC Berkeley 团队开发，目前是开源社区事实上的标准。它的核心贡献是 **PagedAttention**——一种显存管理算法，将操作系统中的"虚拟内存 + 分页"思想应用到 LLM 的 KV Cache 管理中。

```
传统 KV Cache 管理的问题：
┌───────────────────────────────────────────────────────┐
│ 为每个请求预分配一块连续的显存来存 KV Cache              │
│                                                       │
│ 请求 A: ████████░░░░░░░░░░░░  (预分配 1000，实际用 600) │
│ 请求 B: ██░░░░░░░░░░░░░░░░░░  (预分配 1000，实际用 100) │
│          │                                            │
│          └── 内部碎片，浪费 40%~70% 显存 ──┘            │
│                                                       │
│ 结果：实际能用 80 个请求的显存，只能跑 30 个             │
└───────────────────────────────────────────────────────┘

PagedAttention 的解决方式：
┌─────────────────────────────────────────────┐
│ KV Cache 按"页"（Page）分配，不连续也没关系   │
│                                             │
│ 显存: [A-p1][B-p1][A-p2][C-p1][B-p2][A-p3]  │
│         ↑ 按需分配，不预留 ↑                  │
│                                             │
│ 结果：同样的显存，并发能力提升 2~4 倍          │
└─────────────────────────────────────────────┘
```

**一句话：VLLM 让你用同样多的 GPU 显存，同时服务更多用户。**

### 1.6.2 VLLM 的核心优势

| 优势                          | 说明                             | 对你的意义                   |
| ----------------------------- | -------------------------------- | ---------------------------- |
| **PagedAttention**      | 显存利用率从 30%~60% 提升到 90%+ | 4 张卡能干原来 8 张卡的活    |
| **Continuous Batching** | 请求不排队，边生成边接新请求     | 并发能力质变                 |
| **生态完善**            | 支持 500+ 模型，社区 4 万+ Star  | 遇坑容易搜到答案             |
| **OpenAI 兼容 API**     | 直接替换 OpenAI SDK 的 base_url  | 改一行代码从 OpenAI 迁移     |
| **量化支持**            | AWQ / GPTQ / FP8 / INT8          | 72B → 可以在 2 张 A100 上跑 |
| **Tensor Parallelism**  | 多 GPU 自动拆分模型              | 不需要手写模型并行代码       |
| **Prefix Caching**      | 相同 system prompt 只算一次      | 每个请求省 200ms             |
| **多模态**              | 支持视觉语言模型                 | 图文混合场景不用换引擎       |
| **生产配套**            | Prometheus 指标、分布式追踪      | 监控告警开箱即用             |

### 1.6.3 VLLM 的不足

```
不足                            什么时候会遇到
────────────────────────────────────────────────────────────
长序列（> 64K）吞吐下降明显      摘要 100 页 PDF、长文档分析
调度策略较简单                  高并发 + 多优先级混合场景
                                时，低优先级请求可能被饿死

对投机解码（Speculative         小模型辅助大模型加速推理的
Decoding）支持较晚              场景，SGlang 更成熟

prefix caching 与 chunked       long context 场景下有时
prenfill 配合有 bug             会触发
```

**总的来说，VLLM 的劣势集中在特定优化场景——大部分团队的日常业务不需要操心这些。**

## 1.7 SGlang——追求极致推理效率的选择

### 1.7.1 SGlang 是什么

SGlang 是另一个高性能 LLM 推理引擎，由斯坦福等团队开发。如果 VLLM 的关键词是"生态完善、稳"，SGlang 的关键词就是**"快、更快、还是快"**。

它的核心技术是 **RadixAttention**——一种基于前缀树（Radix Tree）的 KV Cache 复用机制。

```
VLLM Prefix Caching vs SGlang RadixAttention：

场景：3 个请求共享相似的 system prompt

  system_prompt_A: "你是一个客服助手，请用中文回答..."    (200 tokens)
  system_prompt_B: "你是一个客服助手，请用英文回答..."    (200 tokens)
  共享前缀:        "你是一个客服助手，请用"               (180 tokens)

VLLM:                               SGlang:
  检测到前缀相同 → 复用一次           前缀组织成 Radix Tree：
                           
      请求 A: 重新计算 200 tokens        [你是一个客服助手，请用]
      请求 B: 复用 A 的 KV Cache       /                    \
      请求 C: 部分复用                   [中文回答...]    [英文回答...]
                                        (自动复用 180 tokens)
  → 复用粒度：粗                        → 复用粒度：细
  → 适合：system prompt 完全相同      → 适合：前缀大量重叠
```

**一句话：如果你的多个请求之间有大量共享前缀（Agent 系统经常如此——system prompt、对话历史、RAG 上下文高度重叠），SGlang 的 RadixAttention 比 VLLM 的 Prefix Caching 复用率更高。**

### 1.7.2 SGlang 的核心优势

| 优势                           | 说明                                    | 对比 VLLM                       |
| ------------------------------ | --------------------------------------- | ------------------------------- |
| **RadixAttention**       | 前缀树复用 KV Cache，共享前缀自动合并   | 比 VLLM Prefix Caching 更细粒度 |
| **更高吞吐**             | 同硬件下，部分 benchmark 吞吐高 1.3~2× | 优势场景：高并发 + 前缀重叠     |
| **Speculative Decoding** | 原生支持，小模型"草稿"加速大模型        | VLLM 支持较晚                   |
| **结构化输出**           | 原生 constrained decoding（JSON/Regex） | VLLM 需 guided_decoding 后端    |
| **调度策略**             | 更灵活的优先级调度                      | SGlang 调度器更精细             |

### 1.7.3 SGlang 的不足

```
不足                            什么时候遇到
────────────────────────────────────────────────────────────
生态不如 VLLM 成熟              GitHub Star 约 VLLM 的 1/3
                                某些不太主流的模型/量化格式支持度不够

社区规模较小                    踩坑时中文资料少，英文 Issue 响应速度
                                不如 VLLM

更新激进，API 不稳定            版本升级偶尔 breaking change，
                                生产环境升级需谨慎

多模态支持弱于 VLLM             视觉语言模型(VLM)支持不如 VLLM 完善

部分硬件平台支持不完整           非 NVIDIA GPU（如昇腾、AMD）的支持
                                不如 VLLM 广泛
```

## 1.8 VLLM vs SGlang 选择指南

### 1.8.1 决策框架

```
                    ┌─ 优先稳定性、生态 → VLLM
                    │
开始选型 ── 你的优先级是？──┤
                    │
                    └─ 优先吞吐、延迟 → SGlang
```

更具体的决策矩阵：

| 场景                                             |  推荐  | 原因                                           |
| ------------------------------------------------ | :----: | ---------------------------------------------- |
| **团队刚开始搞模型部署**                   |  VLLM  | 社区资料多、踩坑成本低                         |
| **模型是 70B+ 大参数**                     |  VLLM  | 大模型环境下 VLLM 优化更稳定，TP/PP 支持更成熟 |
| **模型是 7B~13B 小参数 + 高并发**          | SGlang | 小模型并发场景下 SGlang 吞吐优势明显           |
| **Agent 场景（system prompt 大量共享）**   | SGlang | RadixAttention 的前缀复用率极高                |
| **多模态场景（图文混合）**                 |  VLLM  | VLM 支持更完善                                 |
| **需要稳定的生产 SLA（5 个 9）**           |  VLLM  | 版本稳定，breaking change 少                   |
| **需要极致延迟（< 200ms 首 token）**       | SGlang | 调度器更精细，延迟控制更好                     |
| **需要 FP8 量化（H100/H800）**             |  VLLM  | FP8 支持更早更稳定                             |
| **需要多节点分布式推理**                   |  VLLM  | Pipeline Parallelism 支持更成熟                |
| **需要 constrained decoding (JSON/Regex)** | SGlang | 原生支持，速度快                               |

### 1.8.2 大参数 vs 小参数模型的选择差异

```
大参数模型（70B+）：
  → 优先 VLLM
  原因：
  - VLLM 的 tensor parallelism 和 pipeline parallelism 更成熟
  - 大模型场景下 PagedAttention 的显存效率优势发挥得最充分
  - 大模型部署的坑 VLLM 社区基本都踩过了

小参数模型（7B-13B）+ 高并发（100+ QPS）：
  → 优先 SGlang
  原因：
  - 小模型瓶颈不在显存，在调度效率——SGlang 调度器更强
  - 高并发下 RadixAttention 的前缀共享优势最大化
  - SGlang 的 speculative decoding 对小模型无效（已经是小的了），
    但对"小模型辅助大模型"架构有用

中等参数模型（30B-70B）+ 中并发：
  → 两者都可以，VLLM 更稳
  原因：
  - 这个区间的差异不大，选你团队更熟悉的
  - 优先 VLLM——踩坑成本更低
```

### 1.8.3 实际项目中两者共存是常态

```
Agent 系统的典型部署组合：

  通用大模型（72B）──────── vLLM（稳定、生态好、7×24 不崩）
  翻译小模型（13B）──────── SGlang（高并发、低延迟）
  摘要小模型（7B）───────── SGlang（前缀共享高）
  Embedding 模型─────────── TEI / Infinity（专用 Embedding 引擎）
  Reranker 模型──────────── TEI / Infinity
```

**不是 VLLM 和 SGlang 二选一，而是"哪个模型用什么引擎"。** 同样的 GPU 集群里可以同时跑 VLLM 和 SGlang——它们只是推理引擎，不互斥。

## 1.9 Ollama——为什么生产环境绝对不要用

### 1.9.1 Ollama 的设计目标是什么

Ollama 的官网描述是 *"Get up and running with large language models"*。它的目标用户是在本地电脑上快速跑模型的开发者——写个 demo、做个原型、玩玩 Llama 3。

> **Ollama 是一辆卡丁车，你可以在小区里开得很开心。但不要把它开上高速公路。**

### 1.9.2 六大硬伤——逐条说清楚

**硬伤一：并发能力≈没有**

```
Ollama 的并发模型：
  请求排队 → 一个一个处理

实际测试（来自社区报告，Ollama 0.3.x）：
  机型：A100 80GB，模型 Qwen2.5-7B
  单请求延迟：200ms
  10 并发请求的 P95 延迟：1800ms  ← 9 倍退化
  50 并发请求的 P95 延迟：超时或无响应

VLLM 同等条件：
  单请求延迟：180ms
  50 并发 P95 延迟：450ms  ← 仅 2.5 倍退化
```

Ollama 没有 Continuous Batching——请求来了排队，前面的处理完才轮到你。这在本地用是正常的（你一个人用，没有并发），在生产环境是灾难性的（100 个用户同时在等）。

**硬伤二：安全漏洞多**

Ollama 的安全漏洞不是"可能被攻击"，而是"已经被曝光且修复速度慢"：

```
CVE-2024-XXXX：Ollama API 默认监听 0.0.0.0:11434，无认证
  → 内网任何机器可以调用你的模型，甚至可以上传恶意模型
  → 修复前，公网暴露的 Ollama 实例已被大规模扫描利用

CVE-2024-YYYY：路径遍历漏洞
  → 通过构造特殊请求读取服务器上的任意文件

CVE-2024-ZZZZ：Server-Side Request Forgery (SSRF)
  → 通过 Ollama 作为跳板攻击内网其他服务
```

**Ollama 是为 C 端个人电脑设计的，默认配置就是"方便 > 安全"。** 这在生产环境是不可接受的。

**硬伤三：推理效率低**

Ollama 底层基于 llama.cpp，对推理做的优化主要是"让模型能在消费级硬件上跑起来"（量化、CPU 推理、Metal/CUDA 基础加速）。但它缺少 VLLM/SGlang 中的关键优化：

| 优化技术             |   VLLM   |       SGlang       |       Ollama       |
| -------------------- | :-------: | :-----------------: | :-----------------: |
| PagedAttention       |    ✅    |  ❌ (用了自己方案)  |         ❌         |
| Continuous Batching  |    ✅    |      ✅ (更优)      |         ❌         |
| Prefix Caching       |    ✅    | ✅ (RadixAttention) | ❌ (仅基础 KV 缓存) |
| Tensor Parallelism   | ✅ (原生) |         ✅         |   ❌ (需外部工具)   |
| FP8 量化             |    ✅    |         ✅         |         ❌         |
| Speculative Decoding |    ✅    |         ✅         |         ❌         |

**同样一张 A100，VLLM 跑出来的 QPS 是 Ollama 的 3~5 倍。**

**硬伤四：内存/显存管理粗糙**

Ollama 加载模型的方式是"一把梭"：整个模型加载进显存，然后预分配一个固定大小的 KV Cache buffer。不用的显存浪费了，不够用的时候直接 OOM。VLLM 的 PagedAttention 已经把这个问题解决得很好了。

**硬伤五：完全没有生产级的可观测性**

```
你需要的东西             VLLM 有吗        Ollama 有吗
─────────────────────────────────────────────────
Prometheus 指标          ✅ 内置          ❌
OpenTelemetry 追踪        ✅ 支持           ❌
结构化日志                ✅               ⚠️ 半吊子
请求级别的延迟统计        ✅                ❌
GPU 利用率监控            ✅                ❌
并发队列深度              ✅                ❌
```

**生产环境看不到这些指标 = 盲飞。** 你不知道服务什么时候接近极限、哪个请求慢了、GPU 是不是在空转。

**硬伤六：API 不规范**

Ollama 的 API 虽然模仿了 OpenAI 格式，但有大量自定义字段和行为差异。当你从 Ollama 切换到 VLLM/SGlang 时，代码需要改动，而不是"换个 URL 就行"。

### 1.9.3 Ollama 唯一适合的场景

```
✅ 适合：
  - 本地开发调试（"跑一下看看效果"）
  - 个人项目、hackathon 原型
  - CI 中的轻量级模型测试
  - 完全不考虑并发的单用户场景

❌ 不适合：
  - 任何需要服务多个用户的场景
  - 任何需要 SLA 保证的场景
  - 任何暴露在公网或内网的场景
  - 任何对延迟有要求的场景
  - 任何对吞吐有要求的场景
```

**一句话总结：能用 Ollama 跑起来 ≠ 能上生产。跑起来的下一步是选对推理引擎，而不是把 demo 服务器直接暴露给用户。**

## 1.10 本章小结

| 要点         | 核心原则                                     | 一句话                                                      |
| ------------ | -------------------------------------------- | ----------------------------------------------------------- |
| 进程管控     | supervisorctl 是 Python 模型服务的标配       | **进程挂了自动拉——这是生产环境的底线**              |
| 主从降级     | 主节点大模型保质量，备节点小模型保可用       | **不能要求小团队跑两个 72B，但可以要求它们不挂**      |
| Docker + K8s | 日请求 > 50 万或需要多模型混部时再上         | **K8s 解决的是规模化问题，不是起步问题**              |
| 舰队模式     | 1 通用大模型 + N 专用小模型                  | **不是一个大模型全干——成本、延迟、可靠性三重收益**  |
| VLLM 首选    | 生态最完善的推理引擎，默认选择               | **不知道选什么就选 VLLM，不会错**                     |
| SGlang 可选  | 高并发 + 前缀共享场景的极致效率              | **追求极致吞吐时换 SGlang，但不适合第一个项目**       |
| Ollama 禁用  | 会在生产环境让你崩溃                         | **卡丁车不能上高速——Ollama 是开发工具不是生产引擎** |
| 两者共存     | 大模型用 VLLM 保稳定，小模型用 SGlang 冲吞吐 | **不是二选一，是谁适合什么场景**                      |
